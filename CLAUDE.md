# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Patra is a Flutter mobile client (iOS + iPadOS + Android) for [Kavita](https://www.kavitareader.com/), a self-hosted manga/comics/book server. Login (multi-server), home shelves, library grid, series detail, an image reader with three reading directions, and offline downloads work. EPUB reading is still on the roadmap (see README.md).

## Commands

```sh
flutter pub get          # install dependencies
flutter analyze          # lint — must stay at zero issues
flutter test             # run all tests
flutter test test/x_test.dart   # run a single test file
flutter run -d linux     # fastest local run
```

On this dev machine the Flutter SDK lives in `~/development/flutter` (PATH set in `~/.zshrc`); in non-interactive shells use `export PATH="$HOME/development/flutter/bin:$PATH"` first. Android SDK is at `~/Android/Sdk`. The app targets iOS + Android; Linux desktop is enabled purely as a fast local dev target. `compileSdk` is pinned to 37 in `android/app/build.gradle.kts` because `flutter_secure_storage` requires it. iOS builds only happen in CI (`.github/workflows/build.yml`); there is no Mac here, and nothing about iOS can be reproduced locally. CI leaves a sideloadable artifact for a push to `main`, never for a pull request; what reaches a **store** is only ever a tag.

**Releases are cut by a tag, not by a push.** `on:` fires for a push to `main`, a pull request, and a `v*` tag, but only the tag takes a signed path — and both platform jobs decide that from `github.ref`, not from the event name, so a `workflow_dispatch` aimed at a tag (`gh workflow run build.yml --ref v0.1.0`) is the same release. That dispatch is the recovery hatch for a release that failed halfway: GitHub's own *re-run* keeps its run number, which both stores would then reject as one they have already seen. **The tag is the version, not just the trigger**: it is passed to `--build-name`, which writes Android's `versionName` and iOS's `CFBundleShortVersionString`, and the app reads its own version back out of that at startup rather than compiling one in (see `ClientIdentity` below). So cutting a release is `git tag v0.2.0 && git push origin v0.2.0` and nothing else — no commit, nothing in the repository to bump, and no way for a shipped binary to disagree with the tag it was built from. Push the **one** tag by name, never `--tags`: GitHub creates no event at all for a push carrying more than three tags, so a backlog of local tags would ship nothing and say nothing. Publishing a GitHub **release** works identically and for the same reason — publishing creates the tag, and that push is the trigger — but only when the release is the thing that creates it: made against a tag that already exists it pushes nothing, and nothing runs. A *draft* release creates no tag either, so it triggers on publish and not before. `version:` in pubspec is only the default a *local* build falls back to. What `analyze` checks is therefore the tag's shape rather than its agreement with anything: App Store Connect takes `CFBundleShortVersionString` as one to three dot-separated integers and nothing else, so `v0.2` and `v0.2.0-rc1` are refused before a runner is spent on them. The Android job then greps the versionName back out of the bundle it built, because the tag is now the only place the version lives. Everything else — `main`, pull requests — compiles and tests and ships nothing.

**The build number stays `github.run_number`; the tag cannot replace it.** Both stores want a number that only ever goes up — Play refuses a `versionCode` it has already accepted and wants each higher than the last, App Store Connect refuses a build number it has already seen. Pubspec's `+1` never moves, and a version read as a number does not clear the run numbers already sitting in both stores (25 when the trigger changed) and would repeat itself on a second build of one version. `run_number` counts every run of *this workflow file*, pull requests included, so the numbers jump between releases: increasing is the requirement, not consecutive. Both platform jobs are in the same run, so one tag ships one number to the two stores. Renaming `build.yml`, or its `name:`, restarts that count at 1 and every upload after it is rejected.

The iOS job has **two paths, chosen by whether this is a release ref *and* the signing secrets exist**. With both it signs and uploads to TestFlight; without them it falls back to the historical unsigned IPA meant to be re-signed and sideloaded (AltStore/Sideloadly), so a repository with no Apple credentials — a fork, or this one before the account was wired up — still builds green, and so does every ordinary push to `main`. The signed path writes signing into **`ios/Flutter/Release.xcconfig`**, which is the `baseConfigurationReference` of the *Runner target* — not of the project. That scope is the whole point: the same settings on `xcodebuild`'s command line reach every target in the build, and the Swift Package Manager packages Flutter now uses for plugins fail the archive outright with "does not support provisioning profiles". A target xcconfig also outranks the project-level `CODE_SIGN_IDENTITY = "iPhone Developer"` the Flutter template ships (a development identity TestFlight rejects), and it keeps the team ID in a secret rather than in the repository. With `DEVELOPMENT_TEAM` present in the build settings the flutter tool skips its hunt for a *development* certificate (`code_signing.dart`), which a runner holding only a distribution certificate can never satisfy — that hunt runs before `--config-only` is honoured, so on any path that does not set the team, `--no-codesign` is what gets past it. `ExportOptions.plist` is generated per run for the same reason, and the provisioning profile's *name* is read back out of the profile itself rather than hardcoded, so it cannot drift from what was typed into Apple's portal.

**The main manifest declares `android.permission.INTERNET`, and CI checks the bundle still does.** Flutter's template declares it only in `src/debug/` and `src/profile/`, where it exists for the tool's own hot-reload channel — so a *release* build shipped with no network at all: it installed, opened, and failed every request at the connection, on any address. Nothing catches this. `flutter analyze` and every Dart test pass, the app builds and runs, and the only symptom is `DioExceptionType.connectionError` everywhere, which reads exactly like a server that is down. It went unnoticed until the first release build reached a device, because CI had only ever produced debug APKs. The build step now unzips the bundle it just made and greps its manifest — `grep -qa`, since a bundle's manifest is protobuf and some greps call that binary and report no match.

The **Android job mirrors that shape**, and for the same reason — a tag plus the secrets, or the fallback. Its switch is `android/key.properties`: `build.gradle.kts` reads it if it is there and falls back to the *debug* keys if it is not, so a fork and a fresh clone still build (`flutter run --release` included) while Play — which refuses a debug-signed bundle — gets a real one. CI writes that file from secrets into the runner's temp directory and deletes it in an `always()` step. What it produces is an **App Bundle**, not an APK: `.aab` is the only thing Play accepts. Its `versionCode` and the iOS build number are the same `github.run_number`, above.

Upload to the internal track is a **third** state, gated separately on `PLAY_SERVICE_ACCOUNT_JSON`, because the Play Developer API *cannot create an application*: the first bundle has to go through the Console by hand, so until that is done there is no service account to make one from and the step stays skipped rather than red. The AAB is an artifact in the meantime, which is what gets uploaded manually. The track is set through `tracks` (plural, comma-separated; the singular `track` is deprecated and giving both is a hard error) and must never be left out — the action's default is **production**. It is `internal` — deliberately, while the app is being iterated on: internal testing has no review delay and takes up to 100 testers. It is **not** the closed track, so it does not advance the twelve-testers-opted-in-continuously-for-fourteen-days clock a personal account created after 13 November 2023 must run before it may even ask for production access. Only a closed test (`alpha`) does. Changing that one word is what starts the clock. The release is named after the tag (`releaseName`), or the Console would list it as "25 (0.1.0)". The upload action is pinned to a **commit**, not a tag, because it is handed the service account key and a tag can be moved under it.

Android secrets: `ANDROID_KEYSTORE_BASE64` (the upload keystore, base64 of it — a **PKCS12**, which is what a modern JDK's `keytool` writes and what Gradle assumes while nothing sets `storeType`; the file's extension is never read by anything), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`, and later `PLAY_SERVICE_ACCOUNT_JSON`. Losing the upload keystore is recoverable *only* if Play app signing is enabled, which keeps the real signing key on Google's side and leaves the upload key replaceable — take that option.

Secrets, all in GitHub Actions: `IOS_DIST_P12_BASE64` + `IOS_DIST_P12_PASSWORD` (the Apple Distribution certificate and its private key, exported with `openssl pkcs12 -export -legacy` — OpenSSL 3's default AES-256 PKCS#12 is one macOS `security import` cannot read), `IOS_PROVISION_PROFILE_BASE64`, `IOS_TEAM_ID`, and the App Store Connect API key `ASC_KEY_ID` / `ASC_ISSUER_ID` / `ASC_API_KEY_P8_BASE64` that `altool` uploads with. The certificate and the profile expire after a year. `ITSAppUsesNonExemptEncryption = false` in `Info.plist` is what keeps every build from stalling on a manual export-compliance answer; the app uses only the OS's own HTTPS, which is exempt, plus cleartext HTTP, which is no encryption at all.

## Design system — the handoff is the source of truth

This UI implements a Claude Design handoff kept at `.claude/design/HANDOFF.md` — **untracked on purpose**, so it is there on this machine and absent from a fresh clone. Read it before changing anything visual — **except its §3 and §5**. §3 still says the reader's top bar carries a single reading-direction pill and "NO separate mode/direction toggles"; the rule against splitting *how pages advance* into a mode plus a direction still stands, but the pill itself is now a cog (see the reader section below). §5 still describes the retired "unfinished page" mark and is superseded by `.claude/design/icons/README.md` (the frond) and by the icon and launch-animation sections below; where it is missing, `lib/src/theme.dart` and the notes below are the reference. `lib/src/theme.dart` holds every token (colors, radii, spacing, type scale) plus shared primitives (`SectionLabel`, `CoverProgressBar`, `Skeleton`); shared widgets live in `lib/src/widgets/`. Never hardcode a color or a radius in a screen.

Two hard rules from the handoff:
- **`patraAccent` (purple) = reading progress and identity. `patraOffline` (teal) = downloads and offline. Never swap them.**
- Serif (`PatraText.serifTitle`, Source Serif 4) is only for titles of works, the wordmark, and reader page numerals. Everything else is Space Grotesk.

The handoff was drawn for a phone, so **the iPad is ours to reason about**, and a screen full of phone furniture is what it looks like when nobody did. One token carries it: `isTabletLayout(context)`, which asks the *shortest* side against `tabletBreakpoint` so a phone in landscape is still a phone (the same question `ClientMetrics.isTablet` answers for Kavita). Three shapes, three answers, and which one a screen is decides everything:

- **A column of rows** (series, downloads, settings, and the sheets settings opens) runs **the full width at the app's own gutter**, like every other screen. It was once capped and centred, on the argument that a row's parts otherwise drift to opposite edges with a gulf between them — true, and the cure was worse: at 560 an 820pt iPad wore about 150pt of nothing down each side, and a narrow column floating between two empty bands reads as more wrong than the gap it closes. **The answer to a tablet's width is a grid, not a narrower column.** Inside the row the phone's furniture still *grows*: 46x66 covers become 80x115 (`rowCoverWidth`/`rowCoverWidthTablet` in `theme.dart`, because the series screen and the Downloads tab draw the same row and drifted apart when each held its own number), the row breathes, the type goes one step up the scale. Those sizes were originally derived as ~13% of the capped column — the share a phone gives the cover — and with the cap gone the cover is ~10% of its row again; they stay because they read well at arm's length, not because the proportion still holds. Whatever is drawn on the cover scales with it (the read badge) and so does the decode width, which is computed from the width actually drawn rather than frozen at the phone's 138 — a constant there is the blur the bigger cover was meant to remove. Pinned by `test/series_sections_test.dart`, which also pins that the column is *not* capped: the cover starts one gutter from the screen edge and the save pill ends one gutter from the other.
- **A grid of cards** (the library grid, the home libraries) keeps the size a card is drawn at and takes **another column** instead: `_gridColumns` and `_cardWidth` divide the width by a max card width, with the handoff's phone count (three covers, two cards) as the floor. Three covers across an iPad would be 250pt each; five at 146 is the same screen the phone shows, only more of it.
- **A shelf and the reader canvas run edge to edge** — that is what they are. A shelf spends a tablet's width on bigger tiles (112 → 152); the reader is left alone, because there the whole screen is the point.

Two things must never scale with the screen — **a swipe pane and a button**. `flutter_slidable` asks for an `extentRatio`, but a ratio that is a sensible drawer on a phone slides a tablet's row far enough to hide the cover and title the swipe is about to act on, so `_ChapterRow` measures the row and converts a *width in points* into that ratio; and a button given a whole hero (or a whole settings screen) to fill stops reading as a button, so the resume and sign-out buttons stop at 280. Pinned at 820x1180 by `test/tablet_layout_test.dart`, `test/series_hero_test.dart` and `test/series_sections_test.dart`.

**An empty library is a state, not a blank screen.** A library is empty because the server has not scanned its files, so the copy points at the server and names the library — the name is picked *out of* the localized sentence by `indexOf` rather than concatenated onto it, or a French sentence would be assembled in English word order; a name it cannot find simply loses its emphasis. The dashed rounded outline is the handoff's mark for **a place to fill** (`DashedBorderPainter`, shared with the "add a server" slot), as against the solid borders that enclose something already there. The empty state is pullable like the grid it stands in for, because after asking for a scan there has to be a way to look again. Covered by `test/empty_library_test.dart`.

The mark is **the palm frond**, and it comes in two variants. `assets/icon/patra-1024.png` is the five-blade fan; `assets/icon/patra-compact-1024.png` is the three-blade one, and the choice between them is a size rule rather than a taste: below about 72px the five blades and the gaps between them each fall under two pixels and the fan closes into a blob, so **every icon at or under 72px is rendered from the compact master**. That rule is why `flutter_launcher_icons` is gone — it rasterises one master to every size and would quietly close the fan on the settings and notification icons, which are the smallest and the ones a person actually squints at. `./tool/gen_app_icons.sh` is the pipeline now: it renders every size `AppIcon.appiconset/Contents.json` names plus the five legacy Android mipmaps, picking the master by size, stripping alpha on the iOS side (App Store Connect rejects an icon that carries any) and giving the Android side the platform's own 22.7% corner, which a pre-API-26 launcher does not add for you. It reads only from `assets/icon/`, never from `.claude/design/`, because that folder is untracked and a fresh clone has to be able to regenerate. It needs ImageMagick, and it does not touch the Android adaptive icon (see below).

The **launch screen the OS paints is the ink and nothing else**, on every path. It used to centre the mark, and that was right when Flutter's first frame was the finished app; it is wrong now that the app opens by *growing* the frond out of an empty screen (see the launch animation below). A mark painted by the window would appear, vanish at Flutter's first frame and then rebuild itself. What has to be continuous from cold start is the ink, not the logo. So `drawable/launch_background.xml` is the ink layer alone, and on Android 12+ (`values-v31`, plus `values-night-v31` because the night qualifier outranks the API one) `windowSplashScreenAnimatedIcon` points at `drawable/splash_none.xml`, a deliberately **transparent** drawable: the system always composites *something* over its splash background and reaches for the launcher icon when the attribute is unset, so a transparent drawable is the only way to make that something be nothing. iOS mirrors it — `LaunchScreen.storyboard` paints the same ink and no longer carries an image view, and the `LaunchImage` imageset it used is deleted rather than left behind showing a logo nothing renders.

The Android **adaptive** icon is deliberately *not* generated: its foreground is `drawable/patra_mark.xml`, a vector, so the launcher icon cannot pixelate at any size a launcher asks for and no generator can rewrite `mipmap-anydpi-v26/ic_launcher.xml` with an inset that double-pads a vector already carrying its own padding. It is a transcription of the handoff's `master/patra-frond.svg` — five capsule blades hinged at one pivot at ±50°, ±26° and 0°, the centre one in the accent, plus the short accent stem below the pivot — and the whole of its sizing lives in the outer `<group>`. The SVG draws the frond full-bleed on its tile, but only the middle 66dp of the 108dp canvas is guaranteed visible, so the mark is scaled to **0.76**, which puts its bounding box's far corner 32.1dp from the centre and just inside that 33dp radius, and the pivot drops to y=71.5 so the box that results is centred on the canvas rather than the pivot being. Blade extremes come off the *cap centres* grown by the radius — a capsule has no corners — which is what `FrondGeometry.boundsOf` computes on the Dart side and what these numbers were derived from. `drawable/patra_mark_mono.xml` is the Android 13+ themed variant: same geometry, one colour, and the fan carried by `fillAlpha` alone, since the system ignores the colour but honours alpha. Its parchment steps are lifted off their brand values (0.58/0.46/0.34/0.26 to 0.80/0.68/0.52/0.42) because a tinted line that faint disappears on some wallpapers — the *ordering* is what carries the fan, not the absolute values. Regenerate the two together. `values/colors.xml` keeps `patra_ink` = `#16141C`, which is also `patraInk` in `theme.dart`.

The app ships a single dark theme (`themeMode: ThemeMode.dark`): the reader canvas is pure black and the whole chrome is built around it.

### The launch animation

The app opens by assembling its own logo. The composition is the handoff's `patra-launch.jsx`, transcribed beat for beat into `lib/src/features/launch/launch_composition.dart` — a `LaunchStage` that is a pure function of authored time, so the timeline can be read and pinned without a widget tree. Five beats over **7.8s**: the accent stem grows out of the ink (1.1s), five blades are **turned like pages** left to right, staggered 0.26s apart (2.3s), the wordmark rises and its accent period pops (1.4s), the frond breathes once and holds at 1.04 (0.8s), then it flies into the header logo slot while the app fades and rises up behind it (2.2s). The numbers in that file are the design's, not ours to round; the eases are its four (`easeOutCubic` arriving, `easeOutBack` springing, `easeInOutCubic` turning a page, `easeInOutQuart` leaving).

A page turn is the interesting one: a blade does **not** grow in place. It starts flat out at -72° — the same place for all five — swings to its own angle in the fan, and is drawn narrower while it travels (`0.18 + 0.82·turn^0.8`), so it foreshortens as it crosses the spine and has its width back by the time it lands. That is what makes five identical sweeps read as pages rather than as a flower opening.

`LaunchAnimation` wraps the **whole app** from `MaterialApp.builder` rather than being a route, because the last beat needs the frond flying *and* the app it is flying into laid out underneath. Keeping the app mounted from the first frame also means its first requests are made and usually answered while the splash plays, so the shelves that fade up are real rather than skeletons. Three consequences worth knowing:

- **The splash is outside every `Material` in the app.** Text there falls back to Flutter's error style, and since the wordmark's own style sets a size and a colour but no `decoration`, the one attribute that leaks through is a yellow double underline. The `Material(type: transparency)` around it is what supplies a real `DefaultTextStyle`; `test/launch_animation_test.dart` pins it, because the symptom is easy to reintroduce and looks like a font problem rather than a missing ancestor.
- **The flight is aimed at measured slots, not at numbers.** A `LaunchSlot` is a registry the screens put themselves into (`LaunchLogoSlot`, `LaunchWordmarkSlot`), looked up by render box rather than by a global key handed down: two screens carry slots now and a route transition can have both mounted for a frame, which a single global key answers with a crash. The frond's *bounds* are flown onto the mark slot's rect — the tile it is painted on is larger than the mark, whose fan leaves the tile's top corners empty, so anything that measures the tile lands the mark high. Where no slot is on screen the frond simply fades where it stands.
- **Everything is measured through the frame that is actually laid out**, which is the one *before* the tick doing the measuring. `_painted` keeps the stage the last build used, and its offsets come back off every rect: a slot lives inside the app and is measured through the app's rise, the splash's own wordmark is not in the app but has a rise of its own from the beat it arrived on. Without those corrections the frond lands 18pt low and the wordmark 14pt low — at 60fps a fraction of a pixel, in a test that pumps one big frame the whole rise.
- **The outro adapts to the screen it lands on, not to a flag.** The composition fades the wordmark out at the handoff, because the home header draws the word at 22pt and a shrinking 40pt word would only cross over a different one. The **login masthead draws it at the splash's own 40pt**, so it offers a `LaunchWordmarkSlot` and the word does not resize at all: it travels, and the splash's lockup simply becomes the screen's. Nothing in the animation asks whether a server is configured — the presence of the slot is the question and the answer, so the outro is right on any screen that offers one and needs no second condition to keep in step. `PatraWordmark` is one definition of the word for that reason: the launch animation *lands* its own on the other two, and tracking that drifted between them would show as a shift at the one moment they are compared directly.

A tap sends the splash home — it seeks to the last beat and lands in 500ms rather than cutting the animation out from under the app — and `MediaQuery.disableAnimations` skips it outright, since someone who asked the OS for less motion is not asking to watch a logo assemble itself for eight seconds. The splash is created once, at app start, and takes itself out of the tree when done: a resume is not a launch.

`lib/src/widgets/patra_frond.dart` is the mark itself, shared by the animation and the header, with the geometry in the SVG's own 88x88 tile space so this file, `res/drawable/patra_mark.xml` and the icon bitmaps can be read against one another. `PatraFrond` is sized by the **mark**, not by the tile. Parchment (`#E9E2D0`) is private to that file and has no token in `theme.dart`: it is brand-mark-only and must never appear in the UI.

The **login masthead carries the same lockup** at the screen's own scale — mark `40 × 24/22` — so the two are the same thing at two sizes rather than two arrangements. Its gap is the one number that does *not* scale: 0.65em against the header's 0.81em, because spacing that reads as one lockup at 22pt opens into a gulf when the same ratio is taken to 40pt. What is being held constant is that the mark and the word read as one thing, not the ratio that achieves it. **The header draws the five-blade fan at 24pt, not the compact one.** The design's own mock puts a three-blade mark at ~16pt there, and that was measured against a mock whose wordmark is 17px; at the app's 22pt wordmark the same lockup gives a mark that reads as a plain arrow, and the animation then spends two seconds unfurling five blades only to crossfade them into three. The size rule is real — five blades *do* close up at 16pt — but in the app the mark is painted rather than rasterised, so the answer is to draw it big enough for the fan to stay open. 24pt is where it does, and it fits an AppBar's 56pt with room. The gap to the wordmark is 0.81em of the wordmark, which is the mock's lockup spacing.


## Architecture

State: Riverpod 3. Routing: go_router. HTTP: dio. Layout: `lib/src/api/` (Kavita client + DTOs), `lib/src/auth/` (servers/session), `lib/src/downloads/` (offline storage), `lib/src/settings/`, `lib/src/widgets/` (shared UI), `lib/src/features/<screen>/` (one folder per screen, each declaring its own providers at the top of its file).

### Kavita API client — deliberately hand-written

Kavita's OpenAPI spec is **vendored** at `docs/openapi/kavita-openapi-<version>.json` and refreshed by hand; its name is its own `info.version`, and `test/openapi_contract_test.dart` asserts that, because the copy that first arrived was named 9.0.2 while describing 0.9.0.0. When adding an endpoint, verify its path, parameters, and DTO shape against that file first — do not code it from memory. `lib/src/api/kavita_client.dart` wraps only the endpoints the app uses, and parsing in `models.dart` is defensive (`?? defaults`) because Kavita omits null fields; keep new types minimal, mapping only the fields actually used.

**We do not generate a client, and the spec is the reason rather than the excuse** (measured against 0.9.0.0). It describes **485 operations and 319 schemas**; this app calls 22 paths and reads 6 of `SeriesDto`'s 38 fields and 10 of `ChapterDto`'s 81, so ~90% of a generated surface would be dead code. Worse, it is Swashbuckle output and **`required` appears on 60 of the 319 schemas — none of them a response type we read**, while `nullable: true` marks reference types only. So every `int`, `bool` and `DateTime` is declared non-nullable *and* not required: `SeriesDto.pagesRead` and 70 non-nullable `date-time` fields included. A generator therefore emits either models that crash on an unread series or models that are nullable everywhere, which is what nine hand-written classes already are. The auth it would wire is wrong too — the only declared security scheme is `x-api-key` in a **header**, which this app does not use, while the Bearer JWT it sends on every call is undeclared and the image `apiKey` is a plain query parameter. There are **zero `operationId`s** across all 485 operations, so every method name would be machine-mangled; `/api/Reader/image` declares no `content` at all, so the app's hottest endpoint would generate as `dynamic`; and all 485 operations declare exactly one response, `200`, so nothing there could feed `ConnectionFailure`. Every expensive fact in this client came from Kavita's C# source, not from this file, and that stays true of what is left to build: `/api/Book/book-page` returns a bare `string`, `book-resources` declares no response, and `bookScrollId` appears nowhere under `/api/Book`.

**What the spec is for instead is an oracle.** `test/openapi_contract_test.dart` catches the one class of mistake nothing else here can: the defensive parsing above swallows a mistyped key into a plausible default, so `json['format']` mistyped makes every EPUB row tappable, `json['type']` makes a comic library say "chapitre", and neither throws nor fails another test. It asserts that each path and method exists, that every key `models.dart` reads exists on its schema and is typed compatibly with the cast made on it, that no key read is flagged `deprecated` (which is what flags `ChapterDto.number` and `VolumeDto.number`, and is why we read `minNumber`), and that each enum value hardcoded here matches the spec's own `x-enum-varnames`. The field list is **derived by reading `models.dart`**, never listed in the test — a list is where a check like this rots. The paths are listed, because several are built by interpolation. Enum values are looked up **by value and never by position**: `SeriesSortField` is one-based (`[1..11]`) where the other three filter enums are zero-based, so counting off the names would assert the wrong one and pass. Three things it deliberately does not assert — `required`/`nullable`, response content types, and status codes — because the spec is not good enough at any of them to be worth believing. A missing spec **fails** the suite rather than skipping it.

Non-obvious API facts already encoded in the client:
- Series listing is `POST /api/Series/all-v2`, whose body is a filter of enum values. Four of them are named in `models.dart` (`SeriesFilterField.libraries` = 19, `FilterComparison.contains` = 5, `FilterCombination.and` = 1, `SeriesSortField.sortName` = 1) and checked against the spec's own names by the oracle above, which is what makes them more than comments. `limitTo: 0` stays a literal: it is a bare int32 with no enum and no default, and "0 means no limit" is server behaviour the spec never states — the one number in that body nothing can vouch for.
- That endpoint silently caps results at the page size, so `allSeriesForLibrary` pages until a short page comes back. A single call would truncate a library at 100 series.
- Two auth mechanisms coexist: JWT Bearer header for regular calls, and the user's `apiKey` as a query param for image URLs. Image widgets get both (`client.imageHeaders` + apiKey in the URL) because they can't always send headers.
- **The app identifies itself** (`client_identity.dart`, `client_device.dart`). Kavita 0.9.1+ registers a `ClientDevice` per user from three headers, stamped on every request — including `imageHeaders` — by an interceptor rather than frozen into `BaseOptions`, because one of them moves. `X-Device-Id` is a random per-install UUID kept in secure storage: Kavita's fallback fingerprint hashes only client type + platform + device type, so without it every Android install collapses into one device. The User-Agent (`Patra/0.1.0 (Android 15; CPH2663; Flutter)`) is where Kavita reads the platform from — its parser greps the raw string for `Android`/`iPhone`/`iPad`/`Mac OS`, never for the word "iOS" — and the only place the device model survives. `X-Kavita-Client` is the one that fills the device card: app version, browser slot, device type, screen, orientation. **Nothing else populates any of those**, the name Kavita generates included, since that name is built from the browser field. Its price is a "Web App" badge: the parser is a regex hard-wired to the web UI's `web-app/<v> (<browser>/<v>; <platform>; <deviceType>; <w>x<h>; <o>)` and stamps every sender as a web app — and Kavita has no client type for a third-party app anyway, so the alternative is not a truer badge, only an emptier card. Send it exactly in that shape or not at all: a value that fails the regex still gets stamped Web App *and* loses everything else, which is why `kavitaClientHeader` is null until there is a screen to report. Screen sizes are logical pixels, as Kavita's own web client reports them. `announceDevice` then renames the entry once per session to "Patra on <the device's own name>" — Android's Settings > About > Device name, iOS's device name, a desktop's computer name — falling back to `Build.MODEL` and then to the platform, since the model is a sales code ("CPH2663") on most phones and the card already names the platform in its own field. It never touches a name the user typed in Kavita. Header values are ASCII-sanitized because a device model is whatever the manufacturer typed. `ClientIdentity.appVersion` is what the server is told, and it is **read off the binary** (`package_info_plus`) rather than compiled in: CI builds a release with `--build-name` taken from the tag, so the version in the User-Agent is the version that shipped, with nothing in the repository to keep in step with it. Resolving it never throws — an unnamed build is a cosmetic loss in a device card, not a reason to fail at startup — and falls back to `0.0.0`, which is deliberately *not* a copy of the current version: a hardcoded one is the string that drifts. In a unit test there is no plugin to answer, so the fallback is what an identity carries unless the fixture sets one. It is also what Settings > About names, so the number a person can read off the screen is the one the server was told and the one the tag built — pinned, with the fallback, by `test/about_version_test.dart`. The **build number is deliberately not shown or carried**: it is CI's run counter, it identifies an upload to the two stores and nothing on the device, and Kavita's client header has no field for one.
- **Kavita sentinel numbers leak through the API** (`ParserConstants`): a volume with `minNumber == -100000` holds the chapters that belong to no volume, `+100000` holds the specials, and a chapter with `minNumber == -100000` is the placeholder for a volume with no chapter breakdown. Same magnitude, **opposite signs — the sign is the whole distinction**, so never compare them on `abs()` (doing so silently files the specials volume under loose-leaf and makes `isSpecials` dead code). `VolumeDto.isLooseLeaf` / `isSpecials` / `ChapterDto.isVolumePlaceholder` exist so these never reach the UI as "-100000". Covered by `test/models_test.dart`.
- `ChapterDto.sortOrder` is Kavita's reading order and is **not** the order of the JSON array; the server sorts every list it builds on it, and so must we.
- Neither pseudo-volume is a place to hide a chapter: one filed under specials *without* `isSpecial` is still listed (Kavita lists it too), or it would have no row at all and could be neither read nor saved. A special sitting inside a numbered volume is filtered out of that volume — the series screen has sections rather than tabs, so it would otherwise appear twice.
- `ChapterDto.format` / `ChapterInfoDto.seriesFormat` are `MangaFormat`. **PDFs read through the normal image reader**: `/api/Reader/image` takes `extractPdf`, and with it Kavita rasterises the PDF into one image per page and serves it like an archive — without it the file is cached untouched and every page 404s. `_readerImageQuery` passes it unconditionally, which is harmless elsewhere (Kavita only reads the flag on its PDF/EPUB branch) and is what its own thumbnail endpoint does. That extraction happens on the *first* request and can take a while, so `PageLoading` (`page_loading.dart`) shows the ordinary spinner and, only after 1.8s and only for a PDF, says what the server is doing — an ordinary page must never flash that text on its way in. **EPUB cannot**: it is reflowable text and `ReadingItemService.Extract` does nothing for it, so there is no image path at all — it needs the `/api/Book` endpoints (`book-info`, `book-page`, `book-resources`, `chapters`, all header-authenticated, no `apiKey` query) and a reader of its own, with `bookScrollId` progress and a different offline shape. Until then `MangaFormat.isImageReadable` keeps EPUB rows non-tappable and unsavable, and the reader refuses them outright (a deep link or a resume does not pass through the series screen).
- `GET /api/Reader/chapter-info` returns `pageDimensions`, which the vertical-scrolling view uses to lay pages out (and so keep the slider in sync) before any image has loaded.
- **A scan can be asked for, but only by an admin.** `POST /api/Library/scan?libraryId=N` is behind Kavita's `AdminPolicy`, which is `RequireRole("Admin")` — and so is every other way in: `scan-multiple`, `scan-all`, and `scan-folder`, which is `[AllowAnonymous]` but looks up the key's account and refuses a non-admin itself. There is no non-admin path, so the button is not drawn for one; a 403 is all it could earn. `libraryId` goes in the **query string**, not a body: the action takes a bare `int`, which is where ASP.NET binds a primitive from. The scan is a background job — it is *requested*, never finished, by the call that returns 200.
- The login response carries `roles`, which is how we know. `UserDto.isAdmin` tests for `"Admin"` (`PolicyConstants.AdminRole`) and fails closed on a missing or malformed list, since guessing yes draws a button that can only fail. It is kept on `ServerEntry` and persisted, because a *resumed* session never logs in again — so it is as old as the last sign-in: an entry saved before this existed, or an account promoted since, reads false until the next one. That costs an admin a button and never offers a non-admin one.

### Reaching the server: cleartext, and saying what went wrong

A self-hosted Kavita is usually a bare IP on the LAN with no certificate, so **cleartext HTTP is permitted on both platforms** — `res/xml/network_security_config.xml` (referenced from the manifest) on Android, `NSAllowsArbitraryLoads` on iOS. Neither could be narrower: Android's config only permits cleartext for hosts written down at build time, which is exactly what a client of a user-named server cannot know, and iOS's narrower `NSAllowsLocalNetworking` has a scope Apple's own sources state inconsistently — and nothing about iOS can be verified on this machine. Permitting cleartext is **not** the same decision as trusting a user-installed CA: Android's trust anchors stay system-only, so a self-signed HTTPS server is still refused (and now says so).

The login form validates the address itself, because `Uri.hasScheme` is not enough: `kavita.local:5000` parses with a **scheme of `kavita.local`**, so it used to reach dio and fail as an unreadable error. The scheme must be `http` or `https` and the host must be non-empty.

**Every provider that reaches the network passes `retry: serverRetry`.** Riverpod 3 retries a failed provider on its own, with exponential backoff and *no ceiling* — right for a blip, wrong for being offline. Offline, the three home providers made 3 requests, then 33 within the minute, and kept going; each attempt drops the provider back to `AsyncLoading`, so the shelf remounts its `Skeleton` (an `AnimationController..repeat()`) and the device redraws at ~89fps forever on a screen showing nothing. That is what "a problem starting the app offline" was. `serverRetry` bounds it to three attempts inside ~600ms; coming back online is then the user's move — pull to refresh, or the retry button — rather than an invisible timer. `kavitaClientProvider` keeps its own `retry: … => null` for a different reason (its `StateError` is control flow, not a failure). Pinned by `test/offline_retry_test.dart`, which counts requests across a simulated minute — a test asserting only "an error is shown" would have passed throughout.

The settings screen's server dot is a **connectivity indicator, and has to actually ask**. It was a `const patraOnline`: green from the moment the screen was drawn, with nothing behind it. `offlineProvider` alone could not fix it either — that flag only moves when a request *fails*, so a device that loses its connection while sitting on a screen keeps whatever the last request said. `serverReachableProvider` probes `GET /api/Health`, which is the right endpoint rather than a convenient GET we already make: it is `[AllowAnonymous]`, so it reports reachability even when the token has gone stale (which is the question a dot asks), and `[SkipDeviceTracking]`, so polling it does not churn the `ClientDevice` entry every other endpoint registers. The call runs through the client, so it feeds `offlineProvider` in passing and the banner agrees with the dot. Being offline **outranks** a probe that once succeeded, and the probe re-runs when the app returns to the foreground — the four tabs live in an `IndexedStack`, so the card is never rebuilt from scratch and nothing else would think to ask again. Nothing re-probes while the tab merely sits open; a failed request anywhere is what corrects it in between. The state is said in **words** as well as colour: an 8pt dot that only changes hue is no indicator to someone who cannot tell those two hues apart, so the card spells out "Hors ligne" and the dot's `Semantics` label merges into the card's own node — one screen-reader stop, announced whole. Covered by `test/server_reachability_test.dart`.

`ConnectionFailure` (`connection_failure.dart`) turns a thrown `DioException` into the few cases that change what someone would *do* next — fix the address, wait, trust a certificate, retype a password — rather than printing a type, a URI and a socket error. Two facts it encodes, both verified rather than assumed: Kavita answers **every** credential-side failure of `/api/Account/login` with a bare **401** (unknown user, wrong password, lockout, disabled account, unconfirmed e-mail, password auth disabled), carrying plain text in the *server account's* locale — so the six cannot be told apart, and one message covers them, worded to stay true of a lockout. And a 200 carrying someone else's HTML fails in the **decode**, which dio reports as `unknown` with **no response attached**, so the wrapped `FormatException`/`TypeError` is the only thing left to read — that is the "wrong address, something else is listening" case.

Two more things the `unknown` branch has to catch, because dio's type is not the whole story. **A self-signed certificate never produces `DioExceptionType.badCertificate`**: dio raises that only from an adapter given a `validateCertificate` callback, which this app does not set. What a self-hosted HTTPS server really throws is a `HandshakeException` — a `TlsException`, so neither the `SocketException` nor the `HttpException` dio's IO adapter catches — and it arrives as `unknown`. And **403 is not a wrong address**: the same classifier reports a failed scan from the Library tab, where Kavita's `AdminPolicy` answers 403 to a stale `isAdmin`, so it has a case of its own rather than falling into the catch-all. For the same reason no message is worded for the login screen — the unclassified fallback is `unexpectedError`, not "Could not sign in" — and `test/connection_failure_test.dart` pins that by throwing the *real* exceptions rather than synthesising a `DioException` of a chosen type, which is what let the certificate case look handled when it was not. `test/connection_failure_test.dart` drives each case through `KavitaClient.login` with a realistic content type, which is load-bearing: a mock that labels a plain-text 401 as JSON makes dio fail in the decode instead, and tests a server that does not exist.

### The library type names everything

`LibraryType` (Manga 0 · Comic 1 · Book 2 · Image 3 · LightNovel 4 · ComicVine 5) decides what a series is made of and what its parts are called — Kavita words its whole series page from it, and `lib/src/entity_naming.dart` mirrors that `EntityNamingService`: a comic has **issues** where a manga has **chapters**, and a book library calls a volume a **book** at both levels. Never hardcode "chapter" or "volume" in a screen; go through `LibraryTypeNaming`, and get the type from `libraryTypeProvider(libraryId)` (it falls back to manga while the library list is in flight, so no screen waits on it).

The **French glossary is fixed**: specials = hors-série, volume = tome, chapter = chapitre, issue = numéro (avec le croisillon, `Numéro #12` et `Reprendre — #12`, comme Kavita), storyline = arc narratif. `test/entity_naming_test.dart` pins it in both languages.

The hero's button asks whether the *series* is under way, not the chapter it lands on: finishing a volume leaves the next one untouched, so reading progress off the target alone said "Commencer la lecture" to someone halfway through a series. It is Kavita's own web client that asks the question that way, of the series rather than the chapter; `hasReadingProgress` is that client's concept and appears nowhere in the API, so this mirrors a rule rather than reading a field.

It names only what is **numbered** — `Reprendre — tome 1`, `— ch. 3`, `— #12`, `— livre 2`. A title never reaches it: free text stretches the button across the hero, and a Book library would do it every time, since its files often carry a title and no number at all. Where there is no number (a special, or a lone chapter carrying the sentinel) the button says just `Reprendre`; the title is already on the row it opens.

Naming one chapter follows Kavita's own rules: a special is known by its title alone and is never numbered; a title is *appended* to the number (`Chapitre 12 - Le duel`), not swapped for it, and only when it says something the number does not.

Volumes and volumeless chapters read as one story — Kavita calls that the **storyline** and shows it only for Manga and Image libraries (an issue run is not a storyline; a book library has no chapter level). Our series screen has sections, not tabs, so the storyline is the header over the volumes *and* the loose chapters when a series has both; with only volumes it stays "Tomes". Specials always close the screen. Covered by `test/series_sections_test.dart`.

We deliberately do **not** call `GET /api/Series/series-detail`, which returns these buckets ready-made: it is documented as internal ("may change without hesitation") and its labels come pre-formatted in the *server account's* locale, which would fight our own fr/en. We take `/api/Series/volumes` and apply its rules ourselves.

### Auth: several servers, one active session

`ServerEntry` is a remembered server (`baseUrl`, `username`, and its tokens — **never a password**); an empty `token` means "remembered but signed out". `AuthState` is the list plus `activeUrl`, and `AuthState.active` is non-null only when the active entry still has tokens. `main()` loads it from `flutter_secure_storage` **before** `runApp` and injects it via `initialAuthStateProvider`; `SessionStorage.load()` still migrates the old single-server key layout.

Mutate auth through `authProvider.notifier` (`login`, `resume`, `signOut`, `switchServer`, `forget`, `updateTokens`); read the current session through `sessionProvider`. `signOut` keeps the entry but drops its tokens (a password is needed again), `switchServer` keeps the tokens so returning is one tap. Covered by `test/auth_test.dart`.

`kavitaClientProvider` watches only the session's *identity* (`baseUrl`, `apiKey`), not its tokens: the client patches its own tokens on refresh, so rebuilding it there would invalidate every data provider mid-read. It also keeps the previous client alive across a logout, because screens can rebuild once more while the router redirects. The client refreshes an expired JWT on a 401 and retries the request; a failure of the *retried* request is not a session failure — keep those two error domains separate (`test/kavita_client_test.dart`).

### Navigation

Four tabs (Home / Library / Downloads / Settings) via `StatefulShellRoute.indexedStack`; `/series/:id` and `/reader/:chapterId` are declared **outside** the shell so they are full-screen. Use `context.push()` to drill down — it stacks the screen, giving the AppBar back arrow and correct Android back-button behavior — and `context.go()` only for switching branch or for login/logout redirects. Using `go` for drill-down makes the system back button exit the app.

The bottom bar **measures its labels before showing them** (`_PatraShell._labelsFit`): French labels are much longer than English ones and a large system font makes any of them overflow the bar, so when they do not fit in their share of the width the bar falls back to icons plus tooltips. Keep `PatraText.navLabel` as the single definition of that style — the theme and the measurement must agree, or the check is meaningless.

Reading changes progress on the server, so a screen that pushed the reader invalidates its own provider when the push returns.

A pane **squeezes** the row rather than sliding it (`_SqueezedByPane`). `Slidable` uncovers a pane by translating its whole child, which carries the cover and the title off the leading edge — the swipe hides the very thing it is about to act on, and in a centred column the row slides out of the column and over the margin. The wrapper works from inside that translation: it undoes it and hands the pane's edge the same width as padding, so the row keeps its origin and every part of itself and is merely narrower while the pane is open. Only the pane's own width is squeezed out; a drag that pulls further keeps the library's slide, which is where the over-drag gets its rubber band. Pinned by `test/series_sections_test.dart` — without it the title's left edge goes from 78pt to -16pt.

A chapter row swipes both ways, and the two edges never mean the same kind of thing: **leading = progress** (mark read / unread, in `patraAccent`), **trailing = destruction** (remove the saved copy, in `patraDanger`). Marking goes through `markChapterRead`, which posts to `mark-multiple-read` / `mark-multiple-unread` — there is no single-chapter *unread* endpoint, and that pair takes one body shape for both directions. It needs the server, so the leading pane is gone offline; it does *not* need a readable format, since a file read elsewhere is exactly what one marks by hand. The stored copy's progress is mirrored alongside, or the Downloads tab would disagree with no server to ask.

The write is **optimistic**: `readOverridesProvider` holds the new progress and `seriesVolumesProvider` lays it over the fetch, so the row redraws on the gesture rather than on the round trip. Re-fetching instead would be worse than slow — the screen pattern-matches `AsyncData`, so any `invalidate` of `volumesProvider` drops the whole list to its skeleton. A refused write clears the override and the row goes back. The map is autoDispose and dies with the screen, so the next visit is the server's word again; `_open` clears the chapter's override too, since reading is about to define progress properly. The hero's cover ring is series-wide and cannot be guessed from one chapter, so it re-fetches `seriesProvider` — flash-free, because the hero reads `.value`, which survives a refresh.

### Downloads and offline

`DownloadsService` stores pages under `<documents>/downloads/<chapterId>/`, one extension-less file per page, and writes `meta.json` **last** — a chapter directory without one is a partial download and gets deleted on the next `scan()`. Keep that invariant. `DownloadsNotifier` owns per-chapter `CancelToken`s; a cancelled or failed download leaves nothing behind. A save that waited on the first `scan()` must **re-read `state.value` after the await** rather than keep what the scan returned: a second pill tapped during that same wait resumes first and writes its own entry, and building the next state on the stale snapshot drops it — leaving a download running that nothing on screen tracks any more, and a pill that offers to start it a second time over the files already being written. Covered by `test/downloads_service_test.dart` (pass `DownloadsService(root:)` a temp dir).

Two stores must not be confused. **Saved chapters** live in the documents directory, are chosen by the user and are never evicted; their total is what the Downloads tab reports. The **image cache** is `cached_network_image`'s own store in the system cache directory, holding covers and pages merely browsed online — it grows on its own (it outgrew the downloads three to one on a real device) and the OS may reclaim it. `ImageCacheStore` exposes its size and clears it from Settings; clearing it must never touch the documents directory.

The image cache is **capped**: `ImageCacheStore.trim(maxBytes)` deletes files oldest-first until the cache fits the budget picked in Settings (`ImageCacheLimit`, default 512 MB, persisted like the reading direction). `flutter_cache_manager` only caps by *number* of objects, which says nothing about bytes, so the sweep is ours and works on the files directly — safe because the manager re-checks that a file exists before serving its database row and drops the row when it does not. "Oldest" is by write time; `atime` is unreliable on Android. `trim` runs at startup from `main()`, whenever the limit changes, and — throttled through `trimIfDue` — on every reader page turn, which is where the cache actually grows. Covered by `test/image_cache_store_test.dart` (pass `ImageCacheStore(root:)` a temp dir).

Progress is mirrored into each saved chapter's `meta.json` (`recordProgress`), because the Downloads tab has to show it with no server; the series screen resyncs it from the server, which stays the authority. A chapter opened from the Downloads tab must be opened at its stored page — opening at 0 posts that back and wipes the reader's place.

`offlineProvider` flips to true when a request fails to *reach* the server (dio connection/timeout errors) and back on the next success. Offline, unsaved chapters are dimmed and non-tappable, and the reader falls back to the stored `SavedChapter` metadata so a saved chapter reads with no server at all.

Offline is shown as a **status in the app bar** — `OfflineIndicator`, a struck-through cloud in `patraDanger` on the trailing edge — and not as a banner over the content, which is what it used to be. A banner is a paragraph: it pushed the shelves down, said the same sentence on three screens at once, and was as loud on the twentieth glance as on the first. The sentence survives as the icon's `tooltip` (which is also its semantics label) and as what a tap puts in a SnackBar, because a struck-through cloud says nothing to a screen reader and little to someone meeting it for the first time. Covered by `test/offline_indicator_test.dart` — whose harness has to build the client with `overrideWith`, not `overrideWithValue`: what turns a failed request into the offline state is `onReachabilityChanged`, wired by the real provider, so a ready-made client leaves the indicator dead however unreachable the server is.

### Reader

One setting decides everything: `ReadingDirection` is left-to-right, right-to-left, or **vertical scrolling** — that third one is a *direction*, not a separate mode, and there is a single control for it. The word "webtoon" is Kavita's, after the genre the reader was built for, and it is gone from this app in code as well as on screen: what varies is the motion, not what is being read. It is `verticalScroll` and not merely `vertical` because Kavita has two vertical readers — `ReaderMode.UpDown` pages vertically, `Webtoon` scrolls — and only the second is ours; **on screen the row is the single word "Vertical"** in both languages, which is unambiguous while it is the only vertical direction in the picker. Never write "LTR"/"RTL" in UI copy; use the full localized phrases. The enum name is also the persisted preference (`ReadingSettingsStore` writes `direction.name`, and an unrecognised string falls back to left-to-right *silently*), so `_legacyNames` still reads the stored `webtoon` — renaming a value of this enum without that is how a setting resets itself on someone's device and says nothing.

- **The system's chrome comes and goes with ours.** The chapter opens with the status bar and the home indicator gone (`SystemUiMode.immersiveSticky`) and gets them back — `edgeToEdge`, what every other screen runs under — when the tap in the middle brings the reader's own bars up, and again on the way out. So the clock is never over the page but is always one tap away. Every path that moves `_showChrome` goes through `_showChromeAndBars`, or the two drift apart. iOS hides both for any fullscreen mode; Android honours it below API 36 and ignores it above (we target 36), and an iPad in Split View keeps its status bar whatever the app asks. Covered by `test/reader_test.dart`.
- **The top bar carries one cog, not a control per setting** (`widgets/reader_settings_sheet.dart`). It was a direction pill, which was right while the direction was the only thing there was to say. Two things changed that. Magnifying **cannot be drawn as an icon** the way a direction can — a page glyph with a flow arrow really does say "left to right", and nothing says "a one-finger drag magnifies instead of turning the page", which is the same reason the handoff makes the save pill "always worded, never icon-only". And a second pill would eat the chapter title, which is an `Expanded` that already ellipsizes inside a 56pt bar. The cog costs **no extra tap**: the pill was a menu opener rather than a toggle, so changing direction was always two taps and still is. What it loses is the direction glyph visible in the bar — a small loss, because the chrome is hidden while reading, so that glance is only ever had by someone who has just tapped for a control anyway. It is a **sheet and not a `PopupMenuButton`**, because a `PopupMenuItem` pops its route when tapped and a switch inside one would dismiss the menu as it was flipped; the sheet is also the shape Settings already uses for the same choice, and `ReadingDirectionRows` is shared between the two so the wording cannot drift. The two rows deliberately differ: **picking a direction closes the sheet and overrides the direction for this chapter only; the magnify switch leaves the sheet open and writes the preference straight through.** A switch that closed the surface it lives on could never be turned back off without reopening it, and made per-chapter it would forget itself every time a chapter was opened — a direction belongs to the book, this belongs to the hand. Covered by `test/reader_test.dart`.
- **A one-finger drag can magnify the page** — `magnify_gesture.dart`, off by default, `magnifyProvider` in `reading_settings.dart`, and a switch in both Settings and the reader's own sheet. Pinching needs a second hand, which a person reading on a phone does not have. Press anywhere and the page is carried along with the finger, so pulling **down** brings what was **above** into view and pulling **right** brings the **left**; the *length* of the drag sets the magnification (**2.5x** over **400pt**), and letting go returns the page. The four directions are **one rule, not four cases** — the artwork under the finger is carried towards it — and there must never be an `if (dy > 0)` in that file. Where the drag asks to go past an edge the page stops there and the artwork slides out from under the finger: **the border is held and the grip gives way**, which at these settings is the *normal* case rather than a corner, since there is little slack until near full travel. So what is pinned is where the *view* lands (it walks towards the part asked for, and keeps walking that way for the whole drag), not that a point stays under the fingertip. Three other answers were built and rejected in a prototype kept on the `prototype/reader-loupe-gesture` branch; `docs/adr/0001-reader-magnify-gesture.md` says what each felt like and why 2.5x/400pt. The travel distance is **absolute, not a fraction of the screen** — the ruler is a thumb, and a thumb does not grow with the display. Two consequences: the swipe that turns a page **is gone while the mode is on** (two recognisers cannot share one drag, so pages turn by tapping the sides, and the settings row says so), and **vertical scrolling is excluded**, since there the drag is the only way through the chapter. The reference point comes from the pointer-down and never from `onPanStart`, which reports where the pan was *recognised* — already ~18pt into the drag, in the direction of travel. What the gesture holds against the screen edges is the **artwork**, not the canvas: `drawnContent` computes where the scan is actually drawn (a contain fit, or the box around both halves of a spread), because holding the letterbox bars there would let the drag pan over black. Covered by `test/magnify_gesture_test.dart`, which sweeps every anchor and finger position for a border leak, and by the reader's own tests for what only shows in the tree.
- Wiring that up uncovered a bug worth remembering: **`_PagedView._reported` must be set in `initState`, not by a `late` initialiser.** A `late` field runs its initialiser at the first *read*, and the first read is the comparison in `didUpdateWidget` — where `widget.page` is already the new page, so it initialised to the value it was about to be tested against and the guard skipped the jump. The first tap on a side zone moved the reader's page number and left the pager where it was; the second jumped two. It went unnoticed because a swipe takes the other path entirely, through `onPageChanged`, and swiping was how everyone got through a chapter.
- Paged: tap zones are 30/40/30 (sides page, centre toggles chrome); right-to-left mirrors `reverse`, the tap meanings, the thumbnail strip and the slider together (via `Directionality`) while page numerals stay left-to-right.
- Landscape (paged only) becomes a two-page spread, first page of the pair leading per direction. **Which pages share a screen is `SpreadLayout`'s call, not `page ~/ 2`**: a scan that is itself a double page (Kavita's `isWide`, or dimensions plainly wider than tall — either is enough, since the server only flags the files it measured that way) takes a screen of its own, because pairing it would shrink both pages to a quarter of the screen and run the spine down the middle of a drawing meant to be seen whole. A wide page also shifts the parity of everything after it, so a step is a *screen*, not a fixed number of pages — stepping back off a wide page lands on the first page of the pair before it — and the counter's span comes from the page being arrived at. With no dimensions from the server nothing is wide and the pairing is exactly what it always was. The two pages of a pair are **pushed together against the spine** (`Image.alignment`, right for the leading page and left for the trailing one): each is contained in its own half of the screen, and centred there they would be joined by a gutter that widens with the screen and with how narrow the scans are — the pair has to meet on the centre line and spend the leftover room on the outer edges. Covered by `test/spread_layout_test.dart` and, end to end through the counter and the alignments, `test/reader_test.dart`.
- The thumbnail strip (`thumb_strip.dart`) is an accordion keyed to the page being read — current widest, its two neighbours halfway, the rest at the base size — so its item extents are not uniform: `_leadingEdge` corrects for the three swollen pages, and the scroll target measures that geometry instead of `maxScrollExtent`. **The strip states its own extent** (`_StripDelegate.estimateMaxScrollOffset`): a lazy list otherwise averages the children it has built and applies that to the rest, and with three items half again as wide as the others the guess is short by tens of points — the scroll to the last page then stops short of it and leaves the bulge behind the handle. The stated extent is also steady while the accordion animates, which the guess is not; the gap after each thumbnail rides inside its item, since one child per page is what lets the delegate speak for the whole strip. The strip does **not** centre the current page: the bulge travels across it on the same linear law as the slider handle travels across its track, because the two sit one above the other and a centred bulge points somewhere else than the handle on every page but the middle one. The law lands exactly on offset 0 at the first page and on the end of the scroll at the last. **The slider's padding comes from the strip** (`ThumbStrip.sliderPadding`), not from a number of its own: the bulge's end centres are `hPadding + half a swollen thumbnail` in, Material insets a `Slider`'s handle 26pt inside its own box (measured against this theme), and the difference is what keeps the two markers agreeing at the ends whenever the thumbnails change size. `test/reader_test.dart` pins it by making the slider paint through a probe shape and comparing where the handle actually lands. A chapter short enough to fit on screen cannot scroll, so the thumbnails spread instead — even centres, uneven widths, the gaps carrying the difference — and the padding is computed so the content is exactly the viewport. Spreading stops below `_minStep`, where the current thumbnail and its neighbour would touch; between that and a full strip the natural packing already lines up closely enough. **Sizes: the handoff's 34×48 thumbnail is a stamp on a real device.** This strip is not read, it is *aimed at* — a page you cannot recognise is a page you cannot scrub to — so it is drawn at twice the handoff on a phone (92×128 current, 68×96 base) and `_tabletScale` again on a tablet, while the strip's own margins stay put and the extra height goes into the pictures. Every length goes through `_scale` together, so the accordion's law is untouched and only the numbers change; `_scale` is read in `didChangeDependencies`, never in the geometry getters, which run inside scroll callbacks.
- Thumbnails do **not** load when they are built. `ThumbLoadQueue` holds them for 180 ms, then fetches at most two at a time, nearest the current page first (current, previous, next, outwards), and only pages on screen — a flick through a 200-page chapter used to fire a request per thumbnail mounted. A failed thumbnail is marked done, never retried. The precache and the widget that shows a thumbnail must ask for the **same** decode width (`_thumbCacheWidth`, which is `ThumbStrip.thumbWidth` in device pixels, capped at what Kavita's thumbnail endpoint serves): `ResizeImage` puts it in the cache key, so a mismatch quietly precaches one image and displays another, and a decode a third of the drawn size is the blur the strip exists to avoid. Covered by `test/thumb_strip_test.dart`.
- The vertical-scrolling view must be **placed** before it reports anything. A scroll view has no `initialPage`, so it opens at offset 0 while the reader is on page 40; the first flick would report page 0 and post it back, wiping the place the chapter was opened at. `_VerticalScrollViewState` jumps after the first layout (offsets need the width) and `_placed` gags `_onScroll` until then. Covered by `test/reader_test.dart`.
- The initial save is deferred a frame: it is reached from `build`, and it mirrors progress into the stored copy — writing to a provider while the tree is building is what Riverpod refuses outright.
- Progress posts are serialized through a queue so a slow save cannot regress a later page, and the **last page reports `pages`, not `pages - 1`** — Kavita only marks a chapter read when `pagesRead >= pages`. The initial page is saved on open, since `onPageChanged` never fires for it.

### Localization

The app is localized (English = template/fallback, French). Never hardcode user-facing strings: add the key to both `lib/l10n/app_en.arb` and `lib/l10n/app_fr.arb`, run `flutter gen-l10n` (also runs automatically on build/test), and use `AppLocalizations.of(context)` (import `lib/l10n/generated/app_localizations.dart`; the getter is non-nullable, configured in `l10n.yaml`). Generated files are committed. Widget tests run under the `en` locale — note `SectionLabel` uppercases its text, so tests match `'CONTINUE'`, not `'Continue'`.

**The language can be forced from Settings**, and "follow the device" is a value rather than the absence of one: `localeProvider` holds a `Locale?` and null is exactly what `MaterialApp`'s `locale` takes to mean "resolve against the system", so the default option needs no separate representation. It is restored before `runApp` like every other preference (`LocaleSettingsStore`, `initialLocaleProvider`), and a stored code the build no longer ships resolves back to the device rather than to a language with no translations behind it. The picker is built from `supportedLocales`, so a new translation appears in it by existing — the one thing a new locale needs by hand is a line in `languageEndonym`, because **a language is listed under its own name and never translated**: someone who has landed in a language they cannot read has to be able to find their way out of it. `intl` ships no endonyms, so there is nothing to derive it from; `test/locale_settings_test.dart` fails if a shipped locale has no name of its own.

A test that *writes* a preference needs `mockSecureStorage()` from `test_support.dart`. On a test binding `flutter_secure_storage` has no platform behind it and the Linux implementation reaches for libsecret, which never answers — so a `write` **hangs** the test rather than failing it, which reads as a stuck suite rather than as a missing mock.
