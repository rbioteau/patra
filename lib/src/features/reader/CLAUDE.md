# The reader

*Loaded when work touches `lib/src/features/reader/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

## Reader

One setting decides everything: `ReadingDirection` is left-to-right, right-to-left, or **vertical scrolling** — that third one is a *direction*, not a separate mode, and there is a single control for it. The word "webtoon" is Kavita's, after the genre the reader was built for, and it is gone from this app in code as well as on screen: what varies is the motion, not what is being read. It is `verticalScroll` and not merely `vertical` because Kavita has two vertical readers — `ReaderMode.UpDown` pages vertically, `Webtoon` scrolls — and only the second is ours; **on screen the row is the single word "Vertical"** in both languages, which is unambiguous while it is the only vertical direction in the picker. Never write "LTR"/"RTL" in UI copy; use the full localized phrases. The enum name is also the persisted preference (`ReadingSettingsStore` writes `direction.name`, and an unrecognised string falls back to left-to-right *silently*), so `_legacyNames` still reads the stored `webtoon` — renaming a value of this enum without that is how a setting resets itself on someone's device and says nothing.

- **A seek the reader asked for is not reported back to it.** `_PagedView` follows a seek in `didUpdateWidget` with `jumpToPage`, which dispatches its scroll notification **synchronously** — and `PageView` turns that into `onPageChanged`, from inside the build that delivered the seek. Landscape is where it bites: the view reports the *first* page of the spread it landed on, so a seek to an **odd** page reports a page the reader did not ask for, the reader took that for a real page turn, and `setState` ran in the middle of a build. What follows is not obviously that: the error widget replaces the Scaffold's body, so the same frame dies on "Each child must be laid out exactly once" with a `RenderErrorBox` in `_ScaffoldSlot.body`, then hit tests fail on boxes that were never laid out. `_seeking` guards the jump, and `test/reader_test.dart` taps the second page of a spread. Any programmatic move of a `PageController` needs the same guard.
- **The reader reads its orientation off the `MediaQuery`, and must never wrap itself in a `LayoutBuilder`.** `OrientationBuilder` *is* one — it derives portrait or landscape from its own constraints — and this screen asked it a question it does not need layout to answer: the body fills the window, so the window's orientation is the same one. What it bought instead was a `LayoutBuilder` around the whole reader, and a `LayoutBuilder` runs the builds of everything beneath it **during layout**: the pages, the tap zones, the chrome, the scrubber, every image frame arriving and every `setState` the Slider makes. That is a rebuild-inside-a-layout on every one of them, and this screen died on it — `debugNeedsLayout` and `_debugRelayoutBoundaryAlreadyMarkedNeedsLayout`, both thrown from `scheduleLayoutCallback`, then "Each child must be laid out exactly once" with two `_RenderLayoutBuilder`s in `_ScaffoldSlot.body` and finally a `RenderErrorBox` in the slot. The duplicated child was that `OrientationBuilder`'s own render object: `Scaffold` wraps a body in a `LayoutBuilder` of its own only when `extendBody` or `extendBodyBehindAppBar` is set, and this one sets neither, so the body slot's `LayoutBuilder` was ours — re-inflated under `Scaffold`'s `GlobalKey`'d body while the old one was still in the slot. Read layout information here only where it is genuinely needed (the strip's width), and never around a subtree that rebuilds on animation, images and gestures.
- **The system's chrome comes and goes with ours.** The chapter opens with the status bar and the home indicator gone (`SystemUiMode.immersiveSticky`) and gets them back — `edgeToEdge`, what every other screen runs under — when the tap in the middle brings the reader's own bars up, and again on the way out. So the clock is never over the page but is always one tap away. Every path that moves `_showChrome` goes through `_showChromeAndBars`, or the two drift apart. iOS hides both for any fullscreen mode; Android honours it below API 36 and ignores it above (we target 36), and an iPad in Split View keeps its status bar whatever the app asks. Covered by `test/reader_test.dart`.
- **The top bar carries one cog, not a control per setting** (`widgets/reader_settings_sheet.dart`). It was a direction pill, which was right while the direction was the only thing there was to say. Two things changed that. Magnifying **cannot be drawn as an icon** the way a direction can — a page glyph with a flow arrow really does say "left to right", and nothing says "a one-finger drag magnifies instead of turning the page", which is the same reason the handoff makes the save pill "always worded, never icon-only". And a second pill would eat the chapter title, which is an `Expanded` that already ellipsizes inside a 56pt bar. The cog costs **no extra tap**: the pill was a menu opener rather than a toggle, so changing direction was always two taps and still is. What it loses is the direction glyph visible in the bar — a small loss, because the chrome is hidden while reading, so that glance is only ever had by someone who has just tapped for a control anyway. It is a **sheet and not a `PopupMenuButton`**, because a `PopupMenuItem` pops its route when tapped and a switch inside one would dismiss the menu as it was flipped; the sheet is also the shape Settings already uses for the same choice, and `ReadingDirectionRows` is shared between the two so the wording cannot drift. The two rows deliberately differ: **picking a direction closes the sheet and overrides the direction for this chapter only; the magnify switch leaves the sheet open and writes the preference straight through.** Reading vertically the gesture is inert, and the row **says so** in place of its usual explanation rather than sitting there switched on and doing nothing; it stays switchable, because the preference is global and the next chapter may be paged. A switch that closed the surface it lives on could never be turned back off without reopening it, and made per-chapter it would forget itself every time a chapter was opened — a direction belongs to the book, this belongs to the hand. Covered by `test/reader_test.dart`.
- **A one-finger drag can magnify the page** — `magnify_gesture.dart`, off by default, `magnifyProvider` in `profile_preferences.dart` (it follows the person, like the direction), and a switch in both Settings and the reader's own sheet. Pinching needs a second hand, which a person reading on a phone does not have. Press anywhere and the page is carried along with the finger, so pulling **down** brings what was **above** into view and pulling **right** brings the **left**; the *length* of the drag sets the magnification (**2.5x** over **400pt**), and letting go returns the page. The four directions are **one rule, not four cases** — the artwork under the finger is carried towards it — and there must never be an `if (dy > 0)` in that file. Where the drag asks to go past an edge the page stops there and the artwork slides out from under the finger: **the border is held and the grip gives way**, which at these settings is the *normal* case rather than a corner, since there is little slack until near full travel. So what is pinned is where the *view* lands (it walks towards the part asked for, and keeps walking that way for the whole drag), not that a point stays under the fingertip. **That is only true because the reference point is clamped to within `travel / (maxScale - 1)` of the middle of the screen** (`_band`, ~267pt at the shipped settings, so it moves only a press within ~43pt of an edge, and carries the finger with it so the drag length is untouched). Outside that band the page grows faster than the glue can carry it and pulling *down* walked the view *down* the page — by ~1.6%, wrong way. `H` and `V` cancel out of the derivation, so one number covers both axes and every page shape. The test that thought it covered this swept drag length at a single centred anchor and could not see it; **the anchor is the axis that has to be exhaustive**, as it already was for the border. Three other answers were built and rejected in a prototype kept on the `prototype/reader-loupe-gesture` branch; `docs/adr/0001-reader-magnify-gesture.md` says what each felt like and why 2.5x/400pt. The travel distance is **absolute, not a fraction of the screen** — the ruler is a thumb, and a thumb does not grow with the display. Two consequences: the swipe that turns a page **is gone while the mode is on** (two recognisers cannot share one drag, so pages turn by tapping the sides, and the settings row says so), and **vertical scrolling is excluded**, since there the drag is the only way through the chapter. The reference point comes from the pointer-down and never from `onPanStart`, which reports where the pan was *recognised* — already ~18pt into the drag, in the direction of travel. What the gesture holds against the screen edges is the **artwork**, not the canvas: `drawnContent` computes where the scan is actually drawn (a contain fit, or the box around both halves of a spread), because holding the letterbox bars there would let the drag pan over black. Covered by `test/magnify_gesture_test.dart`, which sweeps every anchor and finger position for a border leak, and by the reader's own tests for what only shows in the tree.
- Wiring that up uncovered a bug worth remembering: **`_PagedView._reported` must be set in `initState`, not by a `late` initialiser.** A `late` field runs its initialiser at the first *read*, and the first read is the comparison in `didUpdateWidget` — where `widget.page` is already the new page, so it initialised to the value it was about to be tested against and the guard skipped the jump. The first tap on a side zone moved the reader's page number and left the pager where it was; the second jumped two. It went unnoticed because a swipe takes the other path entirely, through `onPageChanged`, and swiping was how everyone got through a chapter.
- Paged: tap zones are 30/40/30 (sides page, centre toggles chrome); right-to-left mirrors `reverse`, the tap meanings, the thumbnail strip and the slider together (via `Directionality`) while page numerals stay left-to-right.
- Landscape (paged only) becomes a two-page spread, first page of the pair leading per direction. **Which pages share a screen is `SpreadLayout`'s call, not `page ~/ 2`**: a scan that is itself a double page (Kavita's `isWide`, or dimensions plainly wider than tall — either is enough, since the server only flags the files it measured that way) takes a screen of its own, because pairing it would shrink both pages to a quarter of the screen and run the spine down the middle of a drawing meant to be seen whole. A wide page also shifts the parity of everything after it, so a step is a *screen*, not a fixed number of pages — stepping back off a wide page lands on the first page of the pair before it — and the counter's span comes from the page being arrived at. With no dimensions from the server nothing is wide and the pairing is exactly what it always was. The two pages of a pair are **pushed together against the spine** (`Image.alignment`, right for the leading page and left for the trailing one): each is contained in its own half of the screen, and centred there they would be joined by a gutter that widens with the screen and with how narrow the scans are — the pair has to meet on the centre line and spend the leftover room on the outer edges. Covered by `test/spread_layout_test.dart` and, end to end through the counter and the alignments, `test/reader_test.dart`.
- The thumbnail strip (`thumb_strip.dart`) is an accordion keyed to the page being read — current widest, its two neighbours halfway, the rest at the base size — so its item extents are not uniform: `_leadingEdge` corrects for the three swollen pages, and the scroll target measures that geometry instead of `maxScrollExtent`. **The strip states its own extent** (`_StripDelegate.estimateMaxScrollOffset`): a lazy list otherwise averages the children it has built and applies that to the rest, and with the accordion's three items wider than the rest the guess is short by tens of points — the scroll to the last page then stops short of it and leaves the bulge behind the handle. The stated extent is also steady while the accordion animates, which the guess is not; the gap after each thumbnail rides inside its item, since one child per page is what lets the delegate speak for the whole strip. The strip does **not** centre the current page: the bulge travels across it on the same linear law as the slider handle travels across its track, because the two sit one above the other and a centred bulge points somewhere else than the handle on every page but the middle one. The law lands exactly on offset 0 at the first page and on the end of the scroll at the last. **The slider's padding comes from the strip** (`ThumbStrip.sliderPadding`), not from a number of its own: the bulge's end centres are `hPadding + half a swollen thumbnail` in, Material insets a `Slider`'s handle 26pt inside its own box (measured against this theme), and the difference is what keeps the two markers agreeing at the ends whenever the thumbnails change size. `test/reader_test.dart` pins it by making the slider paint through a probe shape and comparing where the handle actually lands. A chapter short enough to fit on screen cannot scroll, so the thumbnails spread instead — even centres, uneven widths, the gaps carrying the difference — and the padding is computed so the content is exactly the viewport. Spreading stops below `_minStep`, where the current thumbnail and its neighbour would touch; between that and a full strip the natural packing already lines up closely enough. **Sizes are shares of the screen's shortest side, never points.** The shortest side, so a phone gets the same thumbnail in either orientation — a page is the same thing to recognise whichever way the device is held — and a share, because a size only means something against the screen it is drawn on: what the swollen thumbnail's width really costs is the slider's track (which is the screen less that width, see `sliderPadding`) and the pages that fit either side of it. The handoff's 34×48 is a stamp on a real device — this strip is not read, it is *aimed at* — so the base is twice that (`_baseShare` 0.174, 68pt on the 390pt phone the handoff was drawn for) and **the swollen one is a third of the screen** (`_currentShare` 0.33, 129pt), with its neighbours halfway between by arithmetic rather than by a third number. A third is as wide as it can be drawn before the slider stops reading as a slider: doubling it to 184pt put the track at 47% of the screen — a short bar floating between two wide margins — where a third leaves 61% and about four pages on screen. Only widths are shares; heights follow `_pageAspect` (the handoff's 34×48), so no thumbnail is ever drawn out of shape. Past ~107pt on a 3x phone the picture is upscaled — Kavita serves a 320px thumbnail and there is no more detail to ask for — which is accepted, because a large soft page is easier to pick out at arm's length than a small sharp one. **A tablet takes a smaller share of a wider screen** (`_tabletShareFactor` 0.64). A third of an iPad's 820pt short side would be a 270pt thumbnail with no more pages beside it than a phone shows, which is the mistake the rest of this app avoids by taking another column rather than drawing a bigger card; two thirds of the share puts it at 173pt — one step up from the phone, the same step the strip used to take at 1.35 — and spends the width it did not take on pages. **The one limit in points is a gesture, not a share**: the reader's middle third toggles the chrome, so the chrome has to stop short of the middle of the screen — reach past it and the tap that would dismiss it lands on the scrubber and seeks to whatever page is under the finger, which is worse than nothing happening. `_heightBudget` is therefore half the screen less what the chrome takes around the strip, in points because a slider and a line of type are the same size on every screen. It leaves every phone and tablet in portrait the shares whole, and catches a phone on its side, where `_shortScreenFloor` then holds the strip at the sizes it had before (92pt swollen): no size worth drawing clears the middle of a 390pt-tall screen, which was already true at the old sizes. **The strip is drawn at an offset it computes; it has no scroll position.** That is the one decision the rest of this widget follows from, and it was arrived at the hard way. A `ListView` looks like the obvious way to build a strip, and moving it means `jumpTo` — which calls `markNeedsLayout`. But the reader's tree is full of `LayoutBuilder`s (its body, and the `OrientationBuilder` inside it), a `LayoutBuilder` runs the builds of everything under it *during layout*, and the page arrives at the strip in a build. Dirtying layout from inside a layout leaves a node needing layout whose relayout boundary does not know it; the next frame dies on `_debugRelayoutBoundaryAlreadyMarkedNeedsLayout` or on `scheduleLayoutCallback`'s own assertion, and the wreckage is the reader's Scaffold laying out a body it was never handed ("Each child must be laid out exactly once", with a `RenderErrorBox` in the slot). Deferring the scroll to a post-frame callback moves it into the one window Flutter documents as having to stay clean — `LayoutBuilder` defers its own rebuilds out of `postFrameCallbacks` and idle for exactly that reason — and deferring it to the transient phase, where animation ticks live, only made it rarer. So there is no scroll: `_offset` is a **function** of the accordion's two pages and its clock, `PositionedDirectional` puts each thumbnail at `_centre(page) - width/2`, and moving the strip is an ordinary rebuild that any phase may ask for. The sizes and the offset cannot disagree, because they are read from the same state in the same build — they used to be animated apart, which measured 123pt of daylight between the bulge and the slider's handle for the length of every page turn. Measured now: exact at both ends, exact on a jump the length of a chapter *in the frame that asks for it*, and at most 3.5pt out mid-glide. Three things follow. The strip draws only the pages in view (`_window`, exact rather than estimated, and the same window handed to the loader), so the lazy list's extent estimate and the scroll correction it used to make are gone with it. A **finger** on the strip sets `_dragged`, which overrides the follow until the page changes, and lets go into a `ClampingScrollSimulation` for the flick. And a chapter that fits on screen needs no offset at all: `_centre` puts every page under its own handle position directly, which is the same law the offset follows when the strip scrolls instead. **Nothing on that path may reach back into the reader**, and that is a rule about layout rather than about tidiness: a lazy list builds its children *during* layout, so everything the strip's item builder asks for is asked for there — and the reader used to ask for its own MediaQuery (`thumbWidth` × the device pixel ratio, for the decode width), its client and its saved copy from inside that call. An inherited lookup during a layout enrols the reader as a dependent from inside the layout, and a provider read there can mark it dirty in the same place; either way the reader can be rebuilt while it is being laid out, its Scaffold is then handed a body that is not the one it laid out, and the frame dies with "Each child must be laid out exactly once". So `_thumbCacheWidth`, `_client` and `_savedChapter` are all resolved in `didChangeDependencies` or mirrored out of `build`, and `test/reader_test.dart` rotates the device with the scrubber open and taps a far thumbnail, which are the two ways in.
- Thumbnails do **not** load when they are built. `ThumbLoadQueue` holds them for 180 ms, then fetches at most two at a time, nearest the current page first (current, previous, next, outwards), and only pages on screen — a flick through a 200-page chapter used to fire a request per thumbnail mounted. A failed thumbnail is marked done, never retried. The precache and the widget that shows a thumbnail must ask for the **same** decode width (`_thumbCacheWidth`, which is `ThumbStrip.thumbWidth` in device pixels, capped at what Kavita's thumbnail endpoint serves): `ResizeImage` puts it in the cache key, so a mismatch quietly precaches one image and displays another, and a decode a third of the drawn size is the blur the strip exists to avoid. Covered by `test/thumb_strip_test.dart`.
- The vertical-scrolling view must be **placed** before it reports anything. A scroll view has no `initialPage`, so it opens at offset 0 while the reader is on page 40; the first flick would report page 0 and post it back, wiping the place the chapter was opened at. `_VerticalScrollViewState` jumps after the first layout (offsets need the width) and `_placed` gags `_onScroll` until then. Covered by `test/reader_test.dart`.
- The initial save is deferred a frame: it is reached from `build`, and it mirrors progress into the stored copy — writing to a provider while the tree is building is what Riverpod refuses outright.
- Progress posts are serialized through a queue so a slow save cannot regress a later page, and the **last page reports `pages`, not `pages - 1`** — Kavita only marks a chapter read when `pagesRead >= pages`. The initial page is saved on open, since `onPageChanged` never fires for it.
