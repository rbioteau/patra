# The reader

*Loaded when work touches `lib/src/features/reader/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

## Reader

One setting decides everything: `ReadingDirection` is left-to-right, right-to-left, or **vertical scrolling** — that third one is a *direction*, not a separate mode, and there is a single control for it. The word "webtoon" is Kavita's, after the genre the reader was built for, and it is gone from this app in code as well as on screen: what varies is the motion, not what is being read. It is `verticalScroll` and not merely `vertical` because Kavita has two vertical readers — `ReaderMode.UpDown` pages vertically, `Webtoon` scrolls — and only the second is ours; **on screen the row is the single word "Vertical"** in both languages, which is unambiguous while it is the only vertical direction in the picker. Never write "LTR"/"RTL" in UI copy; use the full localized phrases. The enum name is also the persisted preference (`ReadingSettingsStore` writes `direction.name`, and an unrecognised string falls back to left-to-right *silently*), so `_legacyNames` still reads the stored `webtoon` — renaming a value of this enum without that is how a setting resets itself on someone's device and says nothing.

- **A seek the reader asked for is not reported back to it.** `_PagedView` follows a seek in `didUpdateWidget` with `jumpToPage`, which dispatches its scroll notification **synchronously** — and `PageView` turns that into `onPageChanged`, from inside the build that delivered the seek. Landscape is where it bites: the view reports the *first* page of the spread it landed on, so a seek to an **odd** page reports a page the reader did not ask for, the reader took that for a real page turn, and `setState` ran in the middle of a build. What follows is not obviously that: the error widget replaces the Scaffold's body, so the same frame dies on "Each child must be laid out exactly once" with a `RenderErrorBox` in `_ScaffoldSlot.body`, then hit tests fail on boxes that were never laid out. `_seeking` guards the jump, and `test/reader_test.dart` taps the second page of a spread. Any programmatic move of a `PageController` needs the same guard.
- **The reader reads its orientation off the `MediaQuery`, and must never wrap itself in a `LayoutBuilder`.** `OrientationBuilder` *is* one — it derives portrait or landscape from its own constraints — and this screen asked it a question it does not need layout to answer: the body fills the window, so the window's orientation is the same one. What it bought instead was a `LayoutBuilder` around the whole reader, and a `LayoutBuilder` runs the builds of everything beneath it **during layout**: the pages, the tap zones, the chrome, the scrubber, every image frame arriving and every `setState` the Slider makes. That is a rebuild-inside-a-layout on every one of them, and this screen died on it — `debugNeedsLayout` and `_debugRelayoutBoundaryAlreadyMarkedNeedsLayout`, both thrown from `scheduleLayoutCallback`, then "Each child must be laid out exactly once" with two `_RenderLayoutBuilder`s in `_ScaffoldSlot.body` and finally a `RenderErrorBox` in the slot. The duplicated child was that `OrientationBuilder`'s own render object: `Scaffold` wraps a body in a `LayoutBuilder` of its own only when `extendBody` or `extendBodyBehindAppBar` is set, and this one sets neither, so the body slot's `LayoutBuilder` was ours — re-inflated under `Scaffold`'s `GlobalKey`'d body while the old one was still in the slot. Read layout information here only where it is genuinely needed (the strip's width), and never around a subtree that rebuilds on animation, images and gestures.
- **The system's chrome comes and goes with ours.** The chapter opens with the status bar and the home indicator gone (`SystemUiMode.immersiveSticky`) and gets them back — `edgeToEdge`, what every other screen runs under — when the tap in the middle brings the reader's own bars up, and again on the way out. So the clock is never over the page but is always one tap away. Every path that moves `_showChrome` goes through `_showChromeAndBars`, or the two drift apart. iOS hides both for any fullscreen mode; Android honours it below API 36 and ignores it above (we target 36), and an iPad in Split View keeps its status bar whatever the app asks. Covered by `test/reader_test.dart`.
- **The top bar carries one cog, not a control per setting** (`widgets/reader_settings_sheet.dart`). It was a direction pill, which was right while the direction was the only thing there was to say. Two things changed that. Magnifying **cannot be drawn as an icon** the way a direction can — a page glyph with a flow arrow really does say "left to right", and nothing says "a one-finger drag magnifies instead of turning the page", which is the same reason the handoff makes the save pill "always worded, never icon-only". And a second pill would eat the chapter title, which is an `Expanded` that already ellipsizes inside a 56pt bar. The cog costs **no extra tap**: the pill was a menu opener rather than a toggle, so changing direction was always two taps and still is. What it loses is the direction glyph visible in the bar — a small loss, because the chrome is hidden while reading, so that glance is only ever had by someone who has just tapped for a control anyway. **What the sheet holds is what is being read**: the direction, magnifying and the width for a chapter of pictures, and a text size and a line spacing for a book (#75), which has no direction to pick and no page to magnify — one cog, two sheets, and the chapter's own nature decides which (`_ReaderSettings`). It is a **sheet and not a `PopupMenuButton`**, because a `PopupMenuItem` pops its route when tapped and a switch inside one would dismiss the menu as it was flipped; the sheet is also the shape Settings already uses for the same choice, and `ReadingDirectionRows` is shared between the two so the wording cannot drift. What the sheet draws is read off **the sheet's own context**, never off the cog's: picking a direction dismisses the sheet *and* the chrome the cog lives in, and the sheet outlives the cog — held onto the context it was opened with, the next change of the window's metrics, which is what the reader's own immersive mode does as its chrome goes, has it look an ancestor up on a deactivated element and the frame dies. Covered by `test/reader_settings_sheet_test.dart`. The sheet **scrolls**: three rows of settings no longer fit the nine sixteenths of a short screen a sheet is given, and a column that overflows there is a row nobody can see. The three rows deliberately differ: **picking a direction closes the sheet and writes it as this series' own; the magnify switch and the width slider leave it open and write the preference** — the switch on the tap, the slider on release, since a drag is dozens of steps and a preference is one choice. Reading vertically the magnifying gesture is inert, and in the paged directions no strip is laid out at a width of its own, so each row **says so** in place of its usual explanation rather than sitting there switched on and doing nothing; both stay settable, because the preference is global and the next chapter may well be the other kind. A switch that closed the surface it lives on could never be turned back off without reopening it, and made per-chapter either of them would forget itself every time a chapter was opened — a direction belongs to the book, these two belong to the hand. A number a person picks is one row (`_NumberRow`) whether it is a width or a size, because what they share is not the value but everything around it. Covered by `test/reader_test.dart`.
- **The direction a chapter opens in is one chain, asked in `reading_direction.dart` and nowhere else** (#56, #65, #58, ADR-0007): the **series** — a direction chosen for that one series — then the **library** every series shelved in it is read in, then the **detected** direction (#57), and the built-in left-to-right last. A reading profile's own default and this device's sat between the library's and the detected one until #58 took both out: detection is per series, so what those defaults were doing — choosing a direction for works nobody has opened — is what detection does better and *per work*, and a rung held by a person or a device overrides detection for every series at once, which in a library holding manga and webtoons is precisely wrong. It used to be local state in the reader: taken from the profile's preference when the chapter opened, changed in memory, and written nowhere, so a chapter set to vertical reopened paged and no write reached the keychain at all. Now the reader watches `chapterDirectionProvider((seriesId: chapter.seriesId, libraryId: chapter.libraryId))` and holds no copy, and the only things the sheet can do are write the series rung, promote what is in force to the library's, and drop either of those two — each reported as a `ReaderSettingsOutcome` for the reader to act on, since the sheet has no series or library id of its own. Both maps belong to the profile that chose them (`ProfilePreferences.seriesDirections` and `.libraryDirections`, one row per profile in the keychain) and are never sent to the server. Two rules the sheet exists to serve: a checked row alone reads as "I chose this" and a guess is not a choice, so **a line says where the direction in force came from** (only the reader's sheet: Settings has no reading section at all now, #58); and setting a rung to the value the default already holds is not the same as leaving it unset, so a series or a library that is set owes **a row back**, worded with the direction it will actually land on. Promoting does not clear the series direction — one tap, one thing. **A guess is asked last but one**: a series or a library that was set outranks it, and only the built-in left-to-right stands behind it, which nobody chose either. **The library's rung (#65) sits directly under the series'** and above the guess, because both are answers about the work's side of the chain and a library is the wider of the two — and because it is what *replaces* the profile's own (ADR-0007: a default held by a person is the wrong shape, since it overrides detection for every series at once). Its case is a library whose type is wrong: a "Manga" library holding manhua is guessed right-to-left for **every** series in it, and one tap on the library is what puts that right, where a per-series choice would be one tap per work. It is the rung the sheet's promote row writes, and what it promotes to is a library rather than a person. **The name the row is worded with comes off the spine and never off the library list**: `libraryNameProvider` (`catalogue/catalogue_reads.dart`) reads what the device already holds, because watching `catalogue.libraries` is a request — and not a small one, since that list's write starts the eager fill, which pages every library's series. Opening a chapter is not the moment to fill a household's catalogue, so where nothing has been loaded yet the row says "this library" instead. Covered by `test/reading_direction_test.dart`, `test/reader_settings_sheet_test.dart` and `test/reader_test.dart`.
- **The detected rung is read by the reader, because only the reader can read it (#57, #118).** Page dimensions reach the app in exactly one place — the `chapter-info` the reader asks for when a chapter opens — and nowhere else: the catalogue deliberately keeps reader-level data out (ADR-0005) and a saved chapter carries a page count and no dimensions, which is why opening a saved copy with no server to ask is not a lesser reader. So the reader's own fetch is what measures a work (`pageShapesProvider`), and it is recorded against the **series** rather than the chapter it was measured on, because a direction measured on one chapter of a work is a direction for the work. The two signals answer different questions and never compete, so there is no precedence to arbitrate: **whether** a work is vertical is the pages' — the **median** tallness (height / width) of the pages the server did not call a spread, at **1.8**, a number `docs/research/reader-vertical-page-shape.md` measured on a real library (#64: everything on the shelf that turns medians between 1.30 and 1.58, the two works that scroll at 1.86 and 6.94, so 2.0 and 2.2 would open a work that scrolls as one that turns) — and **which way** it goes when it is not is the library type's, the one witness to a convention of origin: a manga library reads right to left, every other one the way a chapter always has. **That type comes off the catalogue and never off the chapter** (#120): `chapter-info` declares one and `GetChapterInfo` has never assigned it — from v0.7.14 to `develop` the value its repository resolves is dropped when the response is rebuilt field by field — so every chapter of every library arrives carrying the enum's default, *manga*, which is the one type that carries a direction. Read off the chapter, this rung therefore answered right-to-left for every work whose pages gave no vertical verdict, which on a server reporting no dimensions is every scan on it. `heldLibraryTypeProvider` (`catalogue/catalogue_reads.dart`) is what answers instead, off the spine already in hand and with nothing put on the wire — `libraryNameProvider`'s mechanism for `libraryNameProvider`'s reason — and it answers **nothing** where the device holds nothing of that library, where `libraryTypeProvider` would fall back to manga and rebuild the same bug one layer down. A rung with no witness stands down and the chain reaches the built-in left-to-right nobody chose. So `PageShape` carries no type: the rung is a family of the series **and** its library, the pair `chapterDirectionProvider` was already a family of, and `ChapterInfo` stops parsing a field that was never more than a constant. Median and not mean, because one spread or one unusually short page drags a mean, which is why Kavita needs a width-variation test and a 40%-strong rule to compensate — Solo Leveling runs from 1.43 to 10.62 and medians at 6.94 — and **fewer than three pages measured is no verdict about being vertical**, Kavita's own floor — the library it was shelved in still says which way it goes, because that is the other question. The record is a measurement and not a preference: nothing is written to the device, reopening a series measures it again, and the reader is inside the app, which `SessionScope` builds on a container of the profile's own. What it costs is a direction that cannot be guessed before a chapter is open, which is what the built-in left-to-right behind it is for, and a saved copy read while its own `chapter-info` is still in flight is laid out one way for a moment and another when the answer lands — the same re-layout the dimensions themselves already cause on that frame. Covered by `test/page_shape_test.dart` and, through a real chapter opening, `test/reader_test.dart`.
- **A third kind of evidence: what a book declared of itself (#118).** The two signals above are inferences from what the server measured; this one is the work's own statement, and it is asked **first** of the three. It arrives because Kavita inlines a book's CSS into every page it hands over, and it is the only witness left: `PrepareFinalHtml` copies the classes off a book's `<html>` and `<body>` and returns their inner HTML in a wrapper of its own, so a `dir` attribute and an `<html lang>` are both thrown away while the stylesheet survives. `parseBookDirection` (`book_face.dart`, beside the `@font-face` walk — it is the same `<style>`, read once) is what reads it, `BookPage` carries it, and the reader records it against the **series** in `declaredDirectionsProvider` exactly as it records the shape of a chapter's pages. It is asked before the two measurements not as a precedence between competing answers but because that is where the questions stop overlapping: a declaration answers *which way the words run*, where the library type only witnesses a convention of origin — and a book has no page dimensions at all, so asking the pages first would read every book left to right and leave the declaration with nothing to say. **Whether** a work is vertical stays the pages' alone, because no book declares that. Four rules it must keep. **A declaration is not a match**: `ScopeStyles` leaves inert declarations behind by the handful — `html{}`, `:root{}`, `html[dir=rtl]{}` and `body[dir=rtl]{}` all survive as text and match nothing once their elements are gone — so what counts is a rule whose selector still picks out the page as a whole (the wrapper, everything, or the page's own paragraphs, `div` standing beside `p` because `_blockTags` already reads one as the other), and "is `direction:rtl` anywhere in the stylesheet" is exactly the over-trigger this exists to refuse. **Nor is a rule that only applies sometimes**, which is why `_rules` drops every at-rule and the rules inside it: nothing here can evaluate a media query, and the grammar matches the *inner* rule of a `@media print{.book-content{direction:rtl}}` as though it stood on its own — so an at-rule left in place turns the book on the strength of its print stylesheet. That correction is `_rules`', so it is the face's too: a font named in a print stylesheet is not the face a page is set in either. **The wrapper's class list is weighed in one place only** — it is what can make a selector the rescoping broke match the page again, which is the case Kavita assembles that list *for* — and never trusted alone. And **only right-to-left is read**: `direction: ltr` is the CSS default and is written as a reset far more often than as a statement, so it cannot be told from silence, where `rtl` is never written by accident. It is still evidence for a *guess*, so a series or a library somebody set outranks it. **And for a book it is the guess's only evidence**: `PageShapesNotifier.record` refuses a reflowable chapter, because a book carries no page dimensions for `chapter-info` to report — so a shape recorded for one says `isVertical: false` about a work nothing was measured of, and the library type beside it then speaks. That shipped as a regression and is what the guard exists for — and the type it would have spoken with was **nobody's**: measured first against the demo server (Kavita 0.9.1.4), where `chapter-info` reports `libraryType: 0`, manga, for all 53 epubs of a library whose type is *Books* while reporting the format correctly for every one of them, and then read in the server's own source, where `GetChapterInfo` simply never assigns the field on any version there has been. So this was not a book shelved oddly; **every book on every server** opened right-to-left, with nothing in the book saying so and nothing on the shelf either. The guard keys off the chapter's content — derived from the format, which the server does report — and never off a type. The same fault reached scans too, a comic of a *Comics* library coming back `libraryType: 0` as well; that was #57's rung rather than this guard's business, and **#120** closed it by taking the type off the catalogue instead. What is left here is unchanged by that, a book still measuring nothing. A book that declares nothing opens left to right, where a book has always opened. What a *choice* does still reach a book is the series' and the library's rungs — and since the book's cog offers no direction row, a library set right-to-left while reading its scans turns the epubs beside them with no row back; that is the gap the missing row leaves, and it is **#121**. What the page then draws from it is directional throughout, not only in its alignment: a list item's bullet is mirrored by the `Row` it sits in, and a quotation's rule and the room it leaves are a `BorderDirectional` and an `EdgeInsetsDirectional` so they move to the right with the words. Covered by `test/book_face_test.dart` for the reading, `test/page_shape_test.dart` for the rung and the chain, and `test/book_reader_test.dart` for the book laid out from it — the pager's own axis included, since a stray `reverse:` on top of the `Directionality` would undo the flip and nothing about the words would show it.
- **A one-finger drag can magnify the page** — `magnify_gesture.dart`, off by default, `magnifyProvider` in `profile_preferences.dart` (it follows the person, like the direction), and a switch in the reader's own sheet — Settings carried one too until #58 took it out, on the grounds that the reader is where a person notices they want it. Pinching needs a second hand, which a person reading on a phone does not have. Press anywhere and the page is carried along with the finger, so pulling **down** brings what was **above** into view and pulling **right** brings the **left**; the *length* of the drag sets the magnification (**2.5x** over **400pt**), and letting go returns the page. The four directions are **one rule, not four cases** — the artwork under the finger is carried towards it — and there must never be an `if (dy > 0)` in that file. Where the drag asks to go past an edge the page stops there and the artwork slides out from under the finger: **the border is held and the grip gives way**, which at these settings is the *normal* case rather than a corner, since there is little slack until near full travel. So what is pinned is where the *view* lands (it walks towards the part asked for, and keeps walking that way for the whole drag), not that a point stays under the fingertip. **That is only true because the reference point is clamped to within `travel / (maxScale - 1)` of the middle of the screen** (`_band`, ~267pt at the shipped settings, so it moves only a press within ~43pt of an edge, and carries the finger with it so the drag length is untouched). Outside that band the page grows faster than the glue can carry it and pulling *down* walked the view *down* the page — by ~1.6%, wrong way. `H` and `V` cancel out of the derivation, so one number covers both axes and every page shape. The test that thought it covered this swept drag length at a single centred anchor and could not see it; **the anchor is the axis that has to be exhaustive**, as it already was for the border. Three other answers were built and rejected in a prototype kept on the `prototype/reader-loupe-gesture` branch; `docs/adr/0001-reader-magnify-gesture.md` says what each felt like and why 2.5x/400pt. The travel distance is **absolute, not a fraction of the screen** — the ruler is a thumb, and a thumb does not grow with the display. Two consequences: the swipe that turns a page **is gone while the mode is on** (two recognisers cannot share one drag, so pages turn by tapping the sides, and the settings row says so), and **vertical scrolling is excluded**, since there the drag is the only way through the chapter. The reference point comes from the pointer-down and never from `onPanStart`, which reports where the pan was *recognised* — already ~18pt into the drag, in the direction of travel. What the gesture holds against the screen edges is the **artwork**, not the canvas: `drawnContent` computes where the scan is actually drawn (a contain fit, or the box around both halves of a spread), because holding the letterbox bars there would let the drag pan over black. Covered by `test/magnify_gesture_test.dart`, which sweeps every anchor and finger position for a border leak, and by the reader's own tests for what only shows in the tree.
- Wiring that up uncovered a bug worth remembering: **`_PagedView._reported` must be set in `initState`, not by a `late` initialiser.** A `late` field runs its initialiser at the first *read*, and the first read is the comparison in `didUpdateWidget` — where `widget.page` is already the new page, so it initialised to the value it was about to be tested against and the guard skipped the jump. The first tap on a side zone moved the reader's page number and left the pager where it was; the second jumped two. It went unnoticed because a swipe takes the other path entirely, through `onPageChanged`, and swiping was how everyone got through a chapter.
- Paged: tap zones are 30/40/30 (sides page, centre toggles chrome); right-to-left mirrors `reverse`, the tap meanings, the thumbnail strip and the slider together (via `Directionality`) while page numerals stay left-to-right.
- Landscape (paged only) becomes a two-page spread, first page of the pair leading per direction. **Which pages share a screen is `SpreadLayout`'s call, not `page ~/ 2`**: a scan that is itself a double page (Kavita's `isWide`, or dimensions plainly wider than tall — either is enough, since the server only flags the files it measured that way) takes a screen of its own, because pairing it would shrink both pages to a quarter of the screen and run the spine down the middle of a drawing meant to be seen whole. A wide page also shifts the parity of everything after it, so a step is a *screen*, not a fixed number of pages — stepping back off a wide page lands on the first page of the pair before it — and the counter's span comes from the page being arrived at. With no dimensions from the server nothing is wide and the pairing is exactly what it always was. The two pages of a pair are **pushed together against the spine** (`Image.alignment`, right for the leading page and left for the trailing one): each is contained in its own half of the screen, and centred there they would be joined by a gutter that widens with the screen and with how narrow the scans are — the pair has to meet on the centre line and spend the leftover room on the outer edges. Covered by `test/spread_layout_test.dart` and, end to end through the counter and the alignments, `test/reader_test.dart`.
- The thumbnail strip (`thumb_strip.dart`) is an accordion keyed to the page being read — current widest, its two neighbours halfway, the rest at the base size — so its item extents are not uniform: `_leadingEdge` corrects for the three swollen pages, and the scroll target measures that geometry instead of `maxScrollExtent`. **The strip states its own extent** (`_StripDelegate.estimateMaxScrollOffset`): a lazy list otherwise averages the children it has built and applies that to the rest, and with the accordion's three items wider than the rest the guess is short by tens of points — the scroll to the last page then stops short of it and leaves the bulge behind the handle. The stated extent is also steady while the accordion animates, which the guess is not; the gap after each thumbnail rides inside its item, since one child per page is what lets the delegate speak for the whole strip. The strip does **not** centre the current page: the bulge travels across it on the same linear law as the slider handle travels across its track, because the two sit one above the other and a centred bulge points somewhere else than the handle on every page but the middle one. The law lands exactly on offset 0 at the first page and on the end of the scroll at the last. **The slider's padding comes from the strip** (`ThumbStrip.sliderPadding`), not from a number of its own: the bulge's end centres are `hPadding + half a swollen thumbnail` in, Material insets a `Slider`'s handle 26pt inside its own box (measured against this theme), and the difference is what keeps the two markers agreeing at the ends whenever the thumbnails change size. `test/reader_test.dart` pins it by making the slider paint through a probe shape and comparing where the handle actually lands. A chapter short enough to fit on screen cannot scroll, so the thumbnails spread instead — even centres, uneven widths, the gaps carrying the difference — and the padding is computed so the content is exactly the viewport. Spreading stops below `_minStep`, where the current thumbnail and its neighbour would touch; between that and a full strip the natural packing already lines up closely enough. **Sizes are shares of the screen's shortest side, never points.** The shortest side, so a phone gets the same thumbnail in either orientation — a page is the same thing to recognise whichever way the device is held — and a share, because a size only means something against the screen it is drawn on: what the swollen thumbnail's width really costs is the slider's track (which is the screen less that width, see `sliderPadding`) and the pages that fit either side of it. The handoff's 34×48 is a stamp on a real device — this strip is not read, it is *aimed at* — so the base is twice that (`_baseShare` 0.174, 68pt on the 390pt phone the handoff was drawn for) and **the swollen one is a third of the screen** (`_currentShare` 0.33, 129pt), with its neighbours halfway between by arithmetic rather than by a third number. A third is as wide as it can be drawn before the slider stops reading as a slider: doubling it to 184pt put the track at 47% of the screen — a short bar floating between two wide margins — where a third leaves 61% and about four pages on screen. Only widths are shares; heights follow `_pageAspect` (the handoff's 34×48), so no thumbnail is ever drawn out of shape. Past ~107pt on a 3x phone the picture is upscaled — Kavita serves a 320px thumbnail and there is no more detail to ask for — which is accepted, because a large soft page is easier to pick out at arm's length than a small sharp one. **A tablet takes a smaller share of a wider screen** (`_tabletShareFactor` 0.64). A third of an iPad's 820pt short side would be a 270pt thumbnail with no more pages beside it than a phone shows, which is the mistake the rest of this app avoids by taking another column rather than drawing a bigger card; two thirds of the share puts it at 173pt — one step up from the phone, the same step the strip used to take at 1.35 — and spends the width it did not take on pages. **The one limit in points is a gesture, not a share**: the reader's middle third toggles the chrome, so the chrome has to stop short of the middle of the screen — reach past it and the tap that would dismiss it lands on the scrubber and seeks to whatever page is under the finger, which is worse than nothing happening. `_heightBudget` is therefore half the screen less what the chrome takes around the strip, in points because a slider and a line of type are the same size on every screen. It leaves every phone and tablet in portrait the shares whole, and catches a phone on its side, where `_shortScreenFloor` then holds the strip at the sizes it had before (92pt swollen): no size worth drawing clears the middle of a 390pt-tall screen, which was already true at the old sizes. **The strip is drawn at an offset it computes; it has no scroll position.** That is the one decision the rest of this widget follows from, and it was arrived at the hard way. A `ListView` looks like the obvious way to build a strip, and moving it means `jumpTo` — which calls `markNeedsLayout`. But the reader's tree is full of `LayoutBuilder`s (its body, and the `OrientationBuilder` inside it), a `LayoutBuilder` runs the builds of everything under it *during layout*, and the page arrives at the strip in a build. Dirtying layout from inside a layout leaves a node needing layout whose relayout boundary does not know it; the next frame dies on `_debugRelayoutBoundaryAlreadyMarkedNeedsLayout` or on `scheduleLayoutCallback`'s own assertion, and the wreckage is the reader's Scaffold laying out a body it was never handed ("Each child must be laid out exactly once", with a `RenderErrorBox` in the slot). Deferring the scroll to a post-frame callback moves it into the one window Flutter documents as having to stay clean — `LayoutBuilder` defers its own rebuilds out of `postFrameCallbacks` and idle for exactly that reason — and deferring it to the transient phase, where animation ticks live, only made it rarer. So there is no scroll: `_offset` is a **function** of the accordion's two pages and its clock, `PositionedDirectional` puts each thumbnail at `_centre(page) - width/2`, and moving the strip is an ordinary rebuild that any phase may ask for. The sizes and the offset cannot disagree, because they are read from the same state in the same build — they used to be animated apart, which measured 123pt of daylight between the bulge and the slider's handle for the length of every page turn. Measured now: exact at both ends, exact on a jump the length of a chapter *in the frame that asks for it*, and at most 3.5pt out mid-glide. Three things follow. The strip draws only the pages in view (`_window`, exact rather than estimated, and the same window handed to the loader), so the lazy list's extent estimate and the scroll correction it used to make are gone with it. A **finger** on the strip sets `_dragged`, which overrides the follow until the page changes, and lets go into a `ClampingScrollSimulation` for the flick. And a chapter that fits on screen needs no offset at all: `_centre` puts every page under its own handle position directly, which is the same law the offset follows when the strip scrolls instead. **Nothing on that path may reach back into the reader**, and that is a rule about layout rather than about tidiness: a lazy list builds its children *during* layout, so everything the strip's item builder asks for is asked for there — and the reader used to ask for its own MediaQuery (`thumbWidth` × the device pixel ratio, for the decode width), its client and its saved copy from inside that call. An inherited lookup during a layout enrols the reader as a dependent from inside the layout, and a provider read there can mark it dirty in the same place; either way the reader can be rebuilt while it is being laid out, its Scaffold is then handed a body that is not the one it laid out, and the frame dies with "Each child must be laid out exactly once". So `_thumbCacheWidth`, `_client` and `_savedChapter` are all resolved in `didChangeDependencies` or mirrored out of `build`, and `test/reader_test.dart` rotates the device with the scrubber open and taps a far thumbnail, which are the two ways in.
- Thumbnails do **not** load when they are built. `ThumbLoadQueue` holds them for 180 ms, then fetches at most two at a time, nearest the current page first (current, previous, next, outwards), and only pages on screen — a flick through a 200-page chapter used to fire a request per thumbnail mounted. A failed thumbnail is marked done, never retried. The precache and the widget that shows a thumbnail must ask for the **same** decode width (`_thumbCacheWidth`, which is `ThumbStrip.thumbWidth` in device pixels, capped at what Kavita's thumbnail endpoint serves): `ResizeImage` puts it in the cache key, so a mismatch quietly precaches one image and displays another, and a decode a third of the drawn size is the blur the strip exists to avoid. Covered by `test/thumb_strip_test.dart`.
- **The strip's geometry is one module, and the strip is a sliver told every page's extent** (`strip_geometry.dart`). `StripGeometry` holds every page's height, where every page starts and the height of the whole strip, derived from the server's page dimensions for the width the strip is laid out at; `StripExtentList` is the strip itself. It is not a `ListView.builder`, because a sliver that measures its children as it goes keeps the offset its *first* child had: change every height at once — which is what a rotation does today and a width factor will do on every pinch — and the content shifts by the offset times one minus the ratio of the two, measured at ~58 pages when halving the width at page 100, while its total is an average-based guess, so the last page cannot be reached at all. That is the flutter#86531 failure arrived at without a transform, and it is why the child delegate states the strip's whole extent, the way the thumbnail strip's delegate did. Offsets, the page at an offset and the total are then all derived from the extents, so a seek lands on the page it asked for at any width and the last page's bottom sits at the bottom of the screen. The cost is a layout that walks the pages: nothing at 200, worth watching at 2000 (ADR-0006). A place in the strip is named by a **page and a fraction down that page** (`StripAnchor`) rather than by a pixel offset, because that is the form that survives every height changing at once. Nothing in the strip's item builder reads an inherited widget or a provider, for the reason the thumbnail strip's does not: a lazy sliver builds its children during layout. Covered by `test/strip_geometry_test.dart`, which measures where pages are actually painted rather than where the arithmetic asked for them — the only kind of test that could have caught the shift.
- **The strip is laid out at a width factor, and the module owns it.** `StripGeometry` takes the width of the canvas and a factor — `1.0` being the whole screen, which is exactly how a chapter opens today — and every height follows, because a height is the width over the page's aspect ratio. Below `1.0` the strip is narrower than the screen and `StripExtentList` pads it by `StripGeometry.inset` either side, which is what centres it; what is not strip is the reader's own black canvas, with nothing of ours painted over it. **The module holds the range** (`0.5`–`1.0`, and not yet wider than the screen, which is the half of this feature that needs the pan ADR-0006 defers) rather than the two things that will set it, so a preference and a pinch cannot clamp it differently. The word is *width factor* and never *scale*. **The decode width is not an optimisation**: `StripGeometry.decodeWidthFor` is the width a page is drawn at, in device pixels, and it is what the reader asks the decoder for — narrowing puts more pages in the same 250pt cache extent (measured at about three to five between full width and half), so a decode left at the file's own size multiplies decoded memory for a change nobody can see. It is one number for the whole strip for a second reason: `ResizeImage` puts it in the cache key, so a page warmed ahead at one width and drawn at another is two images, one of them decoded for nothing — which is why the strip reports the width it decodes at along with the page (`StripPageChanged`), and why the reader warms the next page at that width and no other. The device pixel ratio is read off the `MediaQuery` in `build`, never inside the item builder, for the reason nothing else is read there. **What sets it is a preference** — `widthFactorProvider` (`settings/profile_preferences.dart`), a person's, which the reader *watches* rather than reads once: it is a choice somebody makes and expects to see at once, not a property of the chapter in hand. It is set from the reader's cog and nowhere else (#58): Settings used to carry a row for it too, and the reader is where somebody notices they want one. It is still only the width a chapter *opens* at — a pinch on top of it is a live adjustment and writes nothing, and it is the width a chapter opens at that pages are decoded for (`StripWidthController.decodeWidth`). **A width change has to put the strip back where it was.** Every height changes with the width, so the offset the strip is sitting at is a different page afterwards: at half the width, page 20's offset is page 40's. Nothing scrolls, so nothing is reported — the strip would quietly be showing page 40 to somebody the reader still believes is on page 20, and the next flick would post that page back as progress and lose the place for good. `_VerticalScrollViewState` therefore names the place (`StripAnchor`) off the geometry the current offset belongs to — or rather, the controller does, about the top of the screen, for a preference and for a pinch alike — and puts it back in the same turn, gagging the report the way a seek is gagged, since a width is not the reader moving. In the same turn and not in the frame after: a correction that waited for the frame after painted one frame at the old offset, which is nothing for a menu and a jump on every one of the width slider's dozens of steps. Covered by `test/strip_geometry_test.dart` at `0.5`, `0.7` and `1.0`, by `test/reader_test.dart` for the width the screen really asks the decoder for, and for the offset the strip keeps when the width changes.
- **Two fingers take the width factor, and they write nothing** (`strip_width.dart`). `StripWidthController` owns one number — the width the strip is laid out at — the geometry every offset is derived from, and every pointer over the strip; `StripWidthGestures` is the `Listener` above the scroll view. **Arbitration is ours, and it is not optional.** The scroll view's own drag recognizer is given no device it accepts (`ScrollConfiguration.of(context).copyWith(dragDevices: {})` — `copyWith` of the ambient behaviour rather than a `ScrollBehavior` written from scratch, because one of those would quietly leave the strip without the platform's physics, and with them without the fling a one-finger drag ends in); one finger is driven through `ScrollPosition.drag`, so physics and flings stay the framework's; a second finger turns the gesture into a pinch with the drag **cancelled** on the way in, so a pinch that starts on a moving list inherits no velocity and the scroll it interrupted is dropped rather than thrown; whatever was still moving under it is stopped with the offset it is at, or a fling carries the place out from under the fingers while they are holding it. Lifting one of two fingers starts a fresh drag where the remaining finger is. The stock composition was measured and fails the first of those outright: a pinch that begins while the first finger is already scrolling does not begin at all, and one that does keeps the *previous* gesture's anchor (`prototype/reader-strip-width`, commit `838ffa4`, variant A against B).
- **Every pinch update relayouts for real**, and the same (page, fraction) is put back under the fingers **in the same turn as the width changes** — the paint-preview alternative was measured and rejected (it saved about half a millisecond of a pinch frame that costs about one and a half over a scroll frame, and was the slower of the two with its extra composited layer). It is clamped against our own geometry and not against `maxScrollExtent`, which is the last frame's layout and an extent the strip has not been laid out at yet — `jumpTo` clamps nothing at all, and an offset past either end of the strip is a strip drawn off its own content. **At a document edge the anchor cannot be held** — the first page, with the fingers below the top of it, or the last, where the strip below them shrank away with the width — there is no content left to put under the finger. It clamps, and `clampedBy` says by how much rather than swallowing it: a clamp nobody can see is a correction that reads as one that worked. Measured rather than hidden because ADR-0006 asks for it, and pinned at both ends by `test/strip_width_test.dart` (300pt halving a 200-page strip at its last page, 135pt with the fingers 270pt down the first). A pinch update runs in the pointer phase, which is the one place this screen may move the strip: never from a layout callback, and never deferred to a post-frame one, which paints a frame at the old offset and is a frame late everywhere.
- **A pinch writes nothing.** The width a chapter opens at is the preference; the pinch's width is dropped the moment the preference moves, and leaving the chapter and coming back builds a controller from the preference again. Nothing is reported while two fingers are down either — what the strip is showing is what they are holding, not a page somebody has read their way to — and where it landed is brought up to date when the gesture settles, without being posted. The range stays `0.5`–`1.0` and there is **no horizontal pan**: below `1.0` the strip is never wider than the screen, so there is no axis to arbitrate. If you find yourself writing axis arbitration, stop — that is `>1×`, and it is a later ticket.
- **A rotation is the one correction that is not made in the same turn** (#51), and the one place this module waits for a frame. The new width is not a number until the layout running hands it over, and a `jumpTo` from inside a layout is the thing this screen has already died on — so `measure` names the place off the geometry the strip was *drawn* at, about the top of the screen, and a post-frame callback puts it back at the end of the frame that was laid out at the new width. **The frame right after a rotation is therefore drawn at the old offset: one frame, accepted, recorded in ADR-0006 and pinned in a test so it is not later filed as a bug.** A pinch never pays it, because a pinch knows its width before it asks for it. Only a change of canvas *width* is a rotation — a new chapter places itself, and so does a different page count — and while one is held (`resizing`) nothing the strip lands on is progress: it is the old offset read against new heights, which is not where the reader is. Covered by `test/strip_width_test.dart` turning the surface both ways — and during a fling, which the correction stops rather than leaving to carry the place away — and end to end by `test/reader_test.dart`, with and without the chrome open, where every height is proportional to the width so the offset a rotation lands on is the old one scaled by what the canvas became. **While two fingers hold the width there is no rotation correction at all**: the place is theirs to hold, and their own next update puts it back about the fingers at the new width.
- **The rest of the lifecycle is the same strip** (#51): a chapter the server measured nothing about, a saved chapter read with no server to ask, a chapter of one page, and a page that will not load. With **no dimensions** every page shares `PageDimension.defaultAspectRatio`, so the strip is uniform and its last page is as reachable as any other — nothing needs a fallback, and none is written. A **saved chapter** is the same case by another road: the stored copy carries a page count and no dimensions, so offline is not a lesser reader. A chapter of **one page** has nowhere to seek to: reading vertically the rail *is* the seek control, and a rail with one position is furniture that cannot be used, so the chrome draws the counter alone. Paged reading keeps the chrome it has — this work leaves paged alone (#46) — and the boundary is pinned by a test on each side. And a page that **failed to load** costs the strip nothing but its picture: the extents are the sliver's and not the image's, so the pages around it do not move. Covered by `test/strip_width_test.dart` and `test/reader_test.dart`.
- **The vertical chrome's seek control is a rail, not the paged strip and slider** (#52, `page_rail.dart`). The strip under a horizontal slider runs along the axis the paged directions turn on; vertical reading is scrolled along the other one, so its seek control runs there too — a rail against the right edge of the screen, built by `_VerticalScrollViewState` with the chrome and hidden with it, and replacing the `ThumbStrip`+`Slider` the bottom chrome used to carry in this direction (the paged chrome keeps both, untouched). Its mapping is by the pages' **real heights**: each page gets the share of the rail its height has of the chapter, straight off `StripGeometry`, so a page twice as tall as its neighbour gets twice the rail and the handle sits where the fraction of the chapter's height above it ends. A seek lands at the top of the page asked for either way, which is why the proportional map loses no granularity against an even one — the only thing the even map lied about was position. Where the server measured nothing, the default ratio collapses the rail into an even one by itself. The **number** is drawn while a finger is on the rail and nowhere else, floating a thumb's height clear of the finger that is dragging it (above it in the body of the rail, below it near the top, where there is no room above to clear it): position is what the rail draws, and the number is only the address a seek lands on, so drawing both at once is drawing the answer twice and the question once. **A rail touch is a seek even on the page the reader is on**: the finger snaps a mid-page scroll to the page's top (`_railSeek` reports via `onPageChanged`, whose same-page guard simply hears nothing), mirroring the slider's own tap-to-seek; progress is saved the way the slider saves it. Three of the strip's own rules become the rail's. The rail **listens to the scroll controller** (`controller.addListener`) so the handle follows a scroll the reader has not been told about yet, but a notification the view itself provoked — a seek, a width change — is reported from inside the reader's build, and the rail skips it (`seeking: () => _seeking`, the same flag `_jumpTo` now wraps around every jump of its own) rather than rebuilding from there, which is what this screen has already died on; the build that follows the move carries where the strip landed. Its pointer column is **opaque** so a finger on it is a seek and nothing else listens for the same finger — the strip's scroll and the chrome's tap stay out — dimensions in points because this is a control and a control never scales with the screen (`hitWidth` 44, track 6, handle 26 and accent, since reading progress is what `patraAccent` is for and the paged slider's thumb already wears it). And it runs between the chrome bars — its gaps are the bars' own constants (`_TopChrome.barHeight`, `_BottomChrome.barHeight`), handed in by the caller rather than restated, so a change to either bar is a change to the bar alone (the same rule as `ThumbStrip.sliderPadding`) — plus the safe-area padding measured the way the chrome measures it: a device's notch insets the top bar and the rail clears it wherever it ends up rather than covering the cog, and a device that runs a bar or a gesture nav along the *right* edge of the screen (some do, in portrait) tucks the rail just inside it rather than under it — a rail the system overlays is a rail the reading thumb drags under the system's gesture instead. A chapter of one page draws no rail — the caller's guard `pages > 1`, the same furniture rule as before. Covered by `test/page_rail_test.dart` at the module and by `test/reader_test.dart` for what only shows in the reader.
- **The decode width does not follow the pinch.** It is the width the strip is drawn at — the whole point of it is that narrowing puts more pages in the same cache extent — but `ResizeImage` puts that width in its cache key, and a pinch changes it continuously, so a decode width that tracked it would ask for a new image on every frame of the gesture and re-decode every live page throughout. What the reader asks the decoder for is therefore the width the strip *settled* at — the preference, or where the last pinch let go — and it changes once, when the pinch is over — the last finger but one lifting, which is the moment the width stops moving, and not any frame of the pinch (`StripWidthController.decodeWidth`, which is also the width `onPageChanged` reports for the page warmed ahead). What is drawn in between is the image already in the cache, which is the memory the strip was already paying for. Covered by `test/strip_width_test.dart`.
- **A page keeps the picture it has while the next is decoded** (`PageImage` in `page_loading.dart`). The width a page is decoded at is part of its cache key (`ResizeImage` puts it there), so every time the width moves — a pinch settling, a hand on the width slider, a rotation — every live page is asked for a new picture. `gaplessPlayback` keeps the old one inside the widget, but `Image.frameBuilder` is what decides what is drawn, and a builder that shows `PageLoading` whenever there is no frame covers the very picture it was asked to keep: the strip blinked once per step of the gesture. So the frame builder remembers whether a picture has ever been painted and only waits when there has never been one. Covered by `test/page_loading_test.dart`.
- The pinch tests are **at the widget, not through the reader screen**: `test/strip_width_test.dart` mounts the module's own strip, drives one `TestGesture` per finger for the two-finger cases, and reads where pages are actually painted out of the render tree rather than off the geometry that asked for it — the only kind of test that could have caught the shift. `test/reader_test.dart` covers the one thing that is the reader's: that a pinch narrows the strip, writes no preference, and does not outlive the chapter.
- The vertical-scrolling view must be **placed** before it reports anything. A scroll view has no `initialPage`, so it opens at offset 0 while the reader is on page 40; the first flick would report page 0 and post it back, wiping the place the chapter was opened at. `_VerticalScrollViewState` jumps after the first layout (offsets need the width) and `_placed` gags `_onScroll` until then. Covered by `test/reader_test.dart`.
- The initial save is deferred a frame: it is reached from `build`, and it mirrors progress into the stored copy — writing to a provider while the tree is building is what Riverpod refuses outright.
- Progress posts are serialized through a queue so a slow save cannot regress a later page, and the **last page reports `pages`, not `pages - 1`** — Kavita only marks a chapter read when `pagesRead >= pages`. The initial page is saved on open, since `onPageChanged` never fires for it.
- **Progress goes into the stored copy before it is posted, not after** (#78). A page a reader turns with no server in reach is a page the server has not been told, and the copy is the only thing on the device that outlives the app being closed on it — so `_saveProgress` writes `PendingProgress` (the number *and*, for a book, the anchor) into the copy first, posts, and clears it only once the server has taken it. What sends what is left over is `DownloadsNotifier.syncPendingProgress`, asked for when the server starts answering and when the store is read; the reader itself never retries. Clearing is guarded by the exact record that was sent, so a page turned while the post was in flight is not lost by its answer.

## A book

**The reader branches where the chapter's nature is known, and nowhere else:** `_buildReader` asks `chapter.content` once and hands a [[Reflowable content]] chapter to `_buildBookReader`. Everything above it — the route, the id, the progress arithmetic, the bar, the close gesture — is the reader's own and is not redefined for a book.

- **How long a book is, is `book-info`'s answer, not `chapter-info`'s, and where in it the reader was is `get-progress`'s.** `chapter-info` counts image pages and a book has none, so `chapterInfoProvider` asks the book about itself when the format says EPUB and the chapter keeps the page count and the title it was given (`ChapterInfo.withBook`) — together with the server's own record of progress, since neither answer needs the other and opening a book on one alone is opening it wrong. Three requests where a picture chapter needs one, and the other two are only ever made for a book. **Nor is the third one a request whose failure can be swallowed**: a book the server will not say the place of is a book that would otherwise open at page 0 and post that back, which is the reader's own place wiped — so it does not open, as a chapter it cannot open already does not.
- **Where a reader is in a book is a page and a place within it, and both are the server's to say** (#72). A book's page can be longer than the screen, so a page number alone opens it again at words already read; `bookScrollId`, the marker the progress call has always carried and this app had never sent, is that place, and `get-progress` is where it comes back. **It is a block and a fraction down that block** (`BookAnchor`, #128) — which of the blocks the rewrite pass numbered (`data-patra-block`) the top of the screen is in, and how far through it — written `patra:<block>@<fraction>`, since the server stores the field as an opaque string and the form is ours. Not a number of points, because a text size (#75), a face, a rotation and a differently sized window all move the words; and no longer a fraction of the whole page, which is only *nearly* stable under reflow — pictures do not grow with the words. **A bare fraction is still read**, as the share of the page it always meant: it is already on servers and in copies, and it is what the app's own development renderer still writes, having no blocks to name (and a block anchor opens that renderer at the top). That is `_legacyNames`' rule applied to a position: an old value is a value. It is read back defensively, because Kavita's own web client fills the same field with the id of an element in the page — a marker that is not a place is no anchor at all rather than a failure, and the page opens at its top. Covered by `test/book_anchor_test.dart`.
- **A book's pages are fetched while the reader is at rest, not when they are reached.** `PageView.builder` mounts a page as late as it can — the neighbour the moment a drag begins — so a page asked for only when it is mounted is a page fetched **under the reader's finger**, and what is drawn while it comes is a spinner over the whole screen: the flicker on every turn and every back-turn. So the reader watches `bookPageProvider` for the pages either side of the one it is on, which is both the prefetch and the keep-alive: an `autoDispose` provider something is watching is not disposed, so a page turned back to is still in hand instead of being asked for again. **Watched, not `keepAlive()`d** — the two beside this one are held and the rest of the book is still forgotten with the screen, which is the point of the family. `test/book_reader_test.dart` pins that each page is asked for once across a turn and a turn back, and that no frame of a turn shows a spinner where the reader can see one (off screen does not count: a page fetched beside the one being read is fetched out of sight, which is the whole idea).
- **A book opens where the server says, not where the route does** — the one thing the reader declines to be told. The two ways in do not say the same thing: the series screen names a page (`readerLocation`) and a link names none, so a book opened from a link would otherwise open at its first page while the place it was left at belongs to another one. Asked once, on the first build of the book, and clamped to the page before the last: a book read to its end is remembered at the page *past* it, which is not a page it has.
- **A page is drawn by the platform's web engine where there is one, and by us where there is none** (`book_web_page.dart`, ADR-0013, #127). On Android and iOS the page goes through the rewrite pass and is handed to `webview_flutter`, and the book is composed as its publisher set it — tables, ruby, a picture inline with its words, its own alignment and colours. **Where there is no engine** — Linux, and every test binding — the page is taken apart into blocks and drawn by `BookPageBody` (`book_page.dart`), which honours the book's face and no other rule of its CSS (ADR-0010, ADR-0012); that renderer is what the suite pins, and #131 is what names it development-only. Which one draws is `bookWebEngineProvider`, a provider rather than a check at the call site because an engine, once registered, cannot be unregistered — so a test says which reader it is asking about. The parser is not optional on either path: the downloader reads `pictureSources`, and so does the web path, to know what to fetch.
- **In the app's own renderer, prose is set ragged right; nothing is justified.** In the web engine the book's own declared alignment holds, and justifying where it declares none is #130. It used to be justified, and the reason it is not is measured rather than a matter of taste: on Flutter 3.47.2 the engine **honours U+00AD as a break opportunity but draws no hyphen at the break** — with the app's own font loaded, `hyphen­ation` breaks at exactly the soft hyphen yet its first line measures `73.6`, where a real `hyphen-` measures `82.7`, and the control (`hyphen-ation`, first line `82.7`) shows that a trailing hyphen *is* counted in a line's width. So the app cannot hyphenate: it could only chop words with no mark at all, which reads as a rendering fault rather than as typography — and honouring a publisher's `&shy;` has the same defect. Without hyphenation, a column as narrow as a phone's opens gaps when it is justified; set ragged right, it opens none. A heading is not prose and a list item is a line: neither is stretched, and neither changes. **Do not put justification back** without first saying where the hyphen comes from. Since #93 a publisher's `&shy;` is decoded all the same, and lands on exactly that: as U+00AD it is invisible and it is a break opportunity, where the five characters of its name were drawn in the middle of a word — better than printing its name, and still nothing to justify with.
- **A page's pictures are named inside the book, and the server resolves the name — or are named by a whole address the page already carries, which is the server's guess at itself and is never followed.** `BookPicture.src` is what the page's HTML said: usually a path inside the book (`OEBPS/images/worm.jpg`), which `KavitaClient.bookPictureUrl` turns into a `book-resources` request. Kavita also writes the other kind — a whole address **with no scheme in it** (`//host/api/book/7/book-resources?apiKey=…&file=cover.jpg`), which is what a cover page is made of and what any page's pictures become once the server's own name-correction pass has touched them. **Only the `file` in it is kept**, and the request is rebuilt on the `baseUrl` this session was built with: Kavita composes that address out of `Request.Host + Request.PathBase`, so a reverse proxy serving it on a port or under a path of its own — and not telling it so — has the server naming a host the app has never spoken to, and every picture in the book 404s *from the proxy* while the words come down the working address fine. The one address known to reach the server is the one the pages themselves arrived on. Its `apiKey` goes with the rest of the address, this endpoint being header-authenticated, and repeating it would put one profile's credential into the key of a cache four profiles share. An address that names anything but `book-resources` is left where it lives. Either way it is drawn under `imageCacheKey` like every other image in the app — and where the fetch does fail, a page whose only block is that picture is drawn as nothing at all, with no message, because `BookPageUnavailable` is only for a page with no blocks.
- **A page is a page, not a flow: content that fits is set in the middle of the screen** (`BookPageBody`). What the server laid out on one is shorter than the screen more often than not — a cover, a part's title, the last page of a chapter — and hanging it off the top edge is what made a cover look like a picture pinned to the ceiling. So the column is given the screen's height as a *minimum* and centred in it; a page taller than the screen keeps the scroll it already had, because centring content one has to scroll would begin off the top edge with no way back. The bottom margin is four gutters rather than one, and the centring is inside that room: the page counter sits there, and a page allowed to end under it is a page whose last line cannot be read.
- **Navigation is paged, and none of the picture reader's paged machinery comes with it.** One server page per screen, turned by the same swipe and the same side tap zones (`_TapZones`, hoisted out of `_buildReader` so a book, a paged chapter and a scrolling one share one definition — and named for *where the zones are*, because which side reads on is the direction's business and mirroring it twice would undo the mirror). No page has a size, so there is no spread in landscape and no magnification. **There is a direction, though, and it is not one the cog offers** (#118): the same chain a chapter of pictures is resolved through, whose detected rung reads what the book declared of itself in its own stylesheet — and the one answer sets both halves, the prose's `Directionality` (which is what its `TextAlign.start` resolves against) and the pager, which turns inside that same `Directionality` because a horizontal `PageView` scrolls the way the text around it reads. So there must be **no `reverse` on top of it**, for the same reason the tap zones are named for where they are: a second mirror undoes the first, and the zones are outside that `Directionality` and passed the other way round instead. Doing only the text half would leave a book reading right-to-left while its pages turned left-to-right, which is worse than leaving it as it is. `verticalScroll` collapses to left-to-right here rather than being a third case — a book's pages are the server's and they are turned, so a strip to scroll through is not something a book has — and the chrome, its numerals included, never turns with the book. The cog still offers no direction row: the rung it would write is above a reading that is right nearly always, and #118 left that surface alone. There are no page pictures to fill a strip with either, so the bottom chrome is the counter alone (`_BottomChrome.showStrip`). A page longer than the screen is scrolled by the page's own view, which is where the anchor comes from. **What the cog offers for a book is how it is set** — see the next bullet.

- **A book is set at a text size, a line spacing and a face, and those are the only settings it has** (#75, #92). The bar's cog opens a sheet of its own (`showBookSettingsSheet`) holding exactly those three, and nothing about pictures: which way pages turn is a question about pictures, and with no page sizes there is nothing to measure, nothing to pair into a spread, no strip to lay out at a width and no page to magnify. All three are **one value for every book** and all are the person's — a property of the reader's eyes rather than of the work, like the width and magnifying, with a device default behind them for a profile that has never chosen (the book's own face for the face, ADR-0012). The range they are chosen over is the setting's own (`reading_settings.dart`), so a slider and a pinch cannot clamp differently, and the value is written once, when the finger lifts. **Changing any of them redraws the page where the reader is**: in the web engine the page is written again and put back at the block the bridge last reported, which is exactly the same words whatever they are set at; in the app's own renderer the place is read as a fraction of the room there is to scroll before the words move and put back after they have been laid out. A page that grows under the reader and leaves them where they were in the pixels has made them read the words above again.

- **A book is set in the face its reader chose, and the choice is a kind of type rather than a font** (#92, ADR-0012): the third row of the same sheet, and the last. Three of them — **the book's own**, the app's serif, the app's sans — and the book's own is the default, which is what the server's own client does: its font choice is a sentinel that resolves to CSS `inherit` and leaves the book's stylesheet to win. The rows are **composed in the face they offer** rather than named after a family, because a family name says nothing to somebody who does not already know what that family looks like — and the book's own row is composed in the face the book actually resolved to, the app's sans where it resolved to none. **The whole page is set in it** — prose, headings, quotations and list items — because a book set in a serif with sans intertitres reads as an interface rather than as a book; the page counter is the app's own furniture and stays in the serif either way, as it already did, so a page of a book is a mixture by design and this does not make it one. Emphasis is set in the italic of the face where it has one and in the roman where it does not: **Space Grotesk has no italic at all**, and a slant the engine drew is not a letterform anybody designed. `ReadingFace.resolve` answers the family and the italic together and is the only place either is decided, so a page cannot disagree with the row that chose it. This is the one deliberate hole in the design system's serif rule, written down as a hole in `CONTEXT.md` under **Reading face** and beside the rule itself, so it is not silently widened.
- **The book's own face is read out of the page's own stylesheet, and registered once per book** (`book_face.dart`). Kavita inlines the book's CSS into every page it hands over, scoped, with every `@font-face` source rewritten to `book-resources` — so a page says, in the book's own words, which face its words are in and where that face's files are, and that is the whole of what this app reads of it: the `@font-face` blocks, and the rule that *uses* a family. `parseBookFace` answers with the family and its roman and its italic, or with nothing — a book that ships several families and never says which one its words are in is read as asking for **none**, so the app's sans stands in rather than setting a page of prose in whatever the book used for its chapter titles, and so is a book whose font the engine will not decode. A face is registered through `FontLoader` under a name **namespaced by the chapter**, because that registers a family for the whole process and there is no way to unload one: a book shipping a font called `Literata` must not shadow the app's own. Once it has landed the family is answerable **synchronously**, because a page turn must not flash the fallback, and a second ask for the same face fetches nothing.
- **A copy carries the book's face**, as `book-font` and `book-font-italic` beside its pages — see `lib/src/downloads/CLAUDE.md`. A saved book opening in the face its reader chose with no server to ask is the promise every bundled family exists for, and it would have been a strange promise to break for the one face that is not bundled.
- **The contents of a book are the server's list, and the reader asks before it offers them** (#76). `GET /api/Book/{chapterId}/chapters` is Kavita's own table of contents — the endpoint's summary calls it "essentially building the table of contents" — and it answers a **tree**: `BookChapterItem` carries `children`, so a part is the parent of the rows beneath it and not a heading above them, and the sheet draws that as an indent rather than flattening it. `title` and `page` are what this app reads; **`part` is left alone**, being the id of an anchor inside the book's own files (`01_values.xhtml#h_sVZPaxUSy/`), which only a reader rendering those files can scroll to — a page is what this one opens. The page number is the server's and counts from zero, so the number beside an entry is one more, the way the counter under the page already reads. Choosing one is a jump and nothing else: the same `_goTo` a swipe uses, so progress is reported for it exactly as for a page turned to by hand. It is watched by the reader (`bookContentsProvider`) rather than by the sheet it fills, because **whether the server listed anything is what decides whether a control is drawn at all** — a book with no contents offers none and says nothing about the absence, and a sheet opening onto "no contents" is a message about an absence rather than no button. Where there is one, the control sits in the bottom chrome beside the counter, and the counter stays in the middle of the screen: the room on either side of it is matched, so a page number is still where it was before a book had one.
- **A saved book is read out of the copy, and the copy is what says it is a book** (#77). `bookPageProvider` asks the stored page before it asks the server — the same preference a stored page of pictures already had, and the only page there is once there is no server — and `_bookPicture` draws a name that is a data URI from the bytes it carries (`carriedPictureBytes`), so a page's pictures need no server either. What tells the reader to open the book reader at all offline is `SavedChapter.format`, carried into the `ChapterInfo` the reader falls back to when `chapter-info` cannot be had: without it a saved book would open in the picture reader and show nothing. A copy that does not hold the page being asked for — the server has recounted the book since, which is what leaves a copy out of date (#78) — falls back to asking, exactly as a missing stored page of pictures does. Covered by `test/book_reader_test.dart` (the server is never asked) and `test/offline_reading_test.dart` (no server at all).
- **Opening a saved copy is where the two page totals are put to each other** (#78). A copy keeps the pagination it was made with (ADR-0009), so the count the server gives now is a fact about the copy and not about the chapter: where the two disagree the reader says so once, through `DownloadsNotifier.notePageTotal`, and the Downloads row names the copy out of date and offers to store it again. It is the reader that notices because it is the one place both numbers are in hand — the copy on the device, and the total only the server gives — and it costs no request of its own, `book-info` having been asked anyway. The copy is still read, and still records progress, either way; only the naming is new.
- **A book knows the language it is written in, and nothing guesses it** (#125). `ChapterInfo.language` is the saved copy's where the copy recorded one — a copy is read as it was made (ADR-0009), and one that says costs no request — and otherwise `Chapter.language`, which `chapterInfoProvider` takes off the catalogue through `heldChapter` — the series screen's volumes carry it and are on the device before a row can be tapped, so the normal way in costs no request — and asks `GET /api/Chapter` for only where the catalogue holds no such chapter, which is a book opened from a link. A chapter held with no language is the server's answer, not an absence, and is not asked about again; a question that fails is answered with none rather than failing the book. The reader lays the copy's language over the answer as well, because offline there is no answer to lay it under. **Never** fill a missing one from the interface language, the library type or the profile: an engine with no language declines to hyphenate on its own, which is the behaviour wanted (ADR-0013). It is the rewrite pass's input, which sets it on the document the web engine is handed; the app's own renderer is handed it and draws nothing with it. The **declared direction** is a separate question with a separate source, the book's stylesheet, and the two are not merged. Covered by `test/book_reader_test.dart` (*the language a book is written in*).
- **One pass makes a page inert and self-contained, and it is the whole of the trust boundary** (`book_rewrite.dart`, `rewriteBookPage`, ADR-0013, #126). Kavita sanitises nothing, so everything a web view will be given goes through it — streamed or stored, identically — and nothing else rewrites a page for an engine. It answers a whole document: the content policy **first** (a policy governs only what is asked for after it is read, and it is the backstop, not the defence); no script, handler, frame, `<base>` or `<meta>`; every address a page can fetch from answered by the caller's `localFile` — asked with the name exactly as the page wrote it, the one `pictureSources` reads, and refused where the answer is not itself local — or by a fragment or the page's own `data:`, and **removed** otherwise, a link that leaves the page included; the reader's size, leading and face in a cascade layer declared before the book, whose `!important` outranks every one the book makes — the size on the root only, so a size the book fixes is read as a share of 16px (`12pt` becomes `1rem`) and a heading stays larger than its words, and an inline `!important` on those three loses its mark, since a style attribute's outranks any sheet's; the language on `<html>` only where it is a BCP-47 tag; and a `data-patra-block` per block, counted in document order and forgeable by nobody. **Every tag it keeps is rebuilt**, from attributes read the way a browser's tokenizer reads them (`bookAttributes`), so what leaves it can only be read one way — the way it was checked. That is also why `markupPieces` now ends a tag where a browser does (a `>` inside quotes does not; a `<` opening nothing is a word, and no longer loops forever at the end of a page). A `<style>`'s CSS is left with no `<` and no `&` (`\3c `, `\26 `), because inside an SVG it is markup rather than raw text. An SVG's own `url(` — `fill`, `filter`, `mask`, `clip-path`, `marker-*`, `cursor` — is rewritten like a stylesheet's, and its animations (`set`, `animate*`) are dropped, since they set any attribute to anything after the pass has read it; a `data:` stays only as a picture's name; a declarative shadow root is left a template, the layer not reaching inside one; a CSS comment is dropped, since one between two tokens hid the second from the size rules. **Two things #127 inherits:** a caller's answer is accepted as local when it has no scheme but `file:` and no host, so a relative name is only local if the page is loaded from a file base — load it from anything else and the backstop policy is all that is left; and `bookAttributes` (the tokenizer, which the pass rebuilds tags from) is not `bookAttribute` (the parser's older regex, which `pictureSources` reads through and which answers `href` for an `xlink:href`) — the two agree on any tag a book really carries, and the day they must not differ is the day they become one. The web engine renders it (#127); justification is #130. It also declares the files the reader's chosen face is set from (`faceFiles`), since an engine has none of the app's faces, and sets the page on the reader's canvas in its ink — in the same layer, **without** `!important`, so a book's own colours and margins are its design and outrank them. The pass is meant to be read in one sitting — keep it that way. Covered by `test/book_rewrite_test.dart`, adversarially.
- **In the web engine, a page is a file, and what it names is fetched by the app and written beside it** (`book_document.dart`, #127). `book-resources` is header-authenticated in this client and a header travels with a top-level request alone, so a page cannot name its pictures at the server: `bookPageFilesProvider` fetches every picture a page names — and the files of the face its stylesheet asks for — with the client's own headers, writes them into the temporary directory under `book-pages/<profile>/<chapter>/` — per profile, a chapter id being a server's — and the rewrite is told each one's `file:` address; a name the page carries the bytes of (`data:`, a saved copy's pictures) is not fetched, and a saved copy's face is copied out of the copy, its stylesheet naming it at an address that is dead offline. The document is written at the **root** of the profile's `book-pages/` directory and loaded with `loadFile`, for two reasons that are not details: the rewrite accepts a name as local only where it has no scheme but `file:`, and an engine on iOS reads only inside the directory the page is in. The app's own faces are written out of the bundle into that root's `fonts/` (`appFaceFiles`) and declared to the page by the rewrite (`faceFiles`), since an engine has none of them. Pictures are fetched **before** a page is drawn — ADR-0013's accepted cost — which is why the reader watches `bookPageFilesProvider` for the pages either side of the one it is on, as it watches `bookPageProvider`. The page opens where the anchor says, told and put back through the app's own bridge (`PatraBridge`, `bookBridgeScript`: JavaScript is enabled for it alone, run by the host and so ungoverned by the page's policy). The script is handed the anchor as JSON and puts the named block's line at the top of the screen — again once `document.fonts` is ready, unless the reader has scrolled first — and reports, when a scroll settles, the **innermost** block the top of the screen is in (the last in document order to hold that line), or the next one down at its top where the line falls between blocks; a page scrolled to its very top is at its top, and a page with no named block is reported as a bare fraction. What it posts back is JSON too, and both directions are `BookAnchor.toJson`/`fromJson`, so the anchor's two forms — the JSON a script reads and the string the server stores — live in `BookAnchor` alone. A scroll the script makes is `behavior: 'instant'` whatever the book's own `scroll-behavior`, and is never reported back: only the reader's own scrolling is a place, so opening a page posts nothing the initial save did not. **Nothing of that geometry is testable here** — no engine lays out under a test binding — so the suite pins what the engine is told and what is posted, and a device is where the script is seen to work. The view goes nowhere but its own file — a fragment of it included — and claims vertical drags only, so a horizontal one is still the pager's and a tap still the side zones'. Covered by `test/book_document_test.dart`, and by `test/book_reader_test.dart` (*the web engine*) through a fake `WebViewPlatform` that paints nothing and remembers the document it was handed: what was fetched and with which header, where the pictures are, what was posted, which way the pages turn. **Nothing of the engine paints under a test binding**, and nothing here pretends otherwise.
- **Progress keeps its shape**: a page number, and the total on the last page, which is the rule that marks a chapter read — plus, for a book, the anchor beside it, which is the same call's own field rather than a second one. It is also the only progress there is, so a book under way is a series under way: the Continue hero, On deck, the ring on a cover and the bar under a row all read off the same count (#73). A book is paged by the server, so a page number is also a position the server chose — see ADR-0008 and, for a saved copy, ADR-0009.
- **A page the server cannot produce says so** rather than being a screen of nothing: an empty page reads as a book with no words in it. The message is `BookPageUnavailable`, shown both for a refused request and for an answer with no page in it.
- Covered by `test/book_reader_test.dart`, which drives the real client over the fake HTTP seam in a **Book** library and asserts which page was asked for and what was posted — the anchor included — and where a reopened page was scrolled to, read out of the render tree, and that a page set at another size **or in another face** is set at it without losing the reader's place in it and without asking the server for the page again. It also pins that every run of words on the page is set in the chosen face while the counter is not, and that no block of a page is justified. Never the server's HTML. The sheet's contents for a book against a chapter — the face's row included — are pinned in `test/reader_settings_sheet_test.dart`, and the face following the person across a handover in `test/profile_preferences_test.dart`.
