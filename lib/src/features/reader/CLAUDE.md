# The reader

*Loaded when work touches `lib/src/features/reader/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

## Reader

One setting decides everything: `ReadingDirection` is left-to-right, right-to-left, or **vertical scrolling** — that third one is a *direction*, not a separate mode, and there is a single control for it. The word "webtoon" is Kavita's, after the genre the reader was built for, and it is gone from this app in code as well as on screen: what varies is the motion, not what is being read. It is `verticalScroll` and not merely `vertical` because Kavita has two vertical readers — `ReaderMode.UpDown` pages vertically, `Webtoon` scrolls — and only the second is ours; **on screen the row is the single word "Vertical"** in both languages, which is unambiguous while it is the only vertical direction in the picker. Never write "LTR"/"RTL" in UI copy; use the full localized phrases. The enum name is also the persisted preference (`ReadingSettingsStore` writes `direction.name`, and an unrecognised string falls back to left-to-right *silently*), so `_legacyNames` still reads the stored `webtoon` — renaming a value of this enum without that is how a setting resets itself on someone's device and says nothing.

- **A seek the reader asked for is not reported back to it.** `_PagedView` follows a seek in `didUpdateWidget` with `jumpToPage`, which dispatches its scroll notification **synchronously** — and `PageView` turns that into `onPageChanged`, from inside the build that delivered the seek. Landscape is where it bites: the view reports the *first* page of the spread it landed on, so a seek to an **odd** page reports a page the reader did not ask for, the reader took that for a real page turn, and `setState` ran in the middle of a build. What follows is not obviously that: the error widget replaces the Scaffold's body, so the same frame dies on "Each child must be laid out exactly once" with a `RenderErrorBox` in `_ScaffoldSlot.body`, then hit tests fail on boxes that were never laid out. `_seeking` guards the jump, and `test/reader_test.dart` taps the second page of a spread. Any programmatic move of a `PageController` needs the same guard.
- **The reader reads its orientation off the `MediaQuery`, and must never wrap itself in a `LayoutBuilder`.** `OrientationBuilder` *is* one — it derives portrait or landscape from its own constraints — and this screen asked it a question it does not need layout to answer: the body fills the window, so the window's orientation is the same one. What it bought instead was a `LayoutBuilder` around the whole reader, and a `LayoutBuilder` runs the builds of everything beneath it **during layout**: the pages, the tap zones, the chrome, the scrubber, every image frame arriving and every `setState` the Slider makes. That is a rebuild-inside-a-layout on every one of them, and this screen died on it — `debugNeedsLayout` and `_debugRelayoutBoundaryAlreadyMarkedNeedsLayout`, both thrown from `scheduleLayoutCallback`, then "Each child must be laid out exactly once" with two `_RenderLayoutBuilder`s in `_ScaffoldSlot.body` and finally a `RenderErrorBox` in the slot. The duplicated child was that `OrientationBuilder`'s own render object: `Scaffold` wraps a body in a `LayoutBuilder` of its own only when `extendBody` or `extendBodyBehindAppBar` is set, and this one sets neither, so the body slot's `LayoutBuilder` was ours — re-inflated under `Scaffold`'s `GlobalKey`'d body while the old one was still in the slot. Read layout information here only where it is genuinely needed (the strip's width), and never around a subtree that rebuilds on animation, images and gestures.
- **The system's chrome comes and goes with ours.** The chapter opens with the status bar and the home indicator gone (`SystemUiMode.immersiveSticky`) and gets them back — `edgeToEdge`, what every other screen runs under — when the tap in the middle brings the reader's own bars up, and again on the way out. So the clock is never over the page but is always one tap away. Every path that moves `_showChrome` goes through `_showChromeAndBars`, or the two drift apart. iOS hides both for any fullscreen mode; Android honours it below API 36 and ignores it above (we target 36), and an iPad in Split View keeps its status bar whatever the app asks. Covered by `test/reader_test.dart`.
- **The top bar carries one cog, not a control per setting** (`widgets/reader_settings_sheet.dart`). It was a direction pill, which was right while the direction was the only thing there was to say. Two things changed that. Magnifying **cannot be drawn as an icon** the way a direction can — a page glyph with a flow arrow really does say "left to right", and nothing says "a one-finger drag magnifies instead of turning the page", which is the same reason the handoff makes the save pill "always worded, never icon-only". And a second pill would eat the chapter title, which is an `Expanded` that already ellipsizes inside a 56pt bar. The cog costs **no extra tap**: the pill was a menu opener rather than a toggle, so changing direction was always two taps and still is. What it loses is the direction glyph visible in the bar — a small loss, because the chrome is hidden while reading, so that glance is only ever had by someone who has just tapped for a control anyway. It is a **sheet and not a `PopupMenuButton`**, because a `PopupMenuItem` pops its route when tapped and a switch inside one would dismiss the menu as it was flipped; the sheet is also the shape Settings already uses for the same choice, and `ReadingDirectionRows` is shared between the two so the wording cannot drift. What the sheet draws is read off **the sheet's own context**, never off the cog's: picking a direction dismisses the sheet *and* the chrome the cog lives in, and the sheet outlives the cog — held onto the context it was opened with, the next change of the window's metrics, which is what the reader's own immersive mode does as its chrome goes, has it look an ancestor up on a deactivated element and the frame dies. Covered by `test/reader_settings_sheet_test.dart`. The sheet **scrolls**: three rows of settings no longer fit the nine sixteenths of a short screen a sheet is given, and a column that overflows there is a row nobody can see. The three rows deliberately differ: **picking a direction closes the sheet and overrides the direction for this chapter only; the magnify switch and the width slider leave it open and write the preference** — the switch on the tap, the slider on release, since a drag is dozens of steps and a preference is one choice. Reading vertically the magnifying gesture is inert, and in the paged directions no strip is laid out at a width of its own, so each row **says so** in place of its usual explanation rather than sitting there switched on and doing nothing; both stay settable, because the preference is global and the next chapter may well be the other kind. A switch that closed the surface it lives on could never be turned back off without reopening it, and made per-chapter either of them would forget itself every time a chapter was opened — a direction belongs to the book, these two belong to the hand. Covered by `test/reader_test.dart`.
- **A one-finger drag can magnify the page** — `magnify_gesture.dart`, off by default, `magnifyProvider` in `profile_preferences.dart` (it follows the person, like the direction), and a switch in the reader's own sheet — Settings carried one too until #58 took it out, on the grounds that the reader is where a person notices they want it. Pinching needs a second hand, which a person reading on a phone does not have. Press anywhere and the page is carried along with the finger, so pulling **down** brings what was **above** into view and pulling **right** brings the **left**; the *length* of the drag sets the magnification (**2.5x** over **400pt**), and letting go returns the page. The four directions are **one rule, not four cases** — the artwork under the finger is carried towards it — and there must never be an `if (dy > 0)` in that file. Where the drag asks to go past an edge the page stops there and the artwork slides out from under the finger: **the border is held and the grip gives way**, which at these settings is the *normal* case rather than a corner, since there is little slack until near full travel. So what is pinned is where the *view* lands (it walks towards the part asked for, and keeps walking that way for the whole drag), not that a point stays under the fingertip. **That is only true because the reference point is clamped to within `travel / (maxScale - 1)` of the middle of the screen** (`_band`, ~267pt at the shipped settings, so it moves only a press within ~43pt of an edge, and carries the finger with it so the drag length is untouched). Outside that band the page grows faster than the glue can carry it and pulling *down* walked the view *down* the page — by ~1.6%, wrong way. `H` and `V` cancel out of the derivation, so one number covers both axes and every page shape. The test that thought it covered this swept drag length at a single centred anchor and could not see it; **the anchor is the axis that has to be exhaustive**, as it already was for the border. Three other answers were built and rejected in a prototype kept on the `prototype/reader-loupe-gesture` branch; `docs/adr/0001-reader-magnify-gesture.md` says what each felt like and why 2.5x/400pt. The travel distance is **absolute, not a fraction of the screen** — the ruler is a thumb, and a thumb does not grow with the display. Two consequences: the swipe that turns a page **is gone while the mode is on** (two recognisers cannot share one drag, so pages turn by tapping the sides, and the settings row says so), and **vertical scrolling is excluded**, since there the drag is the only way through the chapter. The reference point comes from the pointer-down and never from `onPanStart`, which reports where the pan was *recognised* — already ~18pt into the drag, in the direction of travel. What the gesture holds against the screen edges is the **artwork**, not the canvas: `drawnContent` computes where the scan is actually drawn (a contain fit, or the box around both halves of a spread), because holding the letterbox bars there would let the drag pan over black. Covered by `test/magnify_gesture_test.dart`, which sweeps every anchor and finger position for a border leak, and by the reader's own tests for what only shows in the tree.
- Wiring that up uncovered a bug worth remembering: **`_PagedView._reported` must be set in `initState`, not by a `late` initialiser.** A `late` field runs its initialiser at the first *read*, and the first read is the comparison in `didUpdateWidget` — where `widget.page` is already the new page, so it initialised to the value it was about to be tested against and the guard skipped the jump. The first tap on a side zone moved the reader's page number and left the pager where it was; the second jumped two. It went unnoticed because a swipe takes the other path entirely, through `onPageChanged`, and swiping was how everyone got through a chapter.
- Paged: tap zones are 30/40/30 (sides page, centre toggles chrome); right-to-left mirrors `reverse`, the tap meanings, the thumbnail strip and the slider together (via `Directionality`) while page numerals stay left-to-right.
- Landscape (paged only) becomes a two-page spread, first page of the pair leading per direction. **Which pages share a screen is `SpreadLayout`'s call, not `page ~/ 2`**: a scan that is itself a double page (Kavita's `isWide`, or dimensions plainly wider than tall — either is enough, since the server only flags the files it measured that way) takes a screen of its own, because pairing it would shrink both pages to a quarter of the screen and run the spine down the middle of a drawing meant to be seen whole. A wide page also shifts the parity of everything after it, so a step is a *screen*, not a fixed number of pages — stepping back off a wide page lands on the first page of the pair before it — and the counter's span comes from the page being arrived at. With no dimensions from the server nothing is wide and the pairing is exactly what it always was. The two pages of a pair are **pushed together against the spine** (`Image.alignment`, right for the leading page and left for the trailing one): each is contained in its own half of the screen, and centred there they would be joined by a gutter that widens with the screen and with how narrow the scans are — the pair has to meet on the centre line and spend the leftover room on the outer edges. Covered by `test/spread_layout_test.dart` and, end to end through the counter and the alignments, `test/reader_test.dart`.
- The thumbnail strip (`thumb_strip.dart`) is an accordion keyed to the page being read — current widest, its two neighbours halfway, the rest at the base size — so its item extents are not uniform: `_leadingEdge` corrects for the three swollen pages, and the scroll target measures that geometry instead of `maxScrollExtent`. **The strip states its own extent** (`_StripDelegate.estimateMaxScrollOffset`): a lazy list otherwise averages the children it has built and applies that to the rest, and with the accordion's three items wider than the rest the guess is short by tens of points — the scroll to the last page then stops short of it and leaves the bulge behind the handle. The stated extent is also steady while the accordion animates, which the guess is not; the gap after each thumbnail rides inside its item, since one child per page is what lets the delegate speak for the whole strip. The strip does **not** centre the current page: the bulge travels across it on the same linear law as the slider handle travels across its track, because the two sit one above the other and a centred bulge points somewhere else than the handle on every page but the middle one. The law lands exactly on offset 0 at the first page and on the end of the scroll at the last. **The slider's padding comes from the strip** (`ThumbStrip.sliderPadding`), not from a number of its own: the bulge's end centres are `hPadding + half a swollen thumbnail` in, Material insets a `Slider`'s handle 26pt inside its own box (measured against this theme), and the difference is what keeps the two markers agreeing at the ends whenever the thumbnails change size. `test/reader_test.dart` pins it by making the slider paint through a probe shape and comparing where the handle actually lands. A chapter short enough to fit on screen cannot scroll, so the thumbnails spread instead — even centres, uneven widths, the gaps carrying the difference — and the padding is computed so the content is exactly the viewport. Spreading stops below `_minStep`, where the current thumbnail and its neighbour would touch; between that and a full strip the natural packing already lines up closely enough. **Sizes are shares of the screen's shortest side, never points.** The shortest side, so a phone gets the same thumbnail in either orientation — a page is the same thing to recognise whichever way the device is held — and a share, because a size only means something against the screen it is drawn on: what the swollen thumbnail's width really costs is the slider's track (which is the screen less that width, see `sliderPadding`) and the pages that fit either side of it. The handoff's 34×48 is a stamp on a real device — this strip is not read, it is *aimed at* — so the base is twice that (`_baseShare` 0.174, 68pt on the 390pt phone the handoff was drawn for) and **the swollen one is a third of the screen** (`_currentShare` 0.33, 129pt), with its neighbours halfway between by arithmetic rather than by a third number. A third is as wide as it can be drawn before the slider stops reading as a slider: doubling it to 184pt put the track at 47% of the screen — a short bar floating between two wide margins — where a third leaves 61% and about four pages on screen. Only widths are shares; heights follow `_pageAspect` (the handoff's 34×48), so no thumbnail is ever drawn out of shape. Past ~107pt on a 3x phone the picture is upscaled — Kavita serves a 320px thumbnail and there is no more detail to ask for — which is accepted, because a large soft page is easier to pick out at arm's length than a small sharp one. **A tablet takes a smaller share of a wider screen** (`_tabletShareFactor` 0.64). A third of an iPad's 820pt short side would be a 270pt thumbnail with no more pages beside it than a phone shows, which is the mistake the rest of this app avoids by taking another column rather than drawing a bigger card; two thirds of the share puts it at 173pt — one step up from the phone, the same step the strip used to take at 1.35 — and spends the width it did not take on pages. **The one limit in points is a gesture, not a share**: the reader's middle third toggles the chrome, so the chrome has to stop short of the middle of the screen — reach past it and the tap that would dismiss it lands on the scrubber and seeks to whatever page is under the finger, which is worse than nothing happening. `_heightBudget` is therefore half the screen less what the chrome takes around the strip, in points because a slider and a line of type are the same size on every screen. It leaves every phone and tablet in portrait the shares whole, and catches a phone on its side, where `_shortScreenFloor` then holds the strip at the sizes it had before (92pt swollen): no size worth drawing clears the middle of a 390pt-tall screen, which was already true at the old sizes. **The strip is drawn at an offset it computes; it has no scroll position.** That is the one decision the rest of this widget follows from, and it was arrived at the hard way. A `ListView` looks like the obvious way to build a strip, and moving it means `jumpTo` — which calls `markNeedsLayout`. But the reader's tree is full of `LayoutBuilder`s (its body, and the `OrientationBuilder` inside it), a `LayoutBuilder` runs the builds of everything under it *during layout*, and the page arrives at the strip in a build. Dirtying layout from inside a layout leaves a node needing layout whose relayout boundary does not know it; the next frame dies on `_debugRelayoutBoundaryAlreadyMarkedNeedsLayout` or on `scheduleLayoutCallback`'s own assertion, and the wreckage is the reader's Scaffold laying out a body it was never handed ("Each child must be laid out exactly once", with a `RenderErrorBox` in the slot). Deferring the scroll to a post-frame callback moves it into the one window Flutter documents as having to stay clean — `LayoutBuilder` defers its own rebuilds out of `postFrameCallbacks` and idle for exactly that reason — and deferring it to the transient phase, where animation ticks live, only made it rarer. So there is no scroll: `_offset` is a **function** of the accordion's two pages and its clock, `PositionedDirectional` puts each thumbnail at `_centre(page) - width/2`, and moving the strip is an ordinary rebuild that any phase may ask for. The sizes and the offset cannot disagree, because they are read from the same state in the same build — they used to be animated apart, which measured 123pt of daylight between the bulge and the slider's handle for the length of every page turn. Measured now: exact at both ends, exact on a jump the length of a chapter *in the frame that asks for it*, and at most 3.5pt out mid-glide. Three things follow. The strip draws only the pages in view (`_window`, exact rather than estimated, and the same window handed to the loader), so the lazy list's extent estimate and the scroll correction it used to make are gone with it. A **finger** on the strip sets `_dragged`, which overrides the follow until the page changes, and lets go into a `ClampingScrollSimulation` for the flick. And a chapter that fits on screen needs no offset at all: `_centre` puts every page under its own handle position directly, which is the same law the offset follows when the strip scrolls instead. **Nothing on that path may reach back into the reader**, and that is a rule about layout rather than about tidiness: a lazy list builds its children *during* layout, so everything the strip's item builder asks for is asked for there — and the reader used to ask for its own MediaQuery (`thumbWidth` × the device pixel ratio, for the decode width), its client and its saved copy from inside that call. An inherited lookup during a layout enrols the reader as a dependent from inside the layout, and a provider read there can mark it dirty in the same place; either way the reader can be rebuilt while it is being laid out, its Scaffold is then handed a body that is not the one it laid out, and the frame dies with "Each child must be laid out exactly once". So `_thumbCacheWidth`, `_client` and `_savedChapter` are all resolved in `didChangeDependencies` or mirrored out of `build`, and `test/reader_test.dart` rotates the device with the scrubber open and taps a far thumbnail, which are the two ways in.
- Thumbnails do **not** load when they are built. `ThumbLoadQueue` holds them for 180 ms, then fetches at most two at a time, nearest the current page first (current, previous, next, outwards), and only pages on screen — a flick through a 200-page chapter used to fire a request per thumbnail mounted. A failed thumbnail is marked done, never retried. The precache and the widget that shows a thumbnail must ask for the **same** decode width (`_thumbCacheWidth`, which is `ThumbStrip.thumbWidth` in device pixels, capped at what Kavita's thumbnail endpoint serves): `ResizeImage` puts it in the cache key, so a mismatch quietly precaches one image and displays another, and a decode a third of the drawn size is the blur the strip exists to avoid. Covered by `test/thumb_strip_test.dart`.
- **The strip's geometry is one module, and the strip is a sliver told every page's extent** (`strip_geometry.dart`). `StripGeometry` holds every page's height, where every page starts and the height of the whole strip, derived from the server's page dimensions for the width the strip is laid out at; `StripExtentList` is the strip itself. It is not a `ListView.builder`, because a sliver that measures its children as it goes keeps the offset its *first* child had: change every height at once — which is what a rotation does today and a width factor will do on every pinch — and the content shifts by the offset times one minus the ratio of the two, measured at ~58 pages when halving the width at page 100, while its total is an average-based guess, so the last page cannot be reached at all. That is the flutter#86531 failure arrived at without a transform, and it is why the child delegate states the strip's whole extent, the way the thumbnail strip's delegate did. Offsets, the page at an offset and the total are then all derived from the extents, so a seek lands on the page it asked for at any width and the last page's bottom sits at the bottom of the screen. The cost is a layout that walks the pages: nothing at 200, worth watching at 2000 (ADR-0006). A place in the strip is named by a **page and a fraction down that page** (`StripAnchor`) rather than by a pixel offset, because that is the form that survives every height changing at once. Nothing in the strip's item builder reads an inherited widget or a provider, for the reason the thumbnail strip's does not: a lazy sliver builds its children during layout. Covered by `test/strip_geometry_test.dart`, which measures where pages are actually painted rather than where the arithmetic asked for them — the only kind of test that could have caught the shift.
- **The strip is laid out at a width factor, and the module owns it.** `StripGeometry` takes the width of the canvas and a factor — `1.0` being the whole screen, which is exactly how a chapter opens today — and every height follows, because a height is the width over the page's aspect ratio. Below `1.0` the strip is narrower than the screen and `StripExtentList` pads it by `StripGeometry.inset` either side, which is what centres it; what is not strip is the reader's own black canvas, with nothing of ours painted over it. **The module holds the range** (`0.5`–`1.0`, and not yet wider than the screen, which is the half of this feature that needs the pan ADR-0006 defers) rather than the two things that will set it, so a preference and a pinch cannot clamp it differently. The word is *width factor* and never *scale*. **The decode width is not an optimisation**: `StripGeometry.decodeWidthFor` is the width a page is drawn at, in device pixels, and it is what the reader asks the decoder for — narrowing puts more pages in the same 250pt cache extent (measured at about three to five between full width and half), so a decode left at the file's own size multiplies decoded memory for a change nobody can see. It is one number for the whole strip for a second reason: `ResizeImage` puts it in the cache key, so a page warmed ahead at one width and drawn at another is two images, one of them decoded for nothing — which is why the strip reports the width it decodes at along with the page (`StripPageChanged`), and why the reader warms the next page at that width and no other. The device pixel ratio is read off the `MediaQuery` in `build`, never inside the item builder, for the reason nothing else is read there. **What sets it is a preference** — `widthFactorProvider` (`settings/profile_preferences.dart`), a person's, which the reader *watches* rather than reads once: it is a choice somebody makes and expects to see at once, not a property of the chapter in hand. It is set from the reader's cog and nowhere else (#58): Settings used to carry a row for it too, and the reader is where somebody notices they want one. It is still only the width a chapter *opens* at — a pinch on top of it is a live adjustment and writes nothing, and it is the width a chapter opens at that pages are decoded for (`StripWidthController.decodeWidth`). **A width change has to put the strip back where it was.** Every height changes with the width, so the offset the strip is sitting at is a different page afterwards: at half the width, page 20's offset is page 40's. Nothing scrolls, so nothing is reported — the strip would quietly be showing page 40 to somebody the reader still believes is on page 20, and the next flick would post that page back as progress and lose the place for good. `_VerticalScrollViewState` therefore names the place (`StripAnchor`) off the geometry the current offset belongs to — or rather, the controller does, about the top of the screen, for a preference and for a pinch alike — and puts it back in the same turn, gagging the report the way a seek is gagged, since a width is not the reader moving. In the same turn and not in the frame after: a correction that waited for the frame after painted one frame at the old offset, which is nothing for a menu and a jump on every one of the width slider's dozens of steps. Covered by `test/strip_geometry_test.dart` at `0.5`, `0.7` and `1.0`, by `test/reader_test.dart` for the width the screen really asks the decoder for, and for the offset the strip keeps when the width changes.
- **Two fingers take the width factor, and they write nothing** (`strip_width.dart`). `StripWidthController` owns one number — the width the strip is laid out at — the geometry every offset is derived from, and every pointer over the strip; `StripWidthGestures` is the `Listener` above the scroll view. **Arbitration is ours, and it is not optional.** The scroll view's own drag recognizer is given no device it accepts (`ScrollConfiguration.of(context).copyWith(dragDevices: {})` — `copyWith` of the ambient behaviour rather than a `ScrollBehavior` written from scratch, because one of those would quietly leave the strip without the platform's physics, and with them without the fling a one-finger drag ends in); one finger is driven through `ScrollPosition.drag`, so physics and flings stay the framework's; a second finger turns the gesture into a pinch with the drag **cancelled** on the way in, so a pinch that starts on a moving list inherits no velocity and the scroll it interrupted is dropped rather than thrown; whatever was still moving under it is stopped with the offset it is at, or a fling carries the place out from under the fingers while they are holding it. Lifting one of two fingers starts a fresh drag where the remaining finger is. The stock composition was measured and fails the first of those outright: a pinch that begins while the first finger is already scrolling does not begin at all, and one that does keeps the *previous* gesture's anchor (`prototype/reader-strip-width`, commit `838ffa4`, variant A against B).
- **Every pinch update relayouts for real**, and the same (page, fraction) is put back under the fingers **in the same turn as the width changes** — the paint-preview alternative was measured and rejected (it saved about half a millisecond of a pinch frame that costs about one and a half over a scroll frame, and was the slower of the two with its extra composited layer). It is clamped against our own geometry and not against `maxScrollExtent`, which is the last frame's layout and an extent the strip has not been laid out at yet — `jumpTo` clamps nothing at all, and an offset past either end of the strip is a strip drawn off its own content. **At a document edge the anchor cannot be held** — the first page, with the fingers below the top of it, or the last, where the strip below them shrank away with the width — there is no content left to put under the finger. It clamps, and `clampedBy` says by how much rather than swallowing it: a clamp nobody can see is a correction that reads as one that worked. Measured rather than hidden because ADR-0006 asks for it, and pinned at both ends by `test/strip_width_test.dart` (300pt halving a 200-page strip at its last page, 135pt with the fingers 270pt down the first). A pinch update runs in the pointer phase, which is the one place this screen may move the strip: never from a layout callback, and never deferred to a post-frame one, which paints a frame at the old offset and is a frame late everywhere.
- **A pinch writes nothing.** The width a chapter opens at is the preference; the pinch's width is dropped the moment the preference moves, and leaving the chapter and coming back builds a controller from the preference again. Nothing is reported while two fingers are down either — what the strip is showing is what they are holding, not a page somebody has read their way to — and where it landed is brought up to date when the gesture settles, without being posted. The range stays `0.5`–`1.0` and there is **no horizontal pan**: below `1.0` the strip is never wider than the screen, so there is no axis to arbitrate. If you find yourself writing axis arbitration, stop — that is `>1×`, and it is a later ticket.
- **A rotation is the one correction that is not made in the same turn** (#51), and the one place this module waits for a frame. The new width is not a number until the layout running hands it over, and a `jumpTo` from inside a layout is the thing this screen has already died on — so `measure` names the place off the geometry the strip was *drawn* at, about the top of the screen, and a post-frame callback puts it back at the end of the frame that was laid out at the new width. **The frame right after a rotation is therefore drawn at the old offset: one frame, accepted, recorded in ADR-0006 and pinned in a test so it is not later filed as a bug.** A pinch never pays it, because a pinch knows its width before it asks for it. Only a change of canvas *width* is a rotation — a new chapter places itself, and so does a different page count — and while one is held (`resizing`) nothing the strip lands on is progress: it is the old offset read against new heights, which is not where the reader is. Covered by `test/strip_width_test.dart` turning the surface both ways — and during a fling, which the correction stops rather than leaving to carry the place away — and end to end by `test/reader_test.dart`, with and without the chrome open, where every height is proportional to the width so the offset a rotation lands on is the old one scaled by what the canvas became. **While two fingers hold the width there is no rotation correction at all**: the place is theirs to hold, and their own next update puts it back about the fingers at the new width.
- **The rest of the lifecycle is the same strip** (#51): a chapter the server measured nothing about, a saved chapter read with no server to ask, a chapter of one page, and a page that will not load. With **no dimensions** every page shares `PageDimension.defaultAspectRatio`, so the strip is uniform and its last page is as reachable as any other — nothing needs a fallback, and none is written. A **saved chapter** is the same case by another road: the stored copy carries a page count and no dimensions, so offline is not a lesser reader. A chapter of **one page** has nowhere to seek to: reading vertically the rail *is* the seek control, and a rail with one position is furniture that cannot be used, so the chrome draws the counter alone. Paged reading keeps the chrome it has — this work leaves paged alone (#46) — and the boundary is pinned by a test on each side. And a page that **failed to load** costs the strip nothing but its picture: the extents are the sliver's and not the image's, so the pages around it do not move. Covered by `test/strip_width_test.dart` and `test/reader_test.dart`.
- **The vertical chrome's seek control is a rail, not the paged strip and slider** (#52, `page_rail.dart`). The strip under a horizontal slider runs along the axis the paged directions turn on; vertical reading is scrolled along the other one, so its seek control runs there too — a rail against the right edge of the screen, built by `_VerticalScrollViewState` with the chrome and hidden with it, and replacing the `ThumbStrip`+`Slider` the bottom chrome used to carry in this direction (the paged chrome keeps both, untouched). Its mapping is by the pages' **real heights**: each page gets the share of the rail its height has of the chapter, straight off `StripGeometry`, so a page twice as tall as its neighbour gets twice the rail and the handle sits where the fraction of the chapter's height above it ends. A seek lands at the top of the page asked for either way, which is why the proportional map loses no granularity against an even one — the only thing the even map lied about was position. Where the server measured nothing, the default ratio collapses the rail into an even one by itself. The **number** is drawn while a finger is on the rail and nowhere else, floating a thumb's height clear of the finger that is dragging it (above it in the body of the rail, below it near the top, where there is no room above to clear it): position is what the rail draws, and the number is only the address a seek lands on, so drawing both at once is drawing the answer twice and the question once. **A rail touch is a seek even on the page the reader is on**: the finger snaps a mid-page scroll to the page's top (`_railSeek` reports via `onPageChanged`, whose same-page guard simply hears nothing), mirroring the slider's own tap-to-seek; progress is saved the way the slider saves it. Three of the strip's own rules become the rail's. The rail **listens to the scroll controller** (`controller.addListener`) so the handle follows a scroll the reader has not been told about yet, but a notification the view itself provoked — a seek, a width change — is reported from inside the reader's build, and the rail skips it (`seeking: () => _seeking`, the same flag `_jumpTo` now wraps around every jump of its own) rather than rebuilding from there, which is what this screen has already died on; the build that follows the move carries where the strip landed. Its pointer column is **opaque** so a finger on it is a seek and nothing else listens for the same finger — the strip's scroll and the chrome's tap stay out — dimensions in points because this is a control and a control never scales with the screen (`hitWidth` 44, track 6, handle 26 and accent, since reading progress is what `patraAccent` is for and the paged slider's thumb already wears it). And it runs between the chrome bars — its gaps are the bars' own constants (`_TopChrome.barHeight`, `_BottomChrome.barHeight`), handed in by the caller rather than restated, so a change to either bar is a change to the bar alone (the same rule as `ThumbStrip.sliderPadding`) — plus the safe-area padding measured the way the chrome measures it: a device's notch insets the top bar and the rail clears it wherever it ends up rather than covering the cog, and a device that runs a bar or a gesture nav along the *right* edge of the screen (some do, in portrait) tucks the rail just inside it rather than under it — a rail the system overlays is a rail the reading thumb drags under the system's gesture instead. A chapter of one page draws no rail — the caller's guard `pages > 1`, the same furniture rule as before. Covered by `test/page_rail_test.dart` at the module and by `test/reader_test.dart` for what only shows in the reader.
- **The decode width does not follow the pinch.** It is the width the strip is drawn at — the whole point of it is that narrowing puts more pages in the same cache extent — but `ResizeImage` puts that width in its cache key, and a pinch changes it continuously, so a decode width that tracked it would ask for a new image on every frame of the gesture and re-decode every live page throughout. What the reader asks the decoder for is therefore the width the strip *settled* at — the preference, or where the last pinch let go — and it changes once, when the pinch is over — the last finger but one lifting, which is the moment the width stops moving, and not any frame of the pinch (`StripWidthController.decodeWidth`, which is also the width `onPageChanged` reports for the page warmed ahead). What is drawn in between is the image already in the cache, which is the memory the strip was already paying for. Covered by `test/strip_width_test.dart`.
- **A page keeps the picture it has while the next is decoded** (`PageImage` in `page_loading.dart`). The width a page is decoded at is part of its cache key (`ResizeImage` puts it there), so every time the width moves — a pinch settling, a hand on the width slider, a rotation — every live page is asked for a new picture. `gaplessPlayback` keeps the old one inside the widget, but `Image.frameBuilder` is what decides what is drawn, and a builder that shows `PageLoading` whenever there is no frame covers the very picture it was asked to keep: the strip blinked once per step of the gesture. So the frame builder remembers whether a picture has ever been painted and only waits when there has never been one. Covered by `test/page_loading_test.dart`.
- The pinch tests are **at the widget, not through the reader screen**: `test/strip_width_test.dart` mounts the module's own strip, drives one `TestGesture` per finger for the two-finger cases, and reads where pages are actually painted out of the render tree rather than off the geometry that asked for it — the only kind of test that could have caught the shift. `test/reader_test.dart` covers the one thing that is the reader's: that a pinch narrows the strip, writes no preference, and does not outlive the chapter.
- The vertical-scrolling view must be **placed** before it reports anything. A scroll view has no `initialPage`, so it opens at offset 0 while the reader is on page 40; the first flick would report page 0 and post it back, wiping the place the chapter was opened at. `_VerticalScrollViewState` jumps after the first layout (offsets need the width) and `_placed` gags `_onScroll` until then. Covered by `test/reader_test.dart`.
- The initial save is deferred a frame: it is reached from `build`, and it mirrors progress into the stored copy — writing to a provider while the tree is building is what Riverpod refuses outright.
- Progress posts are serialized through a queue so a slow save cannot regress a later page, and the **last page reports `pages`, not `pages - 1`** — Kavita only marks a chapter read when `pagesRead >= pages`. The initial page is saved on open, since `onPageChanged` never fires for it.
