# Downloads and offline

*Loaded when work touches `lib/src/downloads/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

`DownloadsService` stores pages under `<documents>/downloads/<profile>/<chapterId>/`, one extension-less file per page, and writes `meta.json` **last** — a chapter directory without readable metadata is a partial download. `queue.json` is the authority for whether that partial is alive: a queued, downloading, interrupted or failed record keeps it for a retry; a readable queue with no live record lets the next `scan()` delete it; and an unreadable queue is ambiguous, so the bytes are kept. The `<profile>` segment is `Profile.id` percent-encoded (see `lib/src/auth/CLAUDE.md`), and `scan()` also **deletes** any chapter directory sitting straight in the downloads root: that is the flat layout this replaced, recognised by being named for a chapter id and so all digits, which no encoded profile id is. A test fixture must therefore be written *through* the service (`saveChapterFixture` in `test_support.dart`) — a hand-built path is not merely filed oddly, it is swept, which makes the test that reads it back quietly vacuous. Covered by `test/downloads_service_test.dart` (pass `DownloadsService(root:, profileId:)` a temp dir and a profile id) and by `test/saved_chapters_per_profile_test.dart`.

`queue.json` in that profile root is the durable source of every download state. One record per chapter carries the request, the current attempt (`queued`, `downloading`, `interrupted`, `failed` or `saved`), its priority and completed-page count, plus the finished `SavedChapter` where one exists. `DownloadsState` is projected from those records; `saved`, `inFlight`, `failed` and `interrupted` are not independent memory-only collections. Queue writes are serialized and replaced through a temporary file, and an enqueue is written before its request starts. The notifier fills at most `maxConcurrentChapterDownloads` slots. Queued batch work stays FIFO; the latest direct request overtakes it, and the chapter open in the reader outranks both until that reader closes. Within each chapter, at most `maxConcurrentPageDownloads` pages are fetched together, and each page is written with asynchronous file I/O rather than blocking the main isolate. On a cold read, a record left queued or downloading becomes interrupted and waits for an explicit retry rather than firing requests during launch. A retry reuses every complete staged page, including pages promoted before a process stopped, and fetches only what is missing; a book also reuses the queue's first page total so a changed server pagination cannot splice two layouts into one copy. A user cancellation removes a fresh record and its partial files; cancelling a refresh restores the saved record for the copy it never spent.

A record also carries the **batch** it was enqueued as part of, where there was one, and keeps it once the copy is finished — which is what lets the Downloads tab go on counting a chapter that has left its in-flight section. Batches are numbered by a counter over the profile's own queue, seeded from the highest id the device has already written down, so a batch asked for now outranks every one before it.

**A pause is not an interruption, and who stopped it is the whole difference** (#104). `paused` sits beside `interrupted` in the record's states and the two are deliberately not one: a pause is the app's own doing — it left the foreground, or the reader left their profile — and what was paused goes on **without being asked**, from the pages it kept; an interruption is a process that stopped without saying so, and only the reader's word starts it again. **A third state, `pausedByUser`, is the reader's own pause** — the pill's tap on a copy that is on its way — and it exists for one reason: `_resumePaused` requeues *everything* the app paused whenever the app comes back to the foreground or a profile is entered, so a reader's pause written down as `paused` would be undone by the next app switch. Nothing resumes a `pausedByUser` copy but a tap. `_pause` never touches one (it takes only `isInFlight`), the launch hold never fills from one (see below), and the two wear **one word to the reader** — *Paused*, the same blue, the same play glyph — because the word is the same fact either way and only the resumption is not. The pause takes effect by cancelling the request, which is why `_run`'s catch reads the status it finds before it decides: without that, a copy the reader paused comes back as `interrupted`, in danger, offering a retry. Leaving the foreground cancels every request in flight and writes each record down as paused, a merely *queued* copy included: the point is that nothing is in flight when the OS takes the app away. `inactive` is deliberately not leaving — it is the app switcher sliding over a screen that is still there, and a copy paused for that would refetch a page for nothing. A **profile** is paused the same way the moment its session ends, because the container that owns the queue is thrown away as soon as somebody else enters: `switchProfile` is where the batch stops, and tapping the same face again builds a container that resumes it at once. Nothing of anybody else's moves — the storage paths are per profile, and so are the queues.

**A launch is the one case that asks.** The queue is read at launch like anything else, and a record that comes back paused or interrupted is *held* rather than resumed — `_awaitingResume` in the notifier is that hold — while `DownloadsState.awaitingResume` is the question it raises: `DownloadsResumeStrip` names how many copies are involved and waits for a tap, and **not one page is fetched until then**, since a resumed batch would spend a data plan before the reader had seen a screen. The two are one while the question stands and part company when it is dropped: see the strip's own paragraph below. Resume sends them all on; "not now" turns the paused ones into interrupted, which is a decision and not a postponement — nothing resumes them at the next trip out of the foreground. **A reader's pause is not part of the question at all**: the hold is filled from `paused` and `interrupted` only, so a `pausedByUser` copy is not counted in the strip's sentence — which says the *app* was closed in the middle of it, and would be false — and is not held, there being nothing to hold it from. It comes back exactly as the reader left it: listed as paused, with the tap that sends it on, and "not now" does not touch it either, because turning the reader's own decision into an interruption is the app rewording it. **Nor is a copy that is on the device part of the question**, and that follows the same rule the tab lists by: the hold is filled from records that carry no `saved` chapter, so a **refresh** that stopped — the one record that can be both on the shelf and stopped — is not counted in the strip's sentence and not held by it, since the copy it was replacing is intact and readable and is offered again from its own row. It goes on at the next return to the foreground, like everything else the app paused. Entering a profile mid-session is *not* a launch, so a queue left paused there resumes as its container is built, and a cold start onto the picker still asks, because `isLaunchProvider` is the launch container's own fact rather than a moment in time. **The question is a strip and not a dialog**, which is not a matter of taste: nothing here has to be settled before the app can be used, so the reader may ignore it, switch tab or open a chapter, and the copies stay where they are — listed as paused, each with the control that sends it on. It is answered once and goes, which is the whole difference between it and the offline banner this app deliberately does not have: that one was a status, as loud on the twentieth glance as on the first. It hangs **under the app bar of the screen the reader is on**, and that is `DownloadsResumeStrip`'s reason for being a widget each screen wraps its own body in (`body: SafeArea(top: false, child: DownloadsResumeStrip(child: …))`, in Home, Library and Settings) rather than something the shell draws over them: only a screen's own Scaffold knows where its bar ends. The shell's Scaffold has none of its own, so a strip drawn there sat *above* the bar naming the screen and under whatever the device keeps in its top inset. It asks for no inset either — the bar above it has paid for the notch, and a strip insetting itself again would sit twice as low. **The Downloads tab does not carry it**, and arriving there closes the question for the rest of the launch (`seenStopped`): that tab is where every stopped copy is already listed with the control that sends it on, so a strip there would be the same sentence twice on one screen. What it closes is the *question* and not the hold — the copies stay paused, stay held, and a foreground return still does not start them, because visiting a tab decides nothing.

**The seam is `appLifecycleProvider`** (`lib/src/lifecycle.dart`), which `PatraApp` reports the platform's real transitions into and a test reports its own into — a test binding cannot drive a background transition, and this is the only seam #104 adds. What a paused copy looks like is a word, not a gap: the Downloads tab lists the copies that stopped deliberately — what the app paused and what the reader paused, which are one fact to them — under their own **Paused** heading in the offline blue, where a failure and an interruption are named in danger under "Needs attention"; each row says which stop it was, and the pill beside it names the tap in that state's colour.

**The Downloads tab is the view of the lot, not only the shelf of finished copies** (#103). Four sections over the one durable record. In-flight copies are listed at the top, with the **summary line** answering "where is the batch" on the heading's own line — counted in pages rather than copies, because a batch of three is not a third done when its shortest chapter lands. Under them **Paused**, in the offline blue, and then **Needs attention** in danger, which is where a failure and a process that died are named because they are the only thing in this tab nobody chose: a pause is not a failure, and one of them is the reader's own doing, so announcing either in the same breath as a failure is the app saying something went wrong when nothing did. **The copies on the device close the tab under a heading of their own**, and that heading is not decoration: it is the only section here that is not a state, so without one its rows read as belonging to the section above them — which is about copies that stopped, and is not what a finished copy is. Every row of the first three is the same row — the cover, the work it belongs to, the pill at its trailing edge and the bin — and the heading above is what says which section it is in.

**A copy that is on the device belongs to the shelf, whatever its record is doing.** A refresh runs with the copy it is replacing still intact, and a copy found on disk under a record that says it stopped is still a copy — so the sets the tab lists the first three sections from are projected **excluding** every record that carries a `saved` chapter (the `away` map in `DownloadsState.fromQueue`). Without that, a refreshing chapter is drawn twice, once in the shelf and once among the copies on their way, and a copy the reader can already read is announced as something that stopped. What a refresh is doing is reported by the saved row's own control (`_RefreshCopy`), which is the one place it belongs. None of this is new state: every line is projected from the same durable records, which is why a failure seen from anywhere but the series screen, or after a restart, is still named. The storage meter still says what it said, and is still the only storage feedback.

**A copy's progress is a ring; a bar on a cover is reading progress.** `CoverProgressBar` pins a 3px bar in the accent to the bottom edge of every cover that has reading progress in it, so the download's own progress is drawn as a **ring** instead — inside the pill, around the glyph, on the series screen and in the tab alike — and the two can never be read for one another, which a colour alone could not promise on a row that carries both. It is also why nothing is drawn on the cover of a copy that is on its way: its bottom edge belongs to the reading. The ring has three drawings, and the third is the one worth naming: it **turns** while the request is out and the server has not yet said how many pages the chapter has (`downloadsPreparing`), because that is a state of its own and a ring stuck at zero for those seconds says the fetch has stalled. A copy waiting its turn draws what it **already has** — a copy resumed from a pause comes back queued with half its pages, and an empty ring would deny them — and never a ring that turns, since only the count's absence earns that.

**The control is the pill, and a copy that is here is not a control at all.** One widget carries both facts — a word and a glyph — and **which of the two the word is depends on whether there is anything to do**: a copy on its way says what it is doing (Waiting, Preparing, Downloading) beside the pause glyph, and a copy that stopped says what the tap does (Resume, Retry) beside the glyph for it, with the row's own line above naming which stop it was. That is one rule and not two: the word says the thing the reader does not already know — nobody needs to be told a running download is running, and nobody can tell from a failure whether the tap is worth making. The ring carries the progress in every state. **The control is drawn bare — no chip and no outline.** Both were tried and both are gone: the prototype's 1.5pt border, then a fill in the state's colour. Either is a third shape on a row that already carries a cover, a title and the ring, and a chip is what makes a *status* read as a button. What says "control" is the word in the state's colour at w600, over an **invisible tap area** — 8 either side and 4 above and below the ring, so a 24pt mark is a 32pt target: a tap area does not have to be painted to be one. (`_RefreshCopy` on a saved row still wears its fill, and deliberately: it appears only on a copy the server has stopped agreeing with, where a bare word would not be noticed.) The one state that does nothing when touched is the copy that is **saved**: the check says all is well, and taking a copy off the device is a swipe on the row it sits in — the series screen's trailing pane, which arms for whatever the chapter has left of itself on the device, whether that is the saved copy, a fetch still on its way or one that stopped on it, with the confirm dialog for the saved copy and without it for the others, a partial being a fetch nobody has read yet. The same bin sits at the trailing edge of the tab's own rows, and the same word (`removeDownload`) does both.


**A page landing must not rebuild the world.** The percentage that used to watch the whole `DownloadsState` handed every visible row a new state to rebuild from on every single page, which is what made a batch stutter. So a row asks for the one fact it is about: `downloadRecordProvider(chapterId)` for one chapter's record — the record of a chapter that did not change is the *same instance* after every queue write, so another chapter's pages leave it alone — `downloadMembershipProvider` for "is this one saved, is it on its way, is it paused, is there anything here to retry", `savedChapterIdsProvider` for the copies on the device as ids, and `batchSummaryProvider` for the summary line. **The pill watches the whole record**, deliberately: every fact in it is one the pill draws — the state, the pages the copy has, whether the server has said how many there are — and a page landing on *its own* chapter has to move its ring. That watch is why `downloadProgressProvider` is gone: a second, narrower subscription to the same record bought nothing once a ring replaced the bar. Every one of those is compared **by content or by identity of something that did not change**; a fresh `Set` or `List` of records is compared by identity and therefore answers "changed" on every page, which is the trap to avoid. Only the screen's own build watches `downloadsProvider` whole, because `AsyncValue`'s loading and error states are its to draw — and it draws a list of `const` children, which Flutter reuses rather than rebuilding. Pinned by `test/downloads_provider_test.dart` ("a page landing hands no other chapter a new state") and covered by `test/saved_copies_test.dart`.

**What a page file holds is what the chapter is made of, and `meta.json` says which.** A chapter of pictures stores one image per page, fetched from `/api/Reader/image`. A **book** stores the pages the *server* rendered — the HTML `book-page` handed over, **byte for byte** — and asks `book-info` for the page total, since a chapter's own count is of image pages and a book has none. **A copy of a book is a directory that opens on its own** (#129, ADR-0013): the pages, and beside them `pictures/` holding every picture they name, each fetched once however many pages name it and filed under `bookFileName(src)` — the name the page gave it, hashed, with its extension — which is the same name the reader's engine directory files it under (`book_markup.dart`, so the two cannot disagree). The page is **not** rewritten to point at them: it keeps the names the server gave, so a stored page goes through the rewrite pass exactly as the streamed one does and is composed identically, and the reader finds each picture beside the pages by the name the page still says. A picture is written before the page that names it, so a page a retry finds complete is one whose pictures are here, and a retry fetches none it already has; promotion swaps `pictures/` whole, so a picture only an old page named goes with the pages it belonged to. A picture the server refuses is simply not there, and the page still names it — a reader with a server can still ask. The directory also holds the **face the book asks for**, as `book-font` and `book-font-italic`, fetched once: the two files in it that are neither a page nor a picture, so promotion has one exception, and the name they are filed under is written down in the reader's module (`BookFontFile`) rather than here so the two cannot disagree. What the copy costs is its pages plus each picture and face once. **A copy written before #129 carries its pictures inside its pages as data URIs** (`data:;base64,…`) and still opens as it is — such a page is valid, the rewrite keeps a `data:` picture, and `carriedPictureBytes` decodes one for the app's own renderer — so nothing is migrated and nothing is fetched again. It is also why a stored page can be megabytes, and why the reader takes a large one apart off the UI thread. The copy's `format` is what tells an offline reader which of the two it is holding, and a copy stored before any book could be saved reads as pages of pictures. `meta.json` also records the **language** the book was written in when the copy was made (`SavedChapter.language`, from the request the series screen built off `Chapter.language`) — a copy keeps it for the reason it keeps its pagination, since with no server it is the only thing that can say; a copy made before it was recorded has none and opens exactly as it always did (#125). Tested through the same seam as the rest of this directory in `test/downloads_service_test.dart`, and end to end — a copy saved by the downloader, opened with no server, handed the engine the very document the streamed page was — in `test/book_reader_test.dart`. Where a copy files a picture (`bookPictureFile`, over `bookFileName` and `bookPicturesDirectory`) and the decoding of an older copy's carried pictures (`carriedPictureBytes`) live in `features/reader/book_markup.dart`, the walk over a page's markup that the parser, the face and the rewrite all read through — a seam of its own so that nothing needing it has to depend on the module that draws a page (#124). Which pictures a page holds (`pictureSources`) is still the parser's answer, in `book_page.dart`.

Two stores must not be confused. **Saved chapters** live in the documents directory, are chosen by the user and are never evicted; their total is what the Downloads tab reports. The **image cache** is `cached_network_image`'s own store in the system cache directory, holding covers and pages merely browsed online — it grows on its own (it outgrew the downloads three to one on a real device) and the OS may reclaim it. `ImageCacheStore` exposes its size and clears it from Settings; clearing it must never touch the documents directory.

The image cache is **capped**: `ImageCacheStore.trim(maxBytes)` deletes files oldest-first until the cache fits the budget picked in Settings (`ImageCacheLimit`, default 512 MB, persisted like the reading direction). `flutter_cache_manager` only caps by *number* of objects, which says nothing about bytes, so the sweep is ours and works on the files directly — safe because the manager re-checks that a file exists before serving its database row and drops the row when it does not. "Oldest" is by write time; `atime` is unreliable on Android. `trim` runs at startup from `main()`, whenever the limit changes, and — throttled through `trimIfDue` — on every reader page turn, which is where the cache actually grows. Covered by `test/image_cache_store_test.dart` (pass `ImageCacheStore(root:)` a temp dir).

Progress is mirrored into each saved chapter's `meta.json` (`recordProgress`), because the Downloads tab has to show it with no server; the series screen resyncs it from the server, which stays the authority. A chapter opened from the Downloads tab must be opened at its stored page — opening at 0 posts that back and wipes the reader's place.

**A copy is also what carries progress the server has not been told** (#78). `SavedChapter.pending` is the page a reader is on — and, for a book, the place within it — written into `meta.json` *before* the post is attempted and cleared only once the server has taken it, because the copy is the one thing on the device that outlives the app being closed on a train. `syncPendingProgress` sends whatever is left: asked for when `offlineProvider` says the server is answering again (listened to, not watched — going offline must not put the store back to loading) and when the store is read, which is the only thing that catches a journey the app was closed in the middle of. Page and anchor travel together, or a book is put back at words already read. **`SavedChapter.place` is the same pair kept for opening rather than for sending** (#128): written with every `pending` and never cleared by a post, because a book read online and then opened on a train has no server to ask where it was. The reader opens a saved book with no server at `place` (or `pending`, for a copy written before `place` was), as a streamed one opens where the server says. A count the series screen mirrors from the server that is not `place`'s page lets it go — somebody read on elsewhere or marked the chapter by hand — and a copy stored again at another page count drops it, a place on an old page being a place on nothing. And a saved book is **not** opened off the copy while the server is still being asked: opening is once, and spending it on the copy posted the copy's page back over the server's; the first failure, or an offline the app already knows about, settles it. What that costs is a saved book opened online behind a server that hangs rather than refuses: it waits for the request's own timeout, where it used to open off the copy at once. Two edges are accepted: a place read on another device on the *same* page is not learnt by the copy (the series screen mirrors a count, not a place), and marking a chapter unread keeps a place that was on its first page. Nothing is retried by the reader itself. The limit is the app's own rule rather than a gap: what says a server is there is a request, and a device that comes back while the app sits on screens asking for nothing makes none. Coming back online is the user's move everywhere here too — a pull to refresh, the retry beside an offline library — and it is that request which empties the outbox.

**A copy that disagrees with the server about how many pages there are is named, not fixed** (ADR-0009). The server can recount a book whenever it likes, so `SavedChapter.serverPages` holds the total it last gave where that is not what the copy was made with: the row says so in words and offers `refresh`, which stores the copy again at the count the server gives now — never a silent refetch, and never a silent keep, since resuming at the wrong page is the one failure that makes a saved copy look broken. The copy is read, and records progress, either way. Both of these are covered in `test/downloads_provider_test.dart` (the outbox, and a server coming back) and `test/saved_copies_test.dart` (a journey reaching the server, a total that changed and one that did not) — the second over two runs of the app sharing one directory, which is the only shape in which the disk is really the thing carrying it.

`offlineProvider` flips to true when a request fails to *reach* the server (dio connection/timeout errors) and back on the next success. Offline, unsaved chapters are dimmed and non-tappable, and the reader falls back to the stored `SavedChapter` metadata so a saved chapter reads with no server at all.

Offline is shown as a **status in the app bar** — `OfflineIndicator`, a struck-through cloud in `patraDanger` on the trailing edge — and not as a banner over the content, which is what it used to be. A banner is a paragraph: it pushed the shelves down, said the same sentence on three screens at once, and was as loud on the twentieth glance as on the first. The sentence survives as the icon's `tooltip` (which is also its semantics label) and as what a tap puts in a SnackBar, because a struck-through cloud says nothing to a screen reader and little to someone meeting it for the first time. Covered by `test/offline_indicator_test.dart` — whose harness has to build the client with `overrideWith`, not `overrideWithValue`: what turns a failed request into the offline state is `onReachabilityChanged`, wired by the real provider, so a ready-made client leaves the indicator dead however unreachable the server is. **A banner and an empty state are not the same thing, and Home has the second.** When every home provider has resolved into a failure — which now means the catalogue could not answer either, since what Home watches are the overlays — and the device is offline, Home draws `_OfflineHome`: a sentence and — *only where it leads somewhere* — a button in `patraOffline` onto the Downloads tab. That is not the banner coming back. The banner said the indicator's own sentence across the top of content that existed, on three screens at once; this is a screen with nothing whatever on it, in words of its own, naming the one tab that still has something. Keeping the wording separate is what keeps the indicator's sentence unique to the indicator, and `offline_indicator_test.dart` still asserts that sentence never appears over content. The button is drawn only when something really is saved, so a device holding nothing is told plainly that it holds nothing rather than handed a way onto an empty tab — which is why `_OfflineHome` reads the downloads at all. No icon: the bar already carries the struck-through cloud, and Home's other empty state is words alone for the same reason.
