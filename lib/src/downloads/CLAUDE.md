# Downloads and offline

*Loaded when work touches `lib/src/downloads/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

`DownloadsService` stores pages under `<documents>/downloads/<profile>/<chapterId>/`, one extension-less file per page, and writes `meta.json` **last** — a chapter directory without one is a partial download and gets deleted on the next `scan()`. Keep that invariant. The `<profile>` segment is `Profile.id` percent-encoded (see `lib/src/auth/CLAUDE.md`), and `scan()` also **deletes** any chapter directory sitting straight in the downloads root: that is the flat layout this replaced, recognised by being named for a chapter id and so all digits, which no encoded profile id is. A test fixture must therefore be written *through* the service (`saveChapterFixture` in `test_support.dart`) — a hand-built path is not merely filed oddly, it is swept, which makes the test that reads it back quietly vacuous. `DownloadsNotifier` owns per-chapter `CancelToken`s; a cancelled or failed download leaves nothing behind. A save that waited on the first `scan()` must **re-read `state.value` after the await** rather than keep what the scan returned: a second pill tapped during that same wait resumes first and writes its own entry, and building the next state on the stale snapshot drops it — leaving a download running that nothing on screen tracks any more, and a pill that offers to start it a second time over the files already being written. Covered by `test/downloads_service_test.dart` (pass `DownloadsService(root:, profileId:)` a temp dir and a profile id) and by `test/saved_chapters_per_profile_test.dart`.

Two stores must not be confused. **Saved chapters** live in the documents directory, are chosen by the user and are never evicted; their total is what the Downloads tab reports. The **image cache** is `cached_network_image`'s own store in the system cache directory, holding covers and pages merely browsed online — it grows on its own (it outgrew the downloads three to one on a real device) and the OS may reclaim it. `ImageCacheStore` exposes its size and clears it from Settings; clearing it must never touch the documents directory.

The image cache is **capped**: `ImageCacheStore.trim(maxBytes)` deletes files oldest-first until the cache fits the budget picked in Settings (`ImageCacheLimit`, default 512 MB, persisted like the reading direction). `flutter_cache_manager` only caps by *number* of objects, which says nothing about bytes, so the sweep is ours and works on the files directly — safe because the manager re-checks that a file exists before serving its database row and drops the row when it does not. "Oldest" is by write time; `atime` is unreliable on Android. `trim` runs at startup from `main()`, whenever the limit changes, and — throttled through `trimIfDue` — on every reader page turn, which is where the cache actually grows. Covered by `test/image_cache_store_test.dart` (pass `ImageCacheStore(root:)` a temp dir).

Progress is mirrored into each saved chapter's `meta.json` (`recordProgress`), because the Downloads tab has to show it with no server; the series screen resyncs it from the server, which stays the authority. A chapter opened from the Downloads tab must be opened at its stored page — opening at 0 posts that back and wipes the reader's place.

`offlineProvider` flips to true when a request fails to *reach* the server (dio connection/timeout errors) and back on the next success. Offline, unsaved chapters are dimmed and non-tappable, and the reader falls back to the stored `SavedChapter` metadata so a saved chapter reads with no server at all.

Offline is shown as a **status in the app bar** — `OfflineIndicator`, a struck-through cloud in `patraDanger` on the trailing edge — and not as a banner over the content, which is what it used to be. A banner is a paragraph: it pushed the shelves down, said the same sentence on three screens at once, and was as loud on the twentieth glance as on the first. The sentence survives as the icon's `tooltip` (which is also its semantics label) and as what a tap puts in a SnackBar, because a struck-through cloud says nothing to a screen reader and little to someone meeting it for the first time. Covered by `test/offline_indicator_test.dart` — whose harness has to build the client with `overrideWith`, not `overrideWithValue`: what turns a failed request into the offline state is `onReachabilityChanged`, wired by the real provider, so a ready-made client leaves the indicator dead however unreachable the server is. **A banner and an empty state are not the same thing, and Home has the second.** When every home provider has resolved into a failure — which now means the catalogue could not answer either, since what Home watches are the overlays — and the device is offline, Home draws `_OfflineHome`: a sentence and — *only where it leads somewhere* — a teal button onto the Downloads tab. That is not the banner coming back. The banner said the indicator's own sentence across the top of content that existed, on three screens at once; this is a screen with nothing whatever on it, in words of its own, naming the one tab that still has something. Keeping the wording separate is what keeps the indicator's sentence unique to the indicator, and `offline_indicator_test.dart` still asserts that sentence never appears over content. The button is drawn only when something really is saved, so a device holding nothing is told plainly that it holds nothing rather than handed a way onto an empty tab — which is why `_OfflineHome` reads the downloads at all. No icon: the bar already carries the struck-through cloud, and Home's other empty state is words alone for the same reason.
