# Preferences

*Loaded when work touches `lib/src/settings/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

## Preferences: what follows the person, what stays with the device

**Reading direction, magnifying, the width a chapter opens at, the size a book is set at, the line spacing of its lines, the face its words are set in, how many unread chapters one tap saves (`BatchDownloadSize`, three by default, chosen under Settings › Storage), and the interface language belong to a person; the image cache budget belongs to the device** — with one exception the direction makes of its own, below. So does one thing that is not a preference at all: whether this device has been told, once, that the batch's size is a setting (`BatchSizeHintStore`, `batch_hint.dart`) — the interface being discovered is the device's business however many people read on it, so the flag is a row of the device's own, read only when a tap asks.
A family tablet is several profiles at one address, so the split is the same one the downloads made: what the *server* owns comes out right by construction, what the *device* owns has to be scoped by hand — and a setting is scoped by whichever of the two it is really about. Disk is the iPad's, so one budget covers everybody; how somebody reads is theirs, so two people sharing a tablet each get their own. Nothing is synced to the server, deliberately: Kavita keeps preferences of its own and none of them is the reading direction, so syncing would cover one setting of four and buy a conflict to resolve for something a tap already fixes.

`lib/src/settings/profile_preferences.dart` holds the store and the seven providers; `reading_settings.dart` and `locale_settings.dart` are now **the device's own defaults**, under the flat keys they have always written. That is what makes this an upgrade nobody notices: a device set before it held profiles keeps every setting it had, for everybody on it, until somebody chooses otherwise for themselves. `ProfilePreferencesStore` is shaped exactly like `ProfileLockStore` and for the same reasons — one value in the keychain rather than a key per profile, read whole before `runApp`, the device's `Keychain` injected so the rules can be exercised without a real one — the two used to declare an identical `read`/`write`/`clear` under two names, with two memory fakes that were the same class renamed, and are now one interface — and the **store instance** (not three values) handed to `SessionScope`, because what a person chooses mid-session has to survive a handover building the app again on a container of its own.

**Which person's preferences are in force is a function of who is reading, and is decided nowhere else.** Each notifier's `build` watches `sessionProvider`, so entering somebody makes their settings the ones that apply — including the one way in that does *not* rebuild the app, the first profile entered in a fresh container. Nothing had to be added for a handover, and nothing can be forgotten on one.

**Two readings of null had to be told apart.** Never having chosen falls back to the device's default; *choosing* to follow the device is a person asking for the system's language, and the device's default must not stand back in for it. The stored language is therefore a code, the **empty string** for "follow the device", and absent for no choice at all — the one place a sentinel earns its keep, since `MaterialApp` already spends null on the other meaning. A code this build no longer ships reads as no choice, which is the same answer `supportedLocale` gives the device's own.

**The language is written twice, and it is the only one that is.** It is a person's, like the others — and it is also the only preference read where there is no person: the picker and the sign-in form are drawn before anybody has been chosen. There is no screen on which to set the gate's language and there should not be one, so choosing a language moves the device's default too, and the gate is drawn in the last language anybody chose here. A profile that has since chosen for itself is unaffected, because its own choice is looked up first. Magnifying, the width and a book's three settings get no such treatment: nothing outside a session reads them, so their device default is only ever what the flat keys held — or, for the width and for how a book is set, the one the app has always used, since this device never held a key for either — and that is the starting point for a profile that has never chosen. **The reading direction has no device default at all** (#58): it is not a preference of a person's or a device's but a property of the work in front of them, held per series and per library, and the direction a chapter opens in with neither set is detected from the work or falls back to the left-to-right it always opened in. The width's is the one default with no key behind it at all, because this device never held one: `1.0` is not a default a household chose once and has to keep, it is simply how a chapter has always opened. **How a book is set is the same shape, and for the same reason**: `16`, `1.55` and Space Grotesk are not a household's choice, they are what every book was set at before there was anything to choose (#75, #92) — and they are one number, one leading and one face for every book rather than one per work, because they are a property of the person's eyes. Removing a profile takes its preferences with its lock and its saved chapters, in the same confirmation, for the same reason.


**The direction a series — or a whole library — is read in is a person's too** (#56, #65), and lives in the same row as everything else they chose: a `Map<int, ReadingDirection>` of series id to direction, and one of library id to direction, written whole with the rest and read defensively, so a malformed entry costs a series or a library its direction and never a profile its row. They are one map each rather than a key per series or per library for the reason the whole row is one value — read whole before `runApp`, written whole on every change — and what it buys is that `forget` takes them with nothing extra said. Nothing outside the reader reads either, and the chain they are the first two rungs of lives with the reader (`features/reader/reading_direction.dart`), which is also where the two readings of null are told apart for the *direction*: having set a series or a library is not the same as leaving it to fall through to a guess, and only the first outranks one (#57, #65).

**One cover is fetched once, however many profiles browse it.** Every image URL carries the auth key as a query parameter — an image request cannot always send a header — and `cached_network_image` keys on the URL, so a household of four downloaded the same artwork four times and stored it four times under the one budget they share. `imageCacheKey` (`kavita_client.dart`) is the URL with the credential taken out, and **every** cached image in the app is filed under it; `test/shared_image_cache_test.dart` reads `lib/` and fails on a `CachedNetworkImage` drawn without one, because the symptom is a slow app rather than a broken one and nothing else would catch it. The invariant that makes the shared key safe rather than merely cheap is recorded beside it: *the app only ever builds an image URL for content the server has already listed for the profile asking*, so a restricted cover is never requested and therefore never cached — there is nothing in the store for the shared key to hand to somebody who could not have fetched it themselves. A screen that guessed an id would break that, and would be the thing to fix rather than the key. Covered by `test/profile_preferences_test.dart` and `test/shared_image_cache_test.dart`.
