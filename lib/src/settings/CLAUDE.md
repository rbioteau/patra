# Preferences

*Loaded when work touches `lib/src/settings/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

## Preferences: what follows the person, what stays with the device

**Reading direction, magnifying and the interface language belong to a person; the image cache budget belongs to the device.** A family tablet is several profiles at one address, so the split is the same one the downloads made: what the *server* owns comes out right by construction, what the *device* owns has to be scoped by hand — and a setting is scoped by whichever of the two it is really about. Disk is the iPad's, so one budget covers everybody; how somebody reads is theirs, so two people sharing a tablet each get their own. Nothing is synced to the server, deliberately: Kavita keeps preferences of its own and none of them is the reading direction, so syncing would cover one setting of three and buy a conflict to resolve for something a tap already fixes.

`lib/src/settings/profile_preferences.dart` holds the store and the three providers; `reading_settings.dart` and `locale_settings.dart` are now **the device's own defaults**, under the flat keys they have always written. That is what makes this an upgrade nobody notices: a device set before it held profiles keeps every setting it had, for everybody on it, until somebody chooses otherwise for themselves. `ProfilePreferencesStore` is shaped exactly like `ProfileLockStore` and for the same reasons — one value in the keychain rather than a key per profile, read whole before `runApp`, the device's `Keychain` injected so the rules can be exercised without a real one — the two used to declare an identical `read`/`write`/`clear` under two names, with two memory fakes that were the same class renamed, and are now one interface — and the **store instance** (not three values) handed to `SessionScope`, because what a person chooses mid-session has to survive a handover building the app again on a container of its own.

**Which person's preferences are in force is a function of who is reading, and is decided nowhere else.** Each notifier's `build` watches `sessionProvider`, so entering somebody makes their settings the ones that apply — including the one way in that does *not* rebuild the app, the first profile entered in a fresh container. Nothing had to be added for a handover, and nothing can be forgotten on one.

**Two readings of null had to be told apart.** Never having chosen falls back to the device's default; *choosing* to follow the device is a person asking for the system's language, and the device's default must not stand back in for it. The stored language is therefore a code, the **empty string** for "follow the device", and absent for no choice at all — the one place a sentinel earns its keep, since `MaterialApp` already spends null on the other meaning. A code this build no longer ships reads as no choice, which is the same answer `supportedLocale` gives the device's own.

**The language is written twice, and it is the only one that is.** It is a person's, like the other two — and it is also the only preference read where there is no person: the picker and the sign-in form are drawn before anybody has been chosen. There is no screen on which to set the gate's language and there should not be one, so choosing a language moves the device's default too, and the gate is drawn in the last language anybody chose here. A profile that has since chosen for itself is unaffected, because its own choice is looked up first. Reading direction and magnifying get no such treatment: nothing outside a session reads them, so their device default is only ever what the flat keys held — the starting point for a profile that has never chosen. Removing a profile takes its preferences with its lock and its saved chapters, in the same confirmation, for the same reason.

**One cover is fetched once, however many profiles browse it.** Every image URL carries the auth key as a query parameter — an image request cannot always send a header — and `cached_network_image` keys on the URL, so a household of four downloaded the same artwork four times and stored it four times under the one budget they share. `imageCacheKey` (`kavita_client.dart`) is the URL with the credential taken out, and **every** cached image in the app is filed under it; `test/shared_image_cache_test.dart` reads `lib/` and fails on a `CachedNetworkImage` drawn without one, because the symptom is a slow app rather than a broken one and nothing else would catch it. The invariant that makes the shared key safe rather than merely cheap is recorded beside it: *the app only ever builds an image URL for content the server has already listed for the profile asking*, so a restricted cover is never requested and therefore never cached — there is nothing in the store for the shared key to hand to somebody who could not have fetched it themselves. A screen that guessed an id would break that, and would be the thing to fix rather than the key. Covered by `test/profile_preferences_test.dart` and `test/shared_image_cache_test.dart`.
