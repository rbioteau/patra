# Auth: several profiles, one active session

*Loaded when work touches `lib/src/auth/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

A **server** is an address and a **profile** is one person's Kavita account on it, so a family tablet is several profiles at one address (ADR-0003). `Profile` carries `baseUrl`, the Kavita `accountId`, `username`, and its **auth key** — never a password, and never the JWT; an empty `apiKey` means "remembered but signed out", which is what `hasCredential` reports.

**Which profile it is, is `(baseUrl, accountId)` and nothing else** — `Profile.id`, the only thing anything keys on. The address, because a Kavita user id is only unique on the server that issued it; the account id, because two people share one address; and **not** the username, because someone who renames themselves in Kavita is the same person and has to be recognised rather than added a second time. The id is read out of the session's own token (`accountIdFrom`, Kavita's `nameid` claim) rather than asked for, so it is there on a resume and not only in a sign-in response. A token carrying no readable id falls back to the name (`https://a.example#@romain`), which costs exactly the rename the key exists to survive — a guard rather than a path, since a real Kavita signs `nameid` on every token it issues.

`AuthState` is the list plus `activeId`, and `AuthState.active` is non-null only when the active profile still holds its key. `main()` loads it from `flutter_secure_storage` **before** `runApp`, puts it through **`AuthState.atLaunch`** and injects the result via `initialAuthStateProvider` — so what the app opens in is not quite what the keychain holds: a device remembering **more than one** profile arrives with nobody active and lands on the picker, whoever read last. A shared tablet has no last reader, only a previous one, and opening in their session is how one person's page turn moves another's place. The rule is applied there rather than in `SessionStorage.load` (which stays a faithful read: `activeId` is a true fact the rest of the session goes on writing) and rather than in `AuthNotifier.build` (which would make a two-profile session unconstructible in a test). Persistence is `profiles` / `activeProfile`, and **there is no migration into it**: the two layouts before it (a list of servers keyed by address, and before that a single server spread over five keys) are deleted on the first load that finds them and never read. Neither can say which *account* its key belongs to — that id only ever arrives in a token, and no layout kept one — so a migrated profile would carry the name-based fallback id and be created a second time under its real id at its very next sign-in. Deleting is the safer half of the choice too: each of those keys is an auth key, which is a whole Kavita account (ADR-0004), and one nothing will ever use again has no business staying in the keychain. What it costs is the whole row rather than only its secret — the address and the name go with it, so each server is found and typed once more on the upgrade that crosses this.

**What the server owns and what the device owns are both per profile now.** Progress, library access and age restriction are the server's and come out right by construction, because they are kept per account. Saved chapters are the device's, and are filed under `<documents>/downloads/<profile>/<chapterId>/` — the profile segment being `Profile.id` percent-encoded, which is reversible by eye on a device and, unlike a hash, cannot land two people in one directory. Filed by chapter id alone they could not be anything but shared: two profiles at one address share every chapter id there is, so one person's saved chapter was listed, readable and progress-writing in the other's session. `downloadsServiceProvider` is therefore scoped to the session (keeping its previous service across a session ending, exactly as `kavitaClientProvider` keeps its client), while `downloadsRootProvider` is the device-owned root a test overrides. There is **no migration**: a saved chapter cannot be attributed to an account after the fact (#8), so the sweep that already deletes an incomplete download reaches one level up and deletes the flat layout's chapter directories — recognised by being named for a chapter id, all digits, which no encoded profile id is. Removing a profile deletes its saved chapters, behind a confirmation that names how many and how much: once the profile is gone nothing on any screen could reach or explain those files.

**Resuming is a request, and its three failures are three different facts.** `resume` signs in again with the stored key, so reopening the app works however long it has been closed — no clock, and no password. Unreachable is **not** a refused credential: the server is opened anyway on the key it already holds, because offline there is nothing to ask and what such a session reads is what it saved. A **401** is the key itself being refused (rotated in Kavita's web UI, or an account that is gone) and is the only answer that means that, since Kavita reports every credential-side failure of that endpoint as a bare 401 — the entry stays remembered and loses its secret, and the login screen lands on the prefilled form. Anything else leaves the key alone: throwing away a working credential over a 500 would cost a password for a fault that fixes itself. The unreachable case is the one failure that does not throw; the other two do, the 401 as **`SignInExpired`** — a type of its own, because `resume` is what saw the 401 and the screen must not have to re-derive it from state it did not throw. It gets `connectionSignInExpired` rather than `ConnectionFailure`'s bad-credentials message: nothing the person typed was rejected, because nothing they typed was sent. `signInProvider` is the seam that makes all of this testable; there is nothing else in that notifier that reaches a network. Covered by `test/auth_test.dart` and `test/widget_test.dart`.

Mutate auth through `authProvider.notifier` (`login`, `resume`, `signOut`, `switchProfile`, `forget`, `updateToken`); read the current session through `sessionProvider`. `signOut` keeps the profile and drops its **auth key** (a password is needed again), `switchProfile` keeps every key so returning to any of them is one tap, and `forget` takes a `Profile.id` and removes that person alone — the others on their server stay. Entering an account the device already holds resolves onto its profile rather than duplicating it, because `_upsert` keys on the id and `_enter` takes that id from the token the sign-in just answered with. Covered by `test/auth_test.dart`.

**A profile has two verbs, and there is no deliberate sign-out.** *Switch* returns to the picker and keeps every key (the face on the Home bar, and the server card in Settings); *remove* forgets one profile and its key. The button that used to sign out is gone: what it produced — remembered but signed out — is a state a key the server has stopped accepting produces on its own, and `signOut` survives in code for exactly that (`onSessionExpired`). Removal is in **Settings** rather than on the picker, and the move is the guard rather than a tidy-up: the picker stands in front of every session and asks for nothing, so the long press that used to live there let anybody holding the device remove anybody's profile, while reaching Settings means having entered a profile and so holding a credential on the device. Settings manages **every remembered profile**, not only the active one — a button that removes the profile being read as, and a row per other face — because removing only the active one would mean a household signing into each person in turn to tidy up, and a profile nothing can sign into any more (an account deleted on the server) could never be removed at all: a face stuck on the picker for good. One confirmation stands in front of both paths (`_confirmForget`), and it names the person *and* the server. **The face is drawn on a one-profile device too**: that is not the tap `AuthState.atLaunch` spares — that rule is about a cold start — and with no sign-out button left, the face is the only way such a device ever gains a second profile, since the add slot is on the picker.

**A profile can be locked, and the lock is offered to the half of the household one would not first think of.** `lib/src/lock/` is its own module: `profile_lock.dart` holds the lock, the store and the rules, and `biometrics.dart` wraps the device's own prompt — both take their platform dependency injected — the store takes the device's `Keychain`, the way `DownloadsService` and `ImageCacheStore` take their root — because a plugin has nothing behind it on a test binding and a rule that had to go through the real one could not be tested at all. A lock is a salted SHA-256 of a four-digit PIN kept under `profileLocks`, keyed by `Profile.id` like everything else the device owns. **The hash is not what makes it hard to break** — four digits is ten thousand guesses, and anything that can read that row can read the auth key beside it, which is worth incomparably more (ADR-0004). What it buys is that a PIN somebody also uses on a bank card does not sit legible in a file.

**The suggestion goes to a profile the server restricts nothing about, and never to a restricted one** (`suggestsLock`). That is the asymmetry ADR-0003 ends on rather than an oversight: Kavita's age restriction protects the *account* it is set on and does exactly nothing once a child is reading inside an adult's session, so on a family device the thing worth a PIN is the session that opens everything. **An administrator counts as unrestricted whatever rating is set on it**, and that is the same rule applied honestly rather than an exception to it: a Kavita admin can edit any account's restriction, their own included, so a restriction there is a preference and not a limit — reading it as protection would be reading a fence somebody can open from the inside. It is a suggestion and not a rule — Settings will lock any profile — and it needs `Profile.ageRestricted`, which is read off `UserDto.ageRestriction.ageRating` and persisted beside `isAdmin`, as old as the last sign-in for the same reason and costing only a suggestion when it is out of date. `AgeRating.NotApplicable` is -1 and is the one value Kavita's own filters read as no restriction; a response carrying none at all reads as unrestricted, which is the safe direction.

**The copy says what the lock does and refuses the sentence it would be easiest to write.** It keeps the people who share this device out of each other's profiles; it is **not** protection for a lost or stolen device, and ADR-0004 is why that has to be exact — each profile's auth key is a complete, non-expiring Kavita account credential, only its own owner can rotate one, and the saved pages are ordinary files.

**It is enforced in exactly one place, and that is what `atLaunch` had to change for.** The picker's `_enter` asks before it spends the key — before the request and not after it, so the lock is asked offline too, which is the only way it could work at all on the train the picker exists for. Every way into a session that spends a *stored* key comes through that tap, with one exception that had to be closed: `AuthState.atLaunch` opens a lone profile without asking anybody, so it now takes the locked ids (`main()` loads the store before it reads the auth state) and leaves a locked one signed out. Such a device then lands on the picker — one face and one lock, which is no longer a question with one answer. Typing a **password** is deliberately not locked: a password is the credential itself, and whoever has it is who the lock is for rather than who it is against. Removing a profile clears its lock in the same confirmation that deletes its saved chapters, or the lock would outlive the profile and lock that same person out on the day they signed back in.

A locked face is marked the way a refused key is — a padlock in the same corner of the avatar, in the same `patraAccent`, plus the word under the name — because they are the same kind of fact about a tap: something extra it will cost. One `_FaceBadge` draws both, and they can never share the corner, since a profile with no key left is signed in with a password and asks for no PIN.

Settings locks **only the profile being read as** — the one place it does not manage every remembered face, and the asymmetry is the point: a lock is chosen by the person it stands in front of, so setting one on somebody else's face would shut them out behind a PIN nobody told them, and clearing one would be taking their lock off for them. Changing or clearing does not ask for the current PIN a second time, because getting to Settings meant getting past it.

**Biometrics are the fast path and the PIN is the real one.** `DeviceBiometrics` asks `local_auth` with `biometricOnly: true` — the alternative, letting the platform fall back to the device's own passcode, would put the lock screen's PIN in front of a profile, which on a family tablet is the one secret everybody already knows. Availability is `getAvailableBiometrics().isNotEmpty` and **not** `canCheckBiometrics`, which answers whether the hardware is there and is true of a phone whose owner has never registered a finger — that would draw a key on the pad that fails every time and never says why, since a refusal here is deliberately silent. Every call is guarded, because a device with no sensor, a missing plugin and a prompt the OS refuses all mean the same thing to the caller: not a way in, use the PIN. The pad is already drawn behind the prompt, so a refusal costs nothing. Android needs `FlutterFragmentActivity` for it (androidx's `BiometricPrompt` is a fragment; without it the prompt simply never appears, which reads as a device with no sensor) and iOS needs `NSFaceIDUsageDescription`, without which the system kills the app rather than refusing the prompt.

`widgets/profile_lock_sheet.dart` is the one surface a PIN is ever typed on, asking for it and setting it, because they are the same secret and a second layout would be a second thing to learn. A **pad and not a text field**: four digits want no punctuation, no return key and no candidate bar, and on the picker a keyboard would slide up over the faces the sheet is drawn in front of. Nothing counts attempts and nothing locks out — what this stands between is family members, and the person mistyping is usually the one it belongs to. Covered by `test/profile_lock_test.dart` (the rules, through the injected vault) and `test/profile_lock_ui_test.dart` (the picker, the four biometric cases, and Settings).

**Entering a second profile builds the whole app again** (`SessionScope`, `lib/src/auth/session_scope.dart`). It owns the `ProviderContainer`: `main()` hands it the state the app opened in plus every override the *device* owns, and when the profile it has been serving is replaced by another it builds a fresh container from those same overrides and throws the old one away. The teardown is **deliberate rather than selective**, and that is the whole reason it lives here: a list of profile-scoped providers to invalidate keeps growing — two were added while this was being designed — and a forgotten entry does not read as a stale number but as one person seeing another's library. Nothing is listed, so nothing can be left off. The scope is keyed on its container, so what is rebuilt is the widget tree as well: a new `GoRouter` with its own navigator key, and no screen state from the previous person either. Two consequences worth knowing. It is **entering** that starts the app over and not leaving — a session that has merely ended leaves a shell whose screens are on their way out and still reading through `kavitaClientProvider`, and there is nothing to hide in the meantime, since the picker draws from the profile list alone. And returning to the *same* profile is therefore not a handover at all: it keeps its container and its shelves are already there. `AuthState.handedOver` is what the next container is seeded with — every key kept, and the JWT dropped from everybody who is not the one now reading, since that is the only place a token could outlive the session that spent it. Pinned by `test/profile_switch_test.dart`, which asserts the container identity rather than a provider's value: a test that only checked one number would pass for whichever provider it happened to name.

`kavitaClientProvider` watches only the session's *identity* (`Profile.id`, `apiKey`), not its tokens: the client patches its own token on renewal, so rebuilding it there would invalidate every data provider mid-read. It also keeps the previous client alive across a session ending, because Riverpod flushes a dirty provider that has listeners at the end of the frame — so a session going null recomputes this while the shell is still on screen and still reading through it. That keep-alive is **per container** and was a top-level variable: a static one outlived the container it was built in, so the fresh container a handover builds would hand the *previous* profile's client to anything that asked before a session had been entered, which is a window onto the wrong session on exactly the device this feature is for. On a 401 the client **mints a new JWT from the auth key** — a login, not a refresh — and retries the request; a failure of the *retried* request is not a session failure, so keep those two error domains separate (`test/kavita_client_test.dart`). That is also what makes a session entered offline self-healing: it starts with no token at all, and the first request that reaches the server 401s and gets one. **Only a bare 401 from that renewal may end the session**, and that rule is new with the key. Firing `onSessionExpired` on any failed renewal was affordable while a session was a token pair expiring anyway — what it cost was a credential with a day left in it. `onSessionExpired` is wired to `signOut`, which now deletes the one secret the profile is remembered by, so a 500, a proxy answering in Kavita's place, or the network going away between the 401 and the renewal must all leave it alone. Same rule as `resume`, one endpoint, one way to be refused.

The client is given the `username` as well as the key, so its renewal is byte-for-byte the request `resume` makes. `LoginDto` says Kavita ignores the name when a key is present, so it is belt and braces — but the alternative was one shape exercised against a real server and a second, subtly different one on the path that recovers a session.
