# The catalogue

*Loaded when work touches `lib/src/catalogue/`. The root `CLAUDE.md` stays the entry point and carries the rules that apply everywhere; this file holds the argument behind this directory alone.*

## The catalogue: what the device remembers of a profile's shelves

A **third store**, beside the saved chapters and the image cache, and the line between them is what it holds: the catalogue **names what exists and never holds a page**. `lib/src/catalogue/`, files under `<documents>/catalogue/<profile>/` — `spine.json` (the libraries plus every library's series list, read whole), `series/<id>.json` (one series' volumes, its own row and its description, read per series), `ondeck.json`. The profile segment is `Profile.id` percent-encoded, exactly as `downloads/` does it and for the same reasons. ADR-0005 records why it is files rather than a database, and what that costs. It is read by the Library tab, by Home's libraries, its On deck shelf and its Continue card, and by the series screen, and what a series it can no longer picture falls back to is `CoverPlaceholder` (see the `patra-design` skill).

**It is written from our own models' `toJson`, in the wire's own shape.** Every `toJson` in `models.dart` writes exactly the keys the `fromJson` beside it reads, so a stored file round-trips through one parser and the contract oracle governs the store as well. It is deliberately not Kavita's payload verbatim: 6 of `SeriesDto`'s 38 fields are read here, and storing the other 32 would be bytes paid for on every device to use none of them.

**A version stamp discards rather than migrates**, and on *any* file: the stamp is on the shape, a bump changes every file, and a version mismatch deletes the whole profile catalogue. Same principle as the auth layouts being deleted rather than read — a catalogue is recoverable by one refresh, so a migration path is code that can only be wrong.

**A read is a request and a write, in that order, and the order is written down once.** Each of the six used to spell the same four steps out for itself — watch the client, resolve the store, make the request, write what came back — which is four chances to get it wrong six times over; two of the six carried no comment saying so at all. `catalogue_read.dart` owns the choreography now and a declaration says only what it asks for and what it writes. Writing in the fetch rather than in a listener beside it is still the choice: a listener would keep the request pure but cannot be built for a `.family` without every screen registering its own, since a family's live keys cannot be enumerated — and writing on the path means the write cannot be skipped, because the only way to get a fetched list is through the thing that stores it. Three rules now live in that one place. **Everything is resolved before the request**, because these providers are `autoDispose` and a screen left mid-flight disposes one — a `ref` read after that throws rather than answering, which would turn a background cache write into a failed fetch. **A read replaces its list**, so a series deleted on the server or lost to this profile disappears at the next successful fetch; merging would keep it for good. And **only a complete answer replaces**: the write runs after the request has returned and never otherwise, which is what `allSeriesForLibrary`'s paging rests on — it rejects until a short page has ended the run, so a run that dies on page 3 never reaches a write and cannot replace 250 stored series with 200. `serverRetry` is applied there too, so a read cannot be declared without it. **The write step is handed the store, the prefetch and the client** (`CatalogueDeps`), which is what keeps the two reads with eager-fill bookkeeping from being special cases: `libraries` starts the fill, `seriesForLibrary` tells it a library is already stored. That second call had **no test at all** — nothing could tell "the tab's own fetch stored this library" from "the fill did" — so dropping `markStored` would have been silent, and what it costs is a 2000-series library paged twice on the one visit that opens the tab. `test/catalogue_write_path_test.dart` pins it by counting pages per library.

**Writes are serialized per file, and the spine is read inside that queue.** The series screen fires the volumes, the row and the description at once and all three merge into one `series/<id>.json`; the eager fill writes the spine while the Library tab's own fetch is writing it too. Left to interleave, each read-modify-write builds on the file as it was before the others and the last to land is the only part kept — which is the loss "only a complete answer replaces" exists to prevent, arriving by a different route. `_oneAtATime` chains work per file name, `loadSpine` goes through it as well (two callers arriving before the first read finishes must not both read), and every spine update reads `_spine` **inside** the queued work rather than before it.

**The store is resolved before the request, never after it.** These providers are autoDispose, so a screen left while its fetch is in flight disposes the provider mid-body — and a `ref` read after that throws rather than answering, which would turn a background cache write into a failed fetch. The store's own writes never throw either: they are reached from a fetch a screen is waiting on, and a device with no room left must show its shelves rather than an error about a cache. What it does lose is the *next* launch; the session goes on holding what it fetched in memory.

**The eager fill hangs off the library list, wherever that landed.** Home asks for that list too, so one trigger covers both tabs rather than a rule per tab: when it lands, every library's series list is fetched **sequentially** (that is the whole of "low priority") so a library never opened is still navigable offline. `CataloguePrefetch` remembers the *successes* per container, so a pull-to-refresh does not page 2000 series again while a library that failed is retried; the Library tab's own fetch marks its library as done. Volumes stay a trace of what was actually opened — nothing prefetches them, or a device that browsed a big library would hold every chapter of all of it.

**Loading is per path.** `main()` awaits the active profile's spine before `runApp` where `AuthState.atLaunch` produced one — the launch animation runs 7.8s behind it, and four store loads plus `ClientIdentity.resolve()` are already awaited there. `SessionScope` reads it behind the tap on the picker path, where there is no first frame to protect because the tap is already a request; it asks `profileCatalogueProvider` **by id** rather than through the session's own store, because it is called from inside `authProvider`'s own notification and the session derived from that state has not been recomputed yet. What makes the awaited read worth anything is that `main()` hands the store it read into over as an override of **one key** of `profileCatalogueProvider` — so the session reads that same instance, already holding the spine, and anybody entered later gets a store of their own from `catalogueRootProvider` like every other profile.

**It is read cache-first, through an overlay, and the precedence rule is the whole feature.** `overlaid` (`catalogue/catalogue_overlay.dart`) is one function: **live wins; otherwise stored data draws as data, not as loading; otherwise the live error; otherwise loading.** Written once and shared rather than open-coded per list, because each branch is a distinct bug — lose the third and the offline empty states go with it, lose the second and a shimmer is drawn over shelves the device is holding. Two of them read like details and are not. **`hasValue`, not `isLoading`, is what "live wins" asks**: a refresh in flight carries the answer it is refreshing, so falling through to the catalogue there swaps the list under the person pulling it (`test/catalogue_overlay_test.dart` drives a real refresh for this, which also pins the assumption it rests on — that Riverpod carries the previous value across one). And **a catalogue still being read counts as loading, never as an absence** — a fifth branch, added deliberately, because the alternative is not a simpler rule but a cold offline start drawing its error state and replacing it with the shelves one frame later.

**`spineOverlay` is a function called from an overlay's own body, and never a provider — that is what keeps the spine current.** The store replaces its whole `Spine` on every write, so a provider that cached one would answer with the spine as it stood when it was first built, and the ordinary case is exactly the one that breaks: browse a library online (which writes the spine *and* prefetches every other library into it), lose the connection, open a second library. Its fetch fails, and a spine cached at launch has never heard of it — an `_ErrorState` over series that are sitting on disk. Read inside the body, the spine is re-read whenever the fetch moves, which is precisely when the answer can change. `test/catalogue_overlay_test.dart` pins it, and that test was written by reintroducing the bug to watch it fail. The read is **synchronous wherever the store already holds the spine** (`main()` has usually awaited it before the first frame, so going through a future would cost a frame of loading over shelves already in hand) and the one-shot disk read is still *watched*, because the path in from the picker awaits nothing — without that, the failure a cold offline start drew would never be replaced by the spine that landed after it.

**There are three of those seams, one per file, and they are not interchangeable.** `spineOverlay` reads the spine, `onDeckOverlay` reads `ondeck.json`, `storedSeriesOverlay` reads `series/<id>.json` — all three call `overlaid`, which stays the one rule, and all three take the fetch as an argument for the same reason. What differs is the file's own shape. **On deck is held in memory exactly as the spine is** (`CatalogueStore.onDeck`, set by `putOnDeck` and by the one disk read), and for the argument above rather than for speed: without it the fallback is frozen at whatever the session's first read found, so a pull with the connection newly gone would answer with *yesterday's* shelf under the person who pulled it.

**The series file is deliberately not held, and the asymmetry is principled rather than an omission.** The spine and the ranking are read once per session and written by somebody *else* — the eager fill fills the spine for libraries no screen asked for — so a frozen fallback really does go stale under them. Each of the three parts of a series file has exactly **one** writer, its own fetch: a part that has been fetched has a live value and never consults the stored copy, and Riverpod carries that value across a refresh that fails (which is what `overlaid`'s first branch already rests on), so going offline mid-session does not lose it. `_seriesReadProvider` is also `autoDispose` where the spine's read is not, so it dies with its fetch and a screen coming back re-reads the file rather than answering from a snapshot. Both halves are pinned under "one series' volumes" in `test/catalogue_overlay_test.dart` — which is where a store-side cache would have had to be argued for.

**An empty stored answer is an answer for a library and an absence for the other two.** A library stored as empty is a state the grid has copy for, and falling through to the failure would replace that copy with a retry button. An empty *library list* and an empty *On deck* are absences: a shelf draws nothing either way, so reading them as answers would only tell Home's offline gate that something came back and take `_OfflineHome` away from a device that really does hold nothing.

**`storedSeriesOverlay` answers with two facts, not one.** `Overlaid<T>` is `({AsyncValue<T> value, bool fromCatalogue})`, because progress is the one case where a screen has to know which of the two answered — see below. **`fromCatalogue` is `!live.hasValue && value.hasValue`** and not `!live.hasValue`: a fetch still in flight has answered with nothing either way, and a screen drawing a skeleton must not be told the device's memory is what it is drawing. The two reads that do not care (`catalogue.series`, `catalogue.seriesMetadata`) take `.provider`, which is one hop below the same `Overlaid` — so the value and the fact can never disagree about one series, and the only caller that needs the fact asks for `.overlaid`.

**A read is a pair, and only one half of it is reachable.** A **read** is the request plus the device's memory laid under it, and there are six: `libraries`, `seriesForLibrary`, `onDeck`, `volumes`, `series` and `seriesMetadata`, all declared in `catalogue/catalogue_reads.dart` and reached under a prefix — `catalogue.volumes(seriesId).provider`. They used to be declared at the top of the three screens that draw them, which is how each fetch came to be public: pull-to-refresh had to reach it from the screen and there was nowhere else for it to live. It also meant Home imported a 1194-line series screen for one provider, and that the module holding the overlay rule held none of the reads applying it. The fetch is now **private to the read**, and what a caller gets is three handles: `.provider` to watch, `.refreshable` to ask again and await the answer (it is what `refresh` *and* `read` take, so one handle covers both), `.invalidatable` to ask again without waiting. They are handles rather than methods because `Ref`, `WidgetRef` and `ProviderContainer` are three unrelated sealed types over two `@internal` bases, so no one parameter type could serve a provider, a screen and a test; `refresh` and `invalidate` are already methods on all three, and what they were missing is something safe to be handed. A **keyed** read hands out one of these per key and never a handle to the whole family, because `invalidate` accepts a family and would drop every key — which is why it is a function rather than an object with a `call`: there is no family handle to reach for. `volumes` is a `StoredRead`, which answers with **two facts**: `.overlaid` carries `fromCatalogue` beside the value, and `seriesVolumesProvider` is the only caller that asks. `libraryTypeProvider` moved with them, since it is a question about the catalogue's contents and two other screens were importing a 779-line screen to reach it; `currentLibraryProvider` stayed, and reads `catalogue.libraries.provider` — offline a comic library would otherwise say "chapitre" and the scan menu would have no library to act on. **What was a source scan is now the compiler's**: a screen cannot watch what it cannot name. `test/catalogue_overlay_test.dart` still reads all of `lib/`, but for the mistake still available — a `…FetchProvider` *declared* outside `lib/src/catalogue/`, which is a seventh read growing where nothing can police it. It stays a scan rather than a type because what makes a fetch safe is being unreachable, and that is a fact about which file it is in.

**The volumes read reaches one screen further than Home, and that is not a second mechanism but the same read.** `catalogue.volumes` is what `seriesVolumesProvider` — and so the series screen — watches, so one read gives Home's card and that screen's chapter rows the catalogue alike. Duplicating it into a card-only provider was the alternative, and it is exactly the fork this file spends a section warning against. What is pinned here is the **mechanism** (the two overlay tests above); the *screen* offline is #34's, along with the two overlays it still needs and the hero skeletons that have to stop with a failure the catalogue cannot answer either.

**`catalogue.libraries` is one question both tabs ask**, deliberately, so they cannot disagree about which libraries exist. That means Home's own offline gate (`nothingCameBack`, which reads `libraries.isResolvedFailure`) consults the catalogue from the moment this read exists: offline with a populated spine, Home draws remembered libraries instead of `_OfflineHome`.

**Home offline draws the shelf and the card, and `_OfflineHome` stands only where the catalogue is empty too.** An app that opens on "nothing here, try Downloads" while the device knows perfectly well what was being read is the inconsistency this whole change exists to remove. Three things about it. What `ondeck.json` holds is **the server's own ranking, not structure** — Kavita computes On deck from `PagesRead > 0 && PagesRead < Pages` plus a recency clause, so a stored one may be hours old — and it is drawn with **no decoration of any kind**: the app bar's struck-through cloud already says the answer may be stale, and per ADR-0005 an individual row is never marked. The **Continue card came along for free**: it is picked out of the On deck answer (`featuredSeries`) rather than fetched, so it draws wherever the featured series' volumes happen to be in the catalogue, and where they are not the existing rule already degrades correctly — the volumes overlay resolves into its fetch's failure, `continueHeroProvider` collapses on `hasError`, and the removal from the shelf is keyed on the card *being* there, so the series simply stays in the shelf. What did have to go is that provider's `offlineProvider` short-circuit, which was the honest answer while the card's chapter could only come from a server and is now the one thing that would refuse the catalogue's. `_OfflineHome`'s Downloads button stays gated on something actually being saved, so a device holding nothing is still told plainly that it holds nothing.

**Progress is overlaid, never absorbed.** The shelves and the grid show the server's last word, and the saved copy's progress is laid over a row only where there is a saved copy. Making the catalogue absorb what was read offline would make every screen agree on the train and then walk visibly backwards on reconnect, when the server's older answer replaces it. The real fix is a replay journal, which is separate work (ADR-0005).

**On the series screen's rows that makes the chain three deep, and the order is the whole of it: the catalogue, under the server's last word, under any unconfirmed mark-read.** `seriesVolumesProvider` is where the top two land. The mark-read stays on top because it is the newest word about a row and the entire point of it is that the row redraws on the gesture rather than on the round trip. Between them, **where the rows are the device's memory the saved copy's progress is laid over them**: `meta.json` is where offline reading writes, so the stored volumes carry the server's last word about a chapter somebody has since read on a train. Where the server has answered, the saved copy is left alone — there the server is the authority and the stored copy is what gets corrected, which is `_ChapterRow`'s mirror. That mirror is then **inert on a remembered row**, the two numbers already agreeing because the overlay put them there, and that is the same fact stated twice rather than luck: without it the mirror would write the catalogue's older number back into `meta.json` and undo the reading. The saved copy wins **unconditionally** where it applies, and deliberately not by a clock or a `max` — either would get a mark-unread the server really did make exactly wrong — with the mirror being what keeps a row from walking backwards, since in the ordinary case it has already carried the server's word into `meta.json` on the same visit that wrote the catalogue. The watch on the saved chapters is **conditional on `fromCatalogue`**, or every row of a live list would rebuild on each tick of a download.

It is laid on in the provider rather than in the row so the hero's resume point and the row's own progress can only ever name one number, and that is what "the hero's ring stays the server's last word" has to be read against: the **series-level** ring and the tally do (they come from `seriesProvider` and from counting volumes, neither of which this touches), while a ring drawn under a *chapter's* cover is that chapter's progress by the rule every cover in this app obeys — and offline the true number for it is the saved copy's, since a bar disagreeing with the row for the same chapter two lines below would be the screen contradicting itself.

**Offline reach stops where a tap could not work.** A series with no saved chapters is still enterable — it says what exists and how far through it you are, which is the answer to "what have I got on this train" — with every unsaved row dimmed and unopenable, as the screen already did offline. Two controls had to learn that same rule, because rows appearing offline at all is new: the **save pill is gone on an unsaved chapter** (it could only offer a fetch that cannot happen, while a copy already here keeps its pill, since removing one is local), and the **hero's resume button is disabled where the chapter it would open is not saved** — it opens one of the rows below it, and a hero offering what the dimmed row refuses is the screen disagreeing with itself. The *format* is deliberately not asked about there, as it never has been: the reader refuses an EPUB outright, because a deep link and a resume do not pass through this screen either. The leading swipe pane (mark read/unread) is already gone offline. Reader-level data stays out of the catalogue: `chapter-info` and `pageDimensions` are how a page is laid out rather than how the app is navigated, and a saved chapter already carries what the reader needs.

It **dies with its profile**, in the confirmation that already takes the lock, the preferences and the saved chapters — and is deliberately *not* named in that copy, which lists what a person chose to keep and what it costs them.

Two things a test has to get right. Fixtures go **through the store**, the same rule as `saveChapterFixture` and for the same reason. And the catalogue root and the downloads root must be **different directories**: both stores file by profile, so one root would put a spine where `DownloadsService.scan` sweeps. A screen test that hands the tree a client rather than signing one in wants `testCatalogue()` from `test_support.dart` — the same move as overriding `kavitaClientProvider`; a test *about* the scoping overrides `catalogueRootProvider` and lets the real provider key the store. Covered by `test/catalogue_store_test.dart`, `test/catalogue_write_path_test.dart`, `test/catalogue_overlay_test.dart` (the rule, each overlay, and the source check), `test/library_offline_test.dart` (the tab itself, with no server) `test/home_offline_test.dart` (Home's shelf, its card and the empty states, all against `UnreachableServer`) and `test/series_offline_test.dart` (the series screen with no server: the whole screen from memory, the dimming, the saved copy's progress, the skeletons stopping and the three-deep order).
