# Patra design decisions

*Invoked, not directory-scoped. The design rules that a session can break from anywhere — the two hard rules, the swipe pane and the button, and where `gen_app_icons.sh` may read from — are stated in the root `CLAUDE.md`; this file is the argument behind them and the rest of the design system.*

The two hard rules (accent vs offline colour, and where the serif is allowed) stay in the root `CLAUDE.md` and are not repeated here.

The handoff was drawn for a phone, so **the iPad is ours to reason about**, and a screen full of phone furniture is what it looks like when nobody did. One token carries it: `isTabletLayout(context)`, which asks the *shortest* side against `tabletBreakpoint` so a phone in landscape is still a phone (the same question `ClientMetrics.isTablet` answers for Kavita). Three shapes, three answers, and which one a screen is decides everything:

- **A column of rows** (series, downloads, settings, and the sheets settings opens) runs **the full width at the app's own gutter**, like every other screen. It was once capped and centred, on the argument that a row's parts otherwise drift to opposite edges with a gulf between them — true, and the cure was worse: at 560 an 820pt iPad wore about 150pt of nothing down each side, and a narrow column floating between two empty bands reads as more wrong than the gap it closes. **The answer to a tablet's width is a grid, not a narrower column.** Inside the row the phone's furniture still *grows*: 46x66 covers become 80x115 (`rowCoverWidth`/`rowCoverWidthTablet` in `theme.dart`, because the series screen and the Downloads tab draw the same row and drifted apart when each held its own number), the row breathes, the type goes one step up the scale. Those sizes were originally derived as ~13% of the capped column — the share a phone gives the cover — and with the cap gone the cover is ~10% of its row again; they stay because they read well at arm's length, not because the proportion still holds. So does the decode width, which is computed from the width actually drawn rather than frozen at the phone's 138 — a constant there is the blur the bigger cover was meant to remove. Pinned by `test/series_sections_test.dart`, which also pins that the column is *not* capped: the cover starts one gutter from the screen edge and the save pill ends one gutter from the other.
- **A grid of cards** (the library grid, the home libraries) keeps the size a card is drawn at and takes **another column** instead: `_gridColumns` and `_cardWidth` divide the width by a max card width, with the handoff's phone count (three covers, two cards) as the floor. Three covers across an iPad would be 250pt each; five at 146 is the same screen the phone shows, only more of it.
- **A shelf and the reader canvas run edge to edge** — that is what they are. A shelf spends a tablet's width on bigger tiles (112 → 152); the reader is left alone, because there the whole screen is the point.

Two things must never scale with the screen — **a swipe pane and a button**. `flutter_slidable` asks for an `extentRatio`, but a ratio that is a sensible drawer on a phone slides a tablet's row far enough to hide the cover and title the swipe is about to act on, so `_ChapterRow` measures the row and converts a *width in points* into that ratio; and a button given a whole hero (or a whole settings screen) to fill stops reading as a button, so the resume and sign-out buttons stop at 280. Pinned at 820x1180 by `test/tablet_layout_test.dart`, `test/series_hero_test.dart` and `test/series_sections_test.dart`.

**Read is marked, never erased.** A finished row wears a **2pt `patraAccent` rail** down its leading edge (`ReadRail` in `widgets/read_mark.dart`; its width is the `readRailWidth` token) and says the word inside its own metadata line — "Lu · 26 pages" / "Read · 26 pages", one localized string with the count as a placeholder, so French is not assembled in English word order. The title stays `patraText`. Both halves of the mark are one widget each — `ReadRail` and `PageCountLine`, in `widgets/read_mark.dart` — for the same reason `rowCoverWidth` is not written twice: the series screen's chapters and the Downloads tab are the same row and drift apart when each holds its own answer. The rail is taken **out of** the row's leading gutter rather than added to it — painted over the gutter the row already had — so a read row and an unread one line up and a column keeps one left edge.

What it replaced was two marks for one state: a gold check pastille pinned on the cover and a short uppercase `READ` tag beside the title, both *additions* to a row meant to be scanned, with the title muted underneath them. Dimming the row instead was the obvious cure and is the one thing forbidden here: **opacity is already spoken for**. A lowered opacity in this app means *unavailable, something must be done* — a chapter that cannot be opened offline, a profile whose key the server has stopped accepting — and read says the opposite. Nothing about this treatment fades or desaturates anything, and a row that is both read and unavailable is attenuated exactly once, by the availability rule alone. On the Downloads row the accent **stops where the sentence about reading does**: the copy's size follows in the muted tone, because how many bytes a file is says nothing about progress and gold is spoken for. A **library grid tile** carries no metadata line and no rail, so its one mark is `CoverProgressBar` **run full**: the bar used to erase itself at `progress >= 1`, which made the one signal carrying meaning disappear at the moment it was complete. That is one behaviour for every cover rather than a tile-only rule: a hero whose picture is a finished series now runs its bar full too, which is the same sentence the tile below it says. Covered by `test/read_mark_test.dart`, `test/series_sections_test.dart` and `test/saved_copies_test.dart`.

**An empty library is a state, not a blank screen.** A library is empty because the server has not scanned its files, so the copy points at the server and names the library — the name is picked *out of* the localized sentence by `indexOf` rather than concatenated onto it, or a French sentence would be assembled in English word order; a name it cannot find simply loses its emphasis. The dashed rounded outline is the handoff's mark for **a place to fill** (`DashedBorderPainter`, shared with the "add a server" slot), as against the solid borders that enclose something already there. The empty state is pullable like the grid it stands in for, because after asking for a scan there has to be a way to look again. Covered by `test/empty_library_test.dart`.

**An administrator can ask for a scan of any library, not only an empty one.** The Library tab's app bar carries a menu beside the offline indicator whose one item is that request, because the empty state was the only way in and an administrator whose libraries all have content could not ask at all. The item is **worded** rather than drawn: a refresh glyph there would be taken for the pull-to-refresh already on the screen, which does the opposite job — pulling asks Kavita what it already knows, a scan is what changes the answer. It is drawn only for an administrator (the same rule that leaves an EPUB row untappable: this app does not draw a control that can only earn a 403) and only once a library is selected, since a menu whose item acts on "the current library" is meaningless while the list is in flight or has failed — `currentLibraryProvider` is that one question, asked by the grid and the menu alike so they cannot mean different libraries. Scope is the selected library; `scan-all` is deliberately absent and would be a second item.

The empty state **keeps its own button**, because the two do different jobs — it explains why there is nothing and offers the fix in place, the menu is for content that has gone stale — so this is two entry points to one action. The action is `LibraryScanNotifier`, a notifier family keyed by library id, and that is what makes them one: a single in-flight flag, so a scan asked for from either place disables the other, and one wording of the failure rather than two. It reports the failure instead of wording it (a notifier has no `BuildContext`) and `_askForScan` is where both callers say it. Two asymmetries are deliberate. The grid is invalidated on the **empty-state path only** — from the menu an invalidate would drop a populated grid to its skeleton for a background job that has produced nothing yet, and the confirmation already says to pull down. And **offline the item is disabled with its reason rather than hidden**, so it cannot be mistaken for having lost the role; it is gated on `offlineProvider` and not on a health probe, because being wrong there is self-correcting (the request fails, `ConnectionFailure` words it, the flag flips) and it keeps the item honest with the indicator beside it. `libraryEmptyBody` is two role-specific strings for the same reason the button is: the non-admin's still sends them to Kavita, which for them is the only route, and the administrator's would be wrong to, with a button two lines below. Covered by `test/library_scan_test.dart`.

**A cover with no picture draws the series, not a grey rectangle.** Covers live in the image cache, which the device owns, is capped by the Settings budget and swept oldest-first, and which the OS may reclaim outright — and a cover is deliberately never pinned (ADR-0005), so a stored series list routinely outlives the pictures of it. `CoverPlaceholder` (`widgets/cover_placeholder.dart`) is the answer, and it is the prototype's own cover vocabulary rather than an error state: a 45° hatch in two near-black tones, dark and low-contrast on purpose so it never competes with the real artwork beside it, with the series' initial in the serif in the middle — the answer the picker already gives a face with no photograph, and the serif because a series title is the title of a work. Not the frond: the frond is the app's identity, and stamping it on sixty tiles of somebody's library says *Patra* where the tile should say *this series*. The reading-progress bar is still drawn on top, because the catalogue knows the progress.

What follows are decisions rather than details. The tones are **derived from the series id**, so a tile is recognisably the same tile between sessions and no shelf is one colour — a bit-mixing hash and not `hashCode`, because a library numbers its series in a row and an integer's hash is near enough the integer, and written down here because the tile has to survive an upgrade rather than merely a run. **What that palette can hold is 24 tiles, not 360**, and that is the finding worth keeping: at a tenth of full saturation and a sixth of full lightness the whole pair spans about eight units of each channel, so hue on its own buys almost nothing — a tenth of the wheel apart still comes out two units apart, which is to say identical. The seed therefore picks one of six hue sectors and one of four brightness steps across the handoff's own range (.150 to .185), which is two dozen pairs a person can actually tell apart against three hundred they cannot; a library of sixty series draws each tone two or three times, deliberately. Nothing it returns can be read as `patraAccent` or `patraOffline`, which are spoken for: these are shades of near-black that happen to lean, not colours. The seed is the **series** even where the picture would have been a volume's or a chapter's, so a column of chapter rows reads as one series rather than a stack of unrelated colours and a shelf tile matches its own hero. And it is **one drawing for both of `CoverImage`'s states** — literally one object, handed to `placeholder` and `errorWidget` alike: a tile showing its initial while the cover loads says strictly more than a grey rectangle, and a grid cannot flicker between two placeholders as its covers resolve at different times. There is no offline branch, because that failure is local and immediate and this widget otherwise never asks. Everything is sized off the box it is given (the band grows with the *fourth* root of the width — a fixed number of points gives a row's cover five bands and a tablet's shelf tile nineteen, a fixed share shrinks the row's to 3.7pt of noise, and the fourth root lands within 0.7pt of all four numbers the prototype authors by hand), since the same drawing is asked for at 46pt on a chapter row and 152pt on a tablet's shelf. Covered by `test/cover_placeholder_test.dart`.

The mark is **the word पत्र**, in the accent gold, and there is one master: `assets/icon/patra-1024.png`. It used to be a palm frond in two variants, and the choice between them was a size rule rather than a taste — below about 72px the five blades and the gaps between them each fell under two pixels and the fan closed into a blob, so every icon at or under 72px came from a three-blade compact master. That rule went with the frond: a word is two solid glyphs with no gaps to close, so one master answers every size and there is nothing to choose between. `flutter_launcher_icons` is still gone, because a generator would rewrite `Contents.json` and the mipmaps under a pipeline that owns them. `./tool/gen_app_icons.sh` is the pipeline now: it renders every size `AppIcon.appiconset/Contents.json` names …

The **launch screen the OS paints is the ink and nothing else**, on every path. It used to centre the mark, and that was right when Flutter's first frame was the finished app; it is wrong now that the app opens by *assembling* the word out of an empty screen (see `lib/src/features/launch/CLAUDE.md`). A mark painted by the window would appear, vanish at Flutter's first frame and then rebuild itself. What has to be continuous from cold start is the ink, not the logo. So `drawable/launch_background.xml` is the ink layer alone, and on Android 12+ (`values-v31`, plus `values-night-v31` because the night qualifier outranks the API one) `windowSplashScreenAnimatedIcon` points at `drawable/splash_none.xml`, a deliberately **transparent** drawable: the system always composites *something* over its splash background and reaches for the launcher icon when the attribute is unset, so a transparent drawable is the only way to make that something be nothing. iOS mirrors it — `LaunchScreen.storyboard` paints the same ink and no longer carries an image view. That ink is now the same colour as the page (`patraBg`, #111722), where it used to be a separate brand tile one shade warmer: the new mark is assembled *out of* the app's own background, so a window a shade off it would read as a cut rather than as a lift.

The Android **adaptive** icon is deliberately *not* generated: its foreground is `drawable/patra_mark.xml`, a vector, so the launcher icon cannot pixelate at any size a launcher asks for and no generator can rewrite `mipmap-anydpi-v26/ic_launcher.xml` with an inset that double-pads a vector already carrying its own padding. It is the brand kit's own `assets/branding/patra-foreground.svg` — the word's two outlines, which are the two glyph clusters shaped by HarfBuzz off Tiro Devanagari Sanskrit — with the SVG's `<g>` transform carried over unchanged as the outer `<group>`: a `translate` of 264.256/205.603 and a `scale` of 4.377 on a 1024 canvas, which is exactly what puts the word's bounding box dead centre. Only the middle 66dp of the 108dp canvas is guaranteed visible, and the kit sized the foreground for it: the box lands at x 252–772, y 374–650 of 1024, comfortably inside. `drawable/patra_mark_mono.xml` is the Android 13+ themed variant: the same two paths in white, because the system ignores the colour and tints the shape from the wallpaper — nothing to fade outward now, the word being one solid mass where the frond's blades used to be carried by `fillAlpha` alone. Regenerate the two together. `values/colors.xml` keeps `patra_ink` = `#111722`, which is the page's own colour (`patraBg` in `theme.dart`), the icon's ground and the window the OS paints — one colour for all three.
